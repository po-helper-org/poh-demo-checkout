# Демо контура производства

Сквозной прогон на этом репозитории: заявка превращается в задачу, задача — в
системные требования, требования — в код, код — в отревьюенный PR. Человек
вмешивается ровно один раз.

Стенд поднимается одной командой — `poh-infra/harness`. Как поднять локально и
что прописать снаружи: [`harness/LOCAL.md`](https://github.com/po-helper-org/poh-infra/blob/main/harness/LOCAL.md).

---

## Прогон, на котором это проверено

Не сценарий, а факт: задача [#1](https://github.com/po-helper-org/poh-demo-checkout/issues/1)
прошла путь целиком 2026-08-18, без ручного вмешательства между шагами.

| Что смотреть | Где |
|---|---|
| Триаж и фазы | метки на [#1](https://github.com/po-helper-org/poh-demo-checkout/issues/1): `advisor:feature-request` → `priority:P3` → `phase:pr-review` |
| Аналитика | ветка `research/issue-1`, каталог `sa_documentation/FNR/FNR_1/` |
| Разработка | [PR #6](https://github.com/po-helper-org/poh-demo-checkout/pull/6): три файла, тестов стало 15 вместо 8 |
| Декомпозиция | [SubIssue #4](https://github.com/po-helper-org/poh-demo-checkout/issues/4) — агент нашёл edge-кейс, завёл отдельно и не стал чинить в той же ветке |
| Ревью | комментарий `PR Reviewer Guide 🔍` на PR #6 |

## Две активности контура

| | Research | Develop |
|---|---|---|
| Работает с | Issue, текстом, аналитиком | веткой, кодом, PR |
| Цель | превратить запрос в описанный документ: БФТ → системные требования → декомпозиция | взять Issue и автономно разработать, протестировать, открыть PR, довести по ревью |
| Кто исполняет | цепочка FNR через `claude -p` в воркере | OpenHands headless на раннере GitHub Actions |
| Видно в | Temporal: `IssueAnalysis` | Actions: `OpenHands Resolver` |

Между ними — точка передачи `ready-for-dev`: единственное место, где контур сам
отдаёт работу человеку. `DEVELOP_AUTOSTART=1` эту паузу снимает.

## Сценарий

### Акт 1. Заявка становится задачей

1. **Claude Code заводит Issue** по минорной фиче.
2. **Вебхук поднимает workflow** — в Temporal появляется `IssueLifecycle`
   с id `issue-<owner/repo>-<N>`. Стадии видны по мере прохождения.
3. **Триаж отрабатывает сам**: `advisor:*` (что это за запрос), `priority:*`
   (по формуле, с разбором в комментарии), `phase:classified`. Дальше цикл
   паркуется и ждёт решения человека.

Смотреть: Issue в GitHub и `IssueLifecycle` в Temporal UI одновременно — метка
`phase:*` и стадия workflow показывают одно и то же состояние двум разным людям.

### Акт 2. Research

4. **Команда `/analyze`** комментарием (либо метка `run:analyze`).
5. **Запускается `IssueAnalysis`** — отдельный workflow, видно в Temporal.
   Внутри цепочка FNR: `task → concept → debate → sysreq → validate`,
   каждая стадия отдельной активностью.
6. **Результат**: ветка `research/issue-<N>` с артефактами в
   `sa_documentation/FNR/FNR_1/`, комментарий со сводкой, фаза
   `phase:system-requirements`.
7. **Передача разработчику**: метка `ready-for-dev` и чеклист готовности —
   что известно, с чего начать и **что осталось неопределённым** (строки
   `[УТОЧНИТЬ]` вычитываются из самих артефактов).

### Акт 3. Develop

8. **Разработка стартует сама** (`DEVELOP_AUTOSTART=1`): активность Develop
   диспатчит `openhands-resolver.yml` и паркует цикл в фазе `in-development`.
9. **OpenHands работает на раннере**: читает Issue + системные требования +
   `AGENTS.md`, пишет код, гоняет тесты.
10. **Edge-кейсы уходят в SubIssue** — с `root-issue: #N` и меткой
    `origin:agent`. В текущей ветке они не чинятся.
11. **На каждый SubIssue поднимается свой `IssueLifecycle`** и проходит
    сокращённый триаж: он уже классифицирован создателем, поэтому только дедуп
    и приоритет.
12. **PR открыт** с `Closes #N`; прогон докладывает событие `pr-open`, и фаза
    задачи двигается сама.

### Акт 4. Ревью

13. **PR-Agent ревьюит** сразу после открытия PR — вызовом из того же прогона,
    комментарий `PR Reviewer Guide 🔍`.
14. **Claude Code вносит правки** и пишет `/review`.
15. **Ревью перезапускается** и переписывает тот же комментарий на месте.
    Замечание пропало — закрыто.
16. **Задача готова к merge** и ждёт живого разработчика.

## Что показать в Temporal

Одна лента на всю цепочку: `IssueLifecycle` живёт от заведения задачи до
влитого PR, а дорогие стадии — `IssueAnalysis`, `IssueEstimation` — дочерние
прогоны под ним. Ожидание человека и ожидание внешнего агента — это не пауза в
коде, а состояние с дедлайном: задача, о которой забыли, эскалируется сама.

## Границы, о которых честно сказать

- **Код пишет OpenHands, а не контур.** Он живёт на раннере GitHub Actions:
  своё окружение, свой sandboxing, свой счёт минут. Контур его запускает и
  слушает доклад.
- **Ревью не чек-лист «исправлено/нет».** `/review` заново ревьюит текущий
  диф, а не сравнивает с прошлым прогоном. Пропало замечание — исправлено.
- **Merge остаётся за человеком.** Контур доводит до состояния «готово к
  слиянию» и останавливается.
