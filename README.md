# poh-demo-checkout

Маленький сервис расчёта стоимости заказа. Существует не ради себя: это
**демо-стенд контура производства** — на нём гоняется полный цикл от заявки до
влитого PR, и код намеренно простой, чтобы предметом разбора был контур, а не
предметная область.

```
Issue заведён
  └─ Issue-Agent: триаж (advisor:* + priority:* + phase:classified)
       └─ аналитика FNR → ветка research/issue-N + системные требования
            ├─ остались вопросы [УТОЧНИТЬ] → комментарий и ожидание ответа
            └─ декомпозиция → SubIssue по релизам MVP / GROW / SUPPORT
                 └─ ready-for-dev + чеклист готовности
                      └─ OpenHands: разработка → PR с Closes #N
                           ├─ edge-кейсы по дороге → .followups.md → SubIssue
                           └─ PR-Agent: ревью
                                └─ круг правок → /review → «замечаний нет»
```

Подзадачи декомпозиции своей разработки НЕ заводят: весь объём MVP исполняет
родитель одним прогоном и одним PR. Иначе на репозитории одновременно работали бы
несколько агентов.

## Сервис

Сервис предоставляет HTTP-интерфейс для расчёта стоимости заказа с поддержкой
промокодов, способов оплаты и метрик.

### Маршруты API

| Метод | Путь | Назначение | Коды ответов | Пример тела запроса | Пример тела ответа |
|---|---|---|---|---|---|
| GET | `/healthz` | Проверка здоровья сервиса | 200, 405 | — | `{"status":"ok","uptime_sec":123}` |
| GET | `/stats` | Получение статистики сервиса | 200 | — | `{"requests":42,"errors":1,"lastError":"..."}` |
| POST | `/quote` | Расчёт стоимости заказа | 200, 400, 404, 415 | См. ниже | См. ниже |

#### POST /quote

**Пример тела запроса (минимальный):**
```json
{
  "items": [
    {
      "sku": "a",
      "price": 1000,
      "qty": 2
    }
  ]
}
```

**Пример тела запроса (полный):**
```json
{
  "items": [
    {
      "sku": "a",
      "price": 1000,
      "qty": 2
    }
  ],
  "promoCode": "WELCOME10",
  "paymentMethod": "cloudpayments",
  "invoiceSeq": 1
}
```

**Пример успешного ответа:**
```json
{
  "goods": 2000,
  "delivery": 300,
  "discount": 200,
  "promoStatus": "applied",
  "total": 2100,
  "payment": {
    "provider": "cloudpayments",
    "amount": 2100,
    "currency": "RUB",
    "invoiceId": "INV-A1B2C3D4-1"
  },
  "paymentStatus": "ready"
}
```

**Ошибки валидации:**
- `{"error": "заказ без позиций"}` — пустой массив `items`
- `{"error": "некорректная цена в позиции X"}` — `price` не число или < 0
- `{"error": "некорректное количество в позиции X"}` — `qty` не целое или <= 0
- `{"error": "минимальная сумма заказа 1000, не хватает X"}` — сумма товаров < 1000
- `{"error": "неизвестный способ оплаты: X"}` — неподдерживаемый `paymentMethod`

Доставка бесплатна от 3000 (включительно). Зависимостей у сервиса нет — это его
свойство, а не упущение.

### Ограничения метрик

Маршрут `GET /stats` возвращает счётчики посещений (`visits`) и успешных транзакций
(`successes`). **Важно:** счётчики хранятся в памяти процесса и сбрасываются при
перезапуске сервиса. Это осознанное архитектурное решение демо-сервиса: отсутствие
персистентности упрощает код и позволяет сосредоточиться на контуре производства,
а не на хранении данных. На графиках метрики будут обнуляться после каждого
перезапуска — это свойство архитектуры, а не ошибка или потеря данных.

### Расхождения между README и кодом

- **Текущий README** описывает только простой случай без промокодов и оплаты,
  но **код** поддерживает: промокоды (`promoCode`/`promo`), способы оплаты
  (`paymentMethod`), генерацию `invoiceId`, поле `invoiceSeq` для retry-логики
- **Код** возвращает больше полей, чем показано в README: `discount`, `promoStatus`,
  `payment`, `paymentStatus` — текущий пример ответа (`{"goods":2000,"delivery":300,"total":2300}`)
  соответствует только базовому случаю без промокодов и оплаты
- **Код** включает дополнительный маршрут `GET /stats` для статистики, которого нет
  в README
- **Код** валидирует `Content-Type` и возвращает 415 при неверном заголовке, но README
  не документирует это поведение
- **Код** поддерживает минимальную сумму заказа (1000 руб.) с ошибкой валидации,
  но README упоминает только порог бесплатной доставки
- **Код** использует параметр `promo` для обратной совместимости наряду с `promoCode`,
  что не отражено в README

## Отгрузка

Влитое сюда доезжает до прод-контура не руками, а Delivery-Agent (реализация в
`poh-infra/harness`): команда `/release` собирает релиз из одобренных PR, катит
их по одному и после каждого шага проверяет живой сервис по `.delivery/checks.json`
— файлу в **этом репозитории**, который определяет, что считается правильным
поведением.

Порядок шага: выкатка → прогон проверок → **окно наблюдения** → повторный прогон
тех же проверок. Окно нужно потому, что зелёная проверка в первую секунду ничего
не говорит про минуту жизни: сервис, падающий через полминуты, обязан быть
пойман и откачен, а не отмечен зелёным. Логика окна наблюдения реализована в
`poh-infra/harness`.

Провал на любом этапе — `git revert` мержа, возврат прежней сборки, остановка
очереди.

**Разделение ответственности:**
- **Этот репозиторий:** `.delivery/checks.json` — определения проверок, критерии
  успешной отгрузки, ожидаемое поведение сервиса
- **Внешняя инфраструктура (`poh-infra/harness`):** сам Delivery-Agent, логика
  окна наблюдения, команда `/release`, координация шагов отгрузки

## Автоматика

| Workflow | Когда | Что делает |
|---|---|---|
| `ci.yml` | PR и push в main | тесты |
| `openhands-resolver.yml` | диспатч от Issue-Agent (либо метка `fix-me`) | разработка по Issue → PR |
| `pr-review.yml` | три входа: вызов из разработки, событие `pull_request`, команда `/review` в PR | ревью PR-Agent + доклад в цикл |

Три входа у ревью не для надёжности, а по необходимости. PR, созданный
`GITHUB_TOKEN`, событий workflow не порождает — оттуда вызов из разработки. PR,
открытый контуром на своём сервере (режим `local`), Actions вообще не проходит —
оттуда `pull_request`. Перепроверку после круга правок просит сам контур командой
`/review`, и пишет он её токеном GitHub App, то есть ботом: фильтра по типу автора
на этой команде нет намеренно.

`pr-review.yml` определяет исход **по выводу** `pr-agent`, а не по коду возврата:
на rate-limit модели тот пишет `Failed to review PR` в лог, оставляет в PR
заглушку «Preparing review...» и завершается успешно. Доклад в цикл несёт
`headRefOid` — коммит, по которому шло ревью: без него круги правок выглядели
повторной доставкой одного и того же факта, и второй круг не начинался.

Правила, по которым работают агенты, — в [`AGENTS.md`](AGENTS.md) и
[`CLAUDE.md`](CLAUDE.md). Конфигурация контура целиком — `poh-infra/harness`.
