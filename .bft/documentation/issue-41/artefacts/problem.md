## Rich Picture — Реконструкция проблемной ситуации

### Акторы

| Актор | Роль | Интерес |
|---|---|---|
| Покупатель | Оформляет заказ | Хочет оформить быстро, без регистрации |
| Поддержка | Ищет заказы по email/телефону | Нужен идентификатор для поиска |
| Курьер | Доставляет заказ | Нужен телефон и адрес доставки |
| Продукт (PO) | Владелец фичи | Хочет снизить отток на этапе оплаты |
| Юрист | Комплаенс | Требует соблюдения ФЗ-152, GDPR |
| Система (существующая) | Требует регистрацию на шаге оплаты | Блокирует часть покупателей |

### Потоки

```
Покупатель → [форма регистрации] → [шаг оплаты] → [заказ создан]
                                                    ↓
                                               [письмо со статусом]

Текущий блок:
Покупатель → [форма регистрации] → ❌ Часть уходит без завершения

Целевой поток (to-be):
Покупатель → [гостевая форма: email + адрес + телефон] → [заказ создан]
                                                    ↓
                                    [письмо: статус + ссылка на регистрацию/вход]
```

### Конкурирующие worldviews

| Worldview | Позиция | Источник |
|---|---|---|
| **Заказчик (PO)** | Обязательная регистрация — барьер, часть покупателей уходит на шаге оплаты. Нужно разрешить гостевой заказ. | po-statement.md:7-8 |
| **Privacy (юридик)** | Нельзя показывать подсказки «email уже зарегистрирован» — это утечка факта регистрации. | po-statement.md:29 |
| **Поддержка** | Почта обязательна — по ней оператор ищет заказ. | po-statement.md:17 |
| **Существующая архитектура** | Сервис `POST /quote` только рассчитывает стоимость. Оформление заказа и профили — вне текущей системы. | architecture.md |
| **Курьер** | Нужен телефон и адрес для доставки. ФИО не обязательно. | po-statement.md:30 |

### Конфликты worldviews

1. **Гостевой доступ vs Привязка к профилю:** Если email уже привязан к аккаунту — заказ создается как гостевой, но потом привязывается. Момент привязки неясен.
2. **Privacy vs UX:** Подсказка «email уже зарегистрирован» улучшает UX, но нарушает privacy.
3. **MVP vs Полнота:** HowToDemo требует базовый флоу, но обработка case «email уже привязан» нужна для MVP (по уточнению заказчика).

## Gap — Разрыв

### Проблема 1: Обязательная регистрация блокирует оформление

**Что не так:** Покупатель не может оформить заказ без создания учётной записи. Часть уходит на шаге оплаты.

**Доказательство:**
- «Сейчас оформить заказ можно только после регистрации: на шаге оплаты форма требует логин, и часть покупателей уходит именно здесь» [po-statement.md:7-8]

### Проблема 2: Нет идентификатора для гостевых заказов

**Что не так:** Поддержка не может найти гостевой заказ без email.

**Доказательство:**
- «почта обязательна — по ней ищется заказ в поддержке» [po-statement.md:17]

### Проблема 3: Risk утечки факта регистрации

**Что не так:** Подсказка «email уже зарегистрирован» раскрывает информацию о существовании аккаунта.

**Доказательство:**
- «Никаких подсказок о существовании аккаунта на форме — это утечка факта регистрации» [po-statement.md:29]

### Проблема 4: Неясность привязки заказа к профилю

**Что не так:** Механизм привязки гостевого заказа к существующему профилю (если email уже привязан) не задан в As-Is.

**Доказательство:**
- Уточнение описывает to-be, но As-Is механизм отсутствует [po-statement.md:26-29]
