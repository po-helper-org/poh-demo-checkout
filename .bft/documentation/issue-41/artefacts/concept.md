## Концепт 1 — Полноценный гостевой флоу (чистый)

### Суть

Введение отдельной сущности `GuestOrder` в базе данных, интеграция с системой рассылки писем, полноценный механизм привязки к профилю после регистрации/входа. Существующий флоу с регистрацией остаётся нетронутым (D-041-1).

### CATWOE

| Элемент | Содержание |
|---|---|
| **C** Customer | Покупатель (может оформить без регистрации), Поддержка (находит заказ по email/телефону), Курьер (получает телефон и адрес) |
| **A** Actor | Команда разработки реализует форму, хранение, рассылку, привязку |
| **T** Transformation | Покупатель с email + адрес + телефон → создан гостевой заказ → отправлено письмо → при входе заказ привязан к профилю |
| **W** Worldview | Гостевой доступ снижает отток на этапе оплаты, не ломая существующий флоу; privacy защищён (PD-001, PD-002) |
| **O** Owner | Product Owner утверждает требования; Архитектор согласовывает схему БД |
| **E** Environment | Ограничения: без внешних зависимостей (D-002), соответствие ФЗ-152/GDPR (требует уточнения у юриста) |

### Плюсы

1. **Закрывает Gap 1 полностью**: полноценный механизм гостевого заказа без принудительной регистрации
2. **Scalable**: архитектура рассчитана на рост — не требует переделки после MVP
3. **Правильная привязка (Gap 4)**: чёткий механизм: гостевой заказ → письмо → вход → привязка к существующему профилю
4. **Privacy по умолчанию**: никакой утечки факта регистрации (PD-001, PD-002)

### Минусы / риски

1. **Зависит от архитектуры**: требует уточнения у архитектора (какая БД, какая рассылка)
2. **Высокие усилия**: нужно менять несколько сервисов (форма, заказы, профили, рассылка)
3. **Риск незакрытых вопросов**: регуляторика (ФЗ-152, GDPR) не уточнена — может потребовать переделку

### Влияние

| Компонент | Изменение |
|---|---|
| Форма оформления заказа | Добавить вариант «без регистрации», поля email/адрес/telefono |
| БД заказов | Новая сущность/таблица `GuestOrder` (email, phone, address, created_at) |
| Система профилей | Механизм привязки гостевых заказов при регистрации/входе |
| Рассылка писем | Интеграция: шаблон письма + ссылка на регистрацию/вход |
| Существующий флоу | Без изменений (D-041-1) |

### Оценка усилий

**L (Large)** — требует координации с архитектором, изменений в БД, интеграции с рассылкой.

### Открытые вопросы

| Вопрос | Статус |
|---|---|
| Какая БД хранит заказы и профили? | **Блокирует** |
| Какая система рассылки писем? | **Блокирует** |
| ФЗ-152, GDPR — требуются ли согласия/cookie? | **Требует уточнения** |

## Концепт 2 — Упрощённый гостевой флоу (компромисс)

### Суть

Минимально жизнеспособный флоу: форма гостевого заказа + базовое хранение в существующей БД (флаг `is_guest`) + простая отправка письма (через встроенный Node.js модуль `sendmail` или SMTP). Привязка к профилю откладывается до пост-MVP или реализуется через SubIssue.

### CATWOE

| Элемент | Содержание |
|---|---|
| **C** Customer | Покупатель (может оформить быстро), Поддержка (находит заказ — есть email) |
| **A** Actor | Команда разработки реализует форму, минимальное хранение, stub-рассылку |
| **T** Transformation | Покупатель → гостевой заказ в БД (флаг is_guest) → письмо отправлено (stub) |
| **W** Worldview | Быстрый старт MVP, усложнение по мере необходимости; privacy соблюдается |
| **O** Owner | Product Owner принимает MVP-границы |
| **E** Environment | Без внешних зависимостей (D-002) — рассылка через stdlib |

### Плюсы

1. **Быстрый старт к HowToDemo**: можно показать флоу энд-ту-энд за 1 спринт
2. **Минимальные изменения**: не требует новой архитектуры БД, используется флаг `is_guest`
3. **Закрывает Gap 1 для MVP**: покупатель действительно может оформить без регистрации
4. **Privacy**: не раскрывает факт регистрации (PD-001)

### Минусы / риски

1. **Техдолг по привязке (Gap 4)**: механизм привязки к профилю не реализован — выносится в SubIssue
2. **Stub-рассылка**: письмо может не доставляться в production — нужна доработка
3. **Дубликат профиля (Gap 2)**: риск, если повторный заказ на тот же email создаст новый профиль вместо привязки

### Влияние

| Компонент | Изменение |
|---|---|
| Форма оформления заказа | Добавить «без регистрации», поля email/адрес/telefono |
| БД заказов | Добавить поле `is_guest` (boolean) в существующую таблицу |
| Рассылка писем | Stub через `nodemailer` (stdlib) — шаблон письма в коде |
| Привязка к профилю | **Отложено** в SubIssue |
| Существующий флоу | Без изменений (D-041-1) |

### Оценка усилий

**M (Medium)** — форма + БД-поле + stub-рассылка, без привязки к профилю.

### Открытые вопросы

| Вопрос | Статус |
|---|---|
| Механизм привязки гостевого заказа к профилю? | **SubIssue после MVP** |
| Какая БД (достаточно ли добавить поле)? | **Уточнить у архитектора** |
| ФЗ-152, GDPR — требуется ли согласие? | **Требует уточнения** |

## Концепт 3 — Демо-флоу с email-токеном (быстрый)

### Суть

Минимальный путь к HowToDemo: на форме gast checkout сохраняется email в качестве «временного идентификатора» заказа в памяти или файле (без реальной БД). Письмо не отправляется — ссылка генерируется и показывается на экране (демо-режим). Привязка к профилю не реализуется.

### CATWOE

| Элемент | Содержание |
|---|---|
| **C** Customer | Покупатель (может оформить в демо-режиме) |
| **A** Actor | Один разработок: форма + in-memory хранилище + заглушка письма |
| **T** Transformation | Покупатель → в-memory заказ → показана «ссылка» на экране |
| **W** Worldview | HowToDemo работает fastest path; production-решение — потом |
| **O** Owner | Product Owner принимает демо-границы |
| **E** Environment | Без внешних зависимостей (D-002); без БД, без рассылки |

### Плюсы

1. **Самый быстрый путь к HowToDemo**: можно запустить за часы, не за спринты
2. **Нулевые зависимости**: не требует БД, не требует рассылки, не требует архитектора
3. **Визуализация флоу**: заказчик видит UX, может дать feedback

### Минусы / риски

1. **Не production**: данные теряются при перезапуске — только для демо
2. **Не закрывает Gap 2**: поддержка не сможет найти заказ (нет persisted email)
3. **Не закрывает Gap 4**: привязка к профилю не реализована
4. **Только визуальный флоу**: реальное письмо не отправляется

### Влияние

| Компонент | Изменение |
|---|---|
| Форма оформления заказа | Добавить «без регистрации», поля email/адрес/telefono |
| Хранение заказа | In-memory Map `orderId → {email, phone, address}` |
| Рассылка писем | **Заглушка**: показать ссылку на экране |
| Привязка к профилю | **Не реализуется** |
| Существующий флоу | Без изменений (D-041-1) |

### Оценка усилий

**S (Small)** — форма + in-memory Map + stub-показ ссылки, один разработок, полдня.

### Открытые вопросы

| Вопрос | Статус |
|---|---|
| Какая БД? | **Не требуется для демо** |
| Какая рассылка? | **Не требуется для демо** |
| Привязка к профилю? | **Не реализуется** |

# Архитектурные дебаты — Issue #41

> **Epic:** issue-41 — Гостевой заказ без регистрации

## Раунд 1 — Защита

### Позиция Архитектора (защита Концепта 2)

Я выбираю **Концепт 2 (Упрощённый гостевой флоу)** как оптимальный баланс между ценностью и усилиями.

**Аргумент 1: Закрывает критический Gap 1 за разумное время**

Концепт 2 позволяет снять блокировку оформления заказа — основную боль заказчика (po-statement.md:7-8) — за один спринт. Форма гостевого заказа + базовое хранение (флаг `is_guest`) + stub-рассылка дают работающий флоу, который можно показать в HowToDemo.

**Якорь:** po-statement.md:7-8 — «часть покупателей уходит именно здесь» на шаге логина; concept.md:92 — «быстрый старт к HowToDemo: можно показать флоу энд-ту-энд за 1 спринт».

**Аргумент 2: Минимальные архитектурные изменения**

Добавление поля `is_guest` в существующую таблицу заказов — это не требует новой сущности, миграций схемы, координации с архитектором по БД. Сервис рассылки через stdlib (`nodemailer`) — в границах D-002 «без внешних зависимостей».

**Якорь:** concept.md:93 — «не требует новой архитектуры БД, используется флаг `is_guest`; CLAUDE.md:63-67 — принцип «без внешних зависимостей».

**Аргумент 3: Привязка к профилю вынесена в SubIssue — но для MVP не критична**

HowToDemo заказчика (po-statement.md) требует проверить флоу: оформить заказ → получить письмо → создать аккаунт → прошлые заказы подтянулись. Этот флоу работает и с отложенной привязкой: первое письмо отправляется сразу, а механизм привязки реализуется в следующем спринте как SubIssue. Это не блокирует MVP.

**Якорь:** po-statement.md:156-161 — HowToDemo включает шаг 5 «убедиться, что прошлые заказы подтянулись»; concept.md:99 — привязка «отложено в SubIssue».

**Аргумент 4: Privacy соблюдён — нет утечки факта регистрации**

Концепт 2 сохраняет требование УТ-2: никаких подсказок «email уже зарегистрирован». Заказ создаётся как гостевой, письмо содержит приглашение войти (если email уже привязан). Это полностью закрывает Gap 3.

**Якорь:** concept.md:95 — «Privacy соблюдается — не раскрывает факт регистрации (PD-001)»; regulatory.md:30 — PD-001.

**Аргумент 5: Легко эволюционировать до Концепта 1**

Концепт 2 — это не тупик, а итерация. После MVP и подтверждения ценности можно развернуть полноценный GuestOrder и интеграцию с продакшн-рассылкой (Концепт 1). Инвестиция в Концепт 2 не пропадёт — флаг `is_guest` мигрирует в отдельную таблицу как часть эволюции.

**Якорь:** concept.md:236-239 — рекомендации для выбора: Концепт 2, если «нужен быстрый MVP, а привязка к профилю и рассылка могут быть доработаны позже».

### Позиция Адвоката Дьявола (атака)

**Контраргумент 1 (Линза: нагрузка/отказ зависимости): Stub-рассылка — точка отказа в production**

Концепт 2 использует `nodemailer` через stdlib, но это не решает задачу реальной доставки писем. Если SMTP-сервер недоступен, письмо не доходит — заказ создан, но пользователь не получает ни подтверждения, ни ссылки для входа. Поддержка не сможет помочь: email есть, но письма нет. Это создаёт разрыв между «заказ оформлен» и «заказ найден».

**Якорь:** concept.md:100 — «Stub-рассылка: письмо может не доставляться в production — нужна доработка»; bft-context-pack.md:218 — интеграция с рассылкой: блокер «какая система рассылки писем?».

**Контраргумент 2 (Линза: идемпотентность/гонки): Дубликат профиля — Gap 2 не закрыт**

Концепт 2 не решает case «повторный заказ на тот же email». Покупатель оформляет первый гостевой заказ (email → is_guest=true), затем второй (тот же email → ещё одна запись с is_guest=true). При регистрации какой заказ привязывается? Оба? Только первый? Концепт 2 говорит: «SubIssue после MVP». Но ФТ-3 уже декларирует требование: «повторный заказ на ту же почту не создаёт дубль профиля».

**Якорь:** po-statement.md:18 — ФТ-3: повторный заказ не создаёт дубль; concept.md:101 — риск «дубликат профиля (Gap 2)».

**Контраргумент 3 (Линза: изменение требований 6-12 мес): Концепт 2 не масштабируется**

Через 6-12 месяцев после MVP гостевые заказы могут составлять 30-50% потока. Флаг `is_guest` в одной таблице с обычными заказами усложняет querying, индексы, отчётность. Когда потребуется полноценная сегрегация (GuestOrder vs Order), миграция будет дороже, чем сразу реализовать отдельную сущность в Концепте 1.

**Якорь:** concept.md:39 — «Scalable: архитектура рассчитана на рост — не требует переделки после MVP» (про Концепт 1).

**Контраргумент 4 (Линза: безопасность/ПДн): Регуляторика не уточнена — риск переделки**

ФЗ-152 требует согласия на обработку ПД (email, телефон, адрес). Концепт 2 не уточняет, где галочка согласия, где хранится факт согласия, что с заказами, созданными до внедрения согласия. Юрист может потребовать: все гостевые заказы должны иметь явный consent-флаг. Это потребует schema change — переделка Концепта 2.

**Якорь:** problem.md:176-180 — вопросы юристу: «требуется ли согласие на обработку ПД в гостевом флоу? (Высокий приоритет)»; regulatory.md:41-43 — ФЗ-152, GDPR требуют уточнения.

**Контраргумент 5 (Линза: скрытые зависимости между командами): Поддержка не сможет эффективно искать заказы**

Концепт 2 хранит email в БД, но не описывает, как поддержка ищет заказ. Есть ли UI? API? Что если покупатель забыл email и хочет найти по телефону? Концепт 2 не закрывает Gap 2 для операционной поддержки — только факт хранения email не означает, что есть инструмент поиска.

**Якорь:** problem.md:82-83 — «Поддержка ищет по email или телефону»; problem.md:101-105 — Gap 2: «нет идентификатора для гостевых заказов».

## Раунд 2 — Пересмотр

### Ответ Архитектора

**На Контраргумент 1 (отказ рассылки): Уточнение границ — НФТ на рассылку**

Справедливо — stub-рассылка в production риск. Добавляем НФТ-1: «Время доставки письма ≤ 30 секунд, SLA 99.5%». Для MVP принимаем этот риск явно: в HowToDemo проверяется флоу в development-окружении, где stub работает. Для production выносим SubIssue: интеграция с продакшн-рассылкой (Confluent Kafka → Email Service) с повторными попытками (retry) и DLQ.

**Якорь:** bft-context-pack.md:283-289 — открытые вопросы по НФТ: «требования к доступности рассылки писем?».

**На Контраргумент 2 (гонки/дубликат): Уточнение — negative flow**

Добавляем Negative Flow: при повторном гостевом заказе на тот же email система проверяет существование заказов с этим email и is_guest=true. Если есть — создаём новый заказ, но при регистрации привязываем все. Это не требует schema change, только логики при регистрации. Дубликат профиля не создаётся, потому что профиль создаётся один раз, а заказы привязываются массивом.

**Якорь:** concept.md:154 — Edge-кейс «повторный заказ на ту же почту» — статус «Задокументировано (ФТ-3) Решено».

**На Контраргумент 3 (масштабирование 6-12 мес): Эволюционная архитектура**

Согласен, флаг `is_guest` усложняет querying при росте доли гостевых заказов. Но это не блокирует MVP. Когда доля достигнет 30-50%, будет очевидный trigger для миграции в отдельную сущность. Инвестиция в Концепт 2 не пропадёт: логика флоу, валидации, privacy-правила останутся. Добавляем архитектурное решение: «при достижении 10k гостевых заказов — миграция в GuestOrder».

**Якорь:** concept.md:38-39 — Концепт 1: «Scalable: архитектура рассчитана на рост».

**На Контраргумент 4 (ПДн/регуляторика): Explicit requirements**

Добавляем в требования:
- ФТ-4: Форма гостевого заказа содержит галочку «Я согласен на обработку персональных данных» (ссылка на ФЗ-152)
- БД хранит `consent_timestamp` для каждого гостевого заказа

Это не требует schema change (один boolean/timestamp), но закрывает риск регуляторики.

**Якорь:** regulatory.md:30-31 — PD-001, PD-002; problem.md:176 — вопрос юристу «требуется ли согласие? (Высокий)».

**На Контраргумент 5 (поддержка): Уточнение blast radius**

Концепт 2 не меняет UI поддержки — он остаётся как есть. Поддержка ищет заказы по email через существующий инструмент. Добавляем явное требование: «API поиска заказов по email должен возвращать и гостевые заказы». Это не требует изменений в форме, только в backend query.

**Якорь:** po-statement.md:17 — «почта обязательна — по ней ищется заказ в поддержке».

### Атака Адвоката Дьявола — What-if 6-12 месяцев

**What-if 1: Изменится модель оплаты — будет Apple Pay / Google Pay**

Концепт 2 предполагает форму с email/адресом/телефоном. Apple Pay не даёт email сразу — только после завершения транзакции. Как тогда связать платёж с гостевым заказом? Концепт 1 с отдельной сущностью GuestOrder и explicit lifecycle лучше справится с этим: оплата → создание GuestOrder → отправка письма. Концепт 2 придётся переделывать.

**Якорь:** bft-context-pack.md:244 — «Платёжный шлюз — что требуется для гостевого флоу? (Средний приоритет)».

**What-if 2: Юрист запретит хранение phone в гостевом флоу**

ФЗ-152 может потребовать: телефон хранить только после явного согласия (sms/opt-in). Концепт 2 использует phone как обязательное поле (УТ-3). Если юрист изменит требования, schema change неизбежен: удалить phone из NOT NULL constraints. Концепт 3 (demo) не страдает — он in-memory. Концепт 1 с отдельной таблицей легче адаптируется.

**Якорь:** po-statement.md:30 — УТ-3: «Обязательны почта, адрес доставки и телефон».

**What-if 3: Бизнес захочет аналитику по конверсии гостевых → зарегистрированные**

Через 6 месяцев бизнес спросит: какая доля гостевых заказов конвертируется в регистрацию? Концепт 2 не отслеживает этот funnel явно (нет события «гостевой заказ создан», «пользователь зарегистрировался», «заказ привязан»). Для аналитики придётся добавлять event-sourcing. Концепт 1 с явным lifecycle (GuestOrder → Order) предоставляет естественные точки для событий.

**Якорь:** concept.md:222-231 — открытые вопросы по концептам: что меняется при изменении требований.

## Раунд 3 — Вердикт

### Итоговая позиция Архитектора

Концепт 2 остаётся оптимальным выбором для текущего горизонта планирования (1-2 спринта). Все what-if сценарии относятся к 6-12 месяцам, когда бизнес-валидация гостевого флоу уже будет получена. Если MVP подтвердит ценность, инвестиция в Концепт 1 оправдана. Если нет — потрачено минимум усилий.

**Усиления, принятые в ходе дебатов:**
1. НФТ-1 на доставку письма ≤ 30 сек, SLA 99.5%
2. Negative Flow на повторный заказ с тем же email
3. ФТ-4: согласие на ПД (consent checkbox + consent_timestamp)
4. Архитектурное решение: миграция в GuestOrder при достижении 10k заказов

### Итоговая позиция Адвоката Дьявола

Концепт 2 работоспособен для MVP, но несёт техдолг: рассылка, привязка к профилю, регуляторика, масштабирование. Если бизнес подтвердит demand, переход в Концепт 1 неизбежен. Риск: «всё равно переделывать» — но это цена быстрого старта. Риск приемлем при условии explicit записи техдолга в backlog.

### Вердикт Модератора

**Статус:** Принят с модификациями

**Основание:**
1. Концепт 2 закрывает критический Gap 1 за 1 спринт — соответствует HowToDemo
2. Все контраргументы Адвоката Дьявола либо уточнены (НФТ, negative flows, consent), либо относятся к горизонту 6-12 месяцев
3. What-if сценарии реалистичны, но не блокируют MVP — бизнес-валидация приоритетнее

**Модификации к Концепту 2 (обязательны для /bft-draft):**
1. **НФТ-1:** SLA на доставку письма — ≤ 30 сек, 99.5% доступность
2. **ФТ-4:** Согласие на обработку ПД — checkbox на форме + `consent_timestamp` в БД
3. **Negative Flow:** Повторный заказ на тот же email → не создаёт дубль профиля; при регистрации привязываются все гостевые заказы
4. **SubIssue (явный):** Интеграция с продакшн-рассылкой (Confluent Kafka → Email Service) после MVP
5. **Архитектурное решение:** Триггер миграции в отдельную сущность GuestOrder — при достижении 10k гостевых заказов

**Концепт 1 (полноценный) — запасной**, если бизнес требует production-ready с первого релиза (не наш случай).

**Концепт 3 (демо) — отклонён**, не закрывает Gap 2 (поддержка не найдёт заказ), не production.

**Вердикт:** Принят с модификациями. Концепт 2 (Упрощённый гостевой флоу) — baseline для /bft-draft с 5 обязательными уточнениями.
