## 1. Rich Picture — Реконструкция проблемной ситуации

### 1.1. Акторы

| Актор | Роль | Зоны интересов |
|---|---|---|
| **Покупатель (гость)** | Лицо без учётной записи, желающее оформить заказ | Возможность купить без регистрации, простота флоу |
| **Покупатель (зарегистрированный)** | Владелец аккаунта | Сохранение существующего флоу, привязка гостевых заказов |
| **Frontend** | UI форма оформления | Валидация на клиенте, UX флоу гостевого заказа |
| **Order Service** | HTTP-сервис расчёта заказа | API контракт `/quote`, приём гостевых данных |
| **User Service** | Управление профилями | Профили пользователей, слияние гостевых заказов |
| **Email Service** | Отправка уведомлений | Письмо со статусом и ссылкой |
| **Поддержка** | Поиск заказов | Поиск заказа по почте |
| **PO (Product Owner)** | Заказчик требования | Снижение оттока на шаге оплаты |

### 1.2. Потоки

**Текущий поток (As-Is):**
```
Покупатель → Корзина → Шаг оплаты → Требование логина/регистрации →
  [отказ части покупателей] → Оформление заказа
```

**Желаемый поток (To-Be):**
```
Параллельные пути:
  A) Покупатель → Корзина → "Оформить без регистрации" →
     Ввод почты/адреса/телефона → Order Service → Email service → Письмо
  B) Покупатель → Корзина → "Войти" → [существующий флоу]

Привязка постфактум:
  Гостевой заказ → Регистрация/Вход по ссылке из письма →
  User Service → Заказ привязан к профилю
```

### 1.3. Конкурирующие worldviews

| Worldview | Позиция | Обоснование |
|---|---|---|
| **PO / Бизнес** | Внедрить гостевой заказ как можно скорее — часть покупателей уходит на шаге обязательной регистрации | po-statement.md:7-8, "часть покупателей уходит именно здесь" |
| **UX / Фронтенд** | Форма гостевого заказа должна быть рядом с входом, не заменять его | po-statement.md:16, "существующий флоу с регистрацией остаётся как есть, гостевой добавляется рядом" |
| **Безопасность / Юристы** | Нельзя раскрывать факт существования аккаунта по введённой почте (утечка приватности) | po-statement.md:36-37, "Никаких подсказок о существовании аккаунта на форме — это утечка факта регистрации" |
| **User Service** | Повторный гостевой заказ на ту же почту не должен создавать дубль профиля | po-statement.md:18, "повторный заказ на ту же почту не должен создавать дубль профиля" |
| **Аритектура контура** | Сервис должен оставаться без внешних зависимостей, логика разделяется | architecture.md:73, "Зависимостей у сервиса нет — это свойство, а не упущение" |
| **Legacy (существующий код)** | Текущий контракт `/quote` ({items}) не должен ломаться обратной совместимостью | domain-rules.md:3-21, DR-1..DR-6 |

### 1.4. Конфликты worldviews

| Конфликт | Стороны | Суть конфликта |
|---|---|---|
| **Утечка приватности vs UX валидации** | Безопасность ↔ UX | Форма НЕ должна подсказывать "почта занята", но UX привык к немедленной валидации |
| **Дубли профилей vs Повторные заказы** | User Service ↔ Бизнес | Гость может делать много заказов на одну почту до регистрации — как хранить без дублей? |
| **Обратная совместимость vs Новые поля** | Legacy ↔ Новая логика | `/quote` сейчас принимает только `{items}`. Добавление `guest` не должно ломать существующих клиентов |
| **Отправка письма vs Зависимости** | Order Service ↔ Архитектура | Email-сервис требуется задачей (po-statement.md:11), но архитектура запрещает зависимости (architecture.md:73) |

## 2. As-Is — Текущее поведение

### 2.1. Как работает сейчас

**API контракт `/quote`** (src/server.mjs:29-43):
- Вход: POST с телом `{"items": [{sku, price, qty}]}`
- Выход: `{goods, delivery, total}` или HTTP 400 с `{error}`
- Валидация: цены через Number.isFinite, количества — целые > 0
- Бизнес-правила: минимум 1000₽, доставка 300₽, бесплатная от 3000₽

**Флоу оформления заказа** (po-statement.md:7-8):
- Шаг оплаты требует логин/регистрацию
- Часть покупателей уходит на этом шаге

**Архитектурные границы** (architecture.md:69-74):
- Зависимостей у сервиса нет
- Арифметика в pricing.mjs, HTTP в server.mjs
- Email service в текущей архитектуре не задокументирован

## 3. Gap — Разрыв между As-Is и желаемым состоянием

### 3.1. Фундаментальный разрыв

Система **не поддерживает** оформление заказа без регистрации. API контракт `/quote` принимает только `{items}`, нет поля для гостевых данных. Отсутствует интеграция с email-сервисом для отправки письма со статусом.

### 3.2. Конкретные проблемы

| Проблема | Доказательство | Следствие |
|---|---|---|
| **Отсутствие поля для гостевых данных** | src/server.mjs:39 — `quote(body?.items)` — только items | Некуда передать email, адрес, телефон |
| **Нет валидации email/телефона** | src/pricing.mjs:28-34 — валидирует только price/qty | Некорректные данные пройдут в систему |
| **Нет интеграции с email** | architecture.md — Email service отсутствует | Письмо со статусом невозможно отправить |
| **Нет логики слияния в профиль** | User Service не задокументирован | Гостевой订单 не привяжется к профилю |
| **Риск утечки факта регистрации** | po-statement.md:36-37 — "Никаких подсказок о существовании аккаунта" | Требуется特殊ная обработка email, уже занятого |
| **Риск дублей профилей** | po-statement.md:18 — "повторный заказ не должен создавать дубль" | Нет стратегии хранения промежуточных гостевых данных |

### 3.3. Ограничения текущей реализации

- Зависимости отсутствуют как архитектурное свойство (architecture.md:73)
- Разделение арифметики и HTTP — жёсткое (AD-1: src/pricing.mjs:1-3)
- HTTP 400 для бизнес-ошибок (AD-3: src/server.mjs:34-36)
- Обратная совместимость API не документирована, но подразумевается существующими клиентами

## 7. Резюме диагноза

**Проблема:** Система не поддерживает оформление заказа без регистрации — API контракт `/quote` принимает только `{items}`, отсутствует поле для гостевых данных, нет интеграции с email-сервисом, не задокументирована логика привязки заказа к профилю.

**Конфликты worldviews:**
1. Утечка приватности (нельзя подсказывать "email занят") vs UX (ожидание немедленной валидации)
2. Требование email-сервиса vs архитектурное ограничение "зависимостей нет"
3. Дубли профилей при повторных гостевых заказах vs целостность данных
4. Обратная совместимость API vs новые поля

**Затронуто:** Order Service (прямо), Frontend (косвенно), Email Service (отсутствует), User Service (не задокументирован), Tests (требуются).

**Блокирующие `[УТОЧНИТЬ]`:** 4 критических вопроса (email провайдер, User Service схема, хранение гостей, самостоятельная регистрация).
