# Solution Concepts — Концепты решения

**Epic:** issue-43 — Гостевой заказ без регистрации
**Дата:** 2026-08-20
**Стадия:** Solution Designer (спектр решений, без выбора победителя)

---

## Метод CATWOE

CATWOE — анализ трансформации системы по шести измерениям:
- **C** Customer — кто выигрывает/теряет от изменения
- **A** Actor — кто реализует изменение
- **T** Transformation — вход → выход (суть трансформации)
- **W** Worldview — зачем / ценность / убеждение
- **O** Owner — кто согласует и владеет решением
- **E** Environment — ограничения среды (технические, организационные)

---

## Концепт 1 — «Чистовая архитектура» (event-based)

### Суть

Order Service публикует событие `OrderCreated` в message broker.独立的 Email Service подписывается на событие и отправляет письмо. Гостевые данные хранятся в отдельной таблице `guest_orders` с уникальным ключом `(email, order_id)`. Привязка к профилю происходит через отдельный эндпоинт `/merge-guest-order` при регистрации.

### CATWOE

| Измерение | Описание |
|---|---|
| **C** Customer | Покупатель получает возможность купить без регистрации; не теряет заказ при ошибке email-сервиса (создание заказа не зависит от отправки письма) |
| **A** Actor | Order Service: публикует событие. Email Service: подписывается, отправляет. Frontend: форма гостевого заказа |
| **T** Transformation | Вход: `{items, guest: {email, phone, address}}` → Выход: заказ создан + событие опубликовано (асинхронно → письмо) |
| **W** Worldview | Разделение ответственности: Order Service не должен знать о доставке email. Слабая связность через события |
| **O** Owner | Архитектор (принцип разделения), PO (функциональность) |
| **E** Environment | Ограничение: требуется message broker (Redis Streams, RabbitMQ, Kafka). Email Service уже существует или создаётся |

### Архитектурные границы

- Order Service НЕ зависит от Email Service (только публикует событие)
- Email Service НЕ зависит от Order Service (только читает событие)
- Хранение: таблица `guest_orders` отдельно от `users`
- Обратная совместимость: поле `guest` опционально

### Плюсы

1. **Закрывает Gap «Нет интеграции с email»** без нарушения архитектурного принципа «зависимостей нет» — связь через события, а не прямой вызов
2. **Устойчивость к сбоям email-сервиса:** заказ создаётся независимо от отправки письма; можно ретраить отправку из очереди
3. **Масштабируемость:** Email Service можно масштабировать независимо от Order Service

### Минусы / риски

1. **Требует message broker:** новой инфраструктурной компоненты, которой сегодня нет в демо-стенде
2. **Сложнее для MVP:** больше компонентов для запуска и отладки
3. **Eventual consistency:** статус «письмо отправлено» не известен моментально

### Влияние

| Компонент | Изменения |
|---|---|
| `src/server.mjs` | Парсинг поля `guest`; публикация события (новая зависимость: message broker client) |
| `src/pricing.mjs` | Валидация полей `guest.email`, `guest.phone`, `guest.address` |
| БД | Новая таблица `guest_orders` |
| Tests | Тесты сценария с `guest`, тесты публикации события |
| Frontend | Форма с полями email/телефон/адрес |

### Оценка усилий

**L** (крупная) — требует введения message broker, отдельного Email Service, схемы БД.

## Концепт 2 — «Компромисс» (inline email-клиент)

### Суть

Order Service отправляет email напрямую через lightweight-библиотеку (встроенную в код сервиса, без отдельного процесса). Гостевые данные передаются в `/quote` и сохраняются в ответе. Email-отправка синхронная, но с таймаутом — при превышении заказ всё равно создаётся, а отправка логируется как failed.

### CATWOE

| Измерение | Описание |
|---|---|
| **C** Customer | Покупатель получает письмо сразу (при успешной отправке). При сбое — заказ создан, письмо в очереди ретрая |
| **A** Actor | Order Service: парсит `guest`, валидирует, отправляет email (через встроенную библиотеку). Frontend: форма |
| **T** Transformation | Вход: `{items, guest: {email, phone, address}}` → Выход: `{goods, delivery, total, guestOrderId}` + email отправлен (или failed) |
| **W** Worldview | Практичность: не строить ради email отдельный сервис. «Зависимость» в виде библиотеки допустима |
| **O** Owner | PO (функциональность), Архитектор (компромисс по зависимостям) |
| **E** Environment | Ограничение: встроенная SMTP-библиотека (например, Node.js `nodemailer` или стандартная библиотека). Требует SMTP-хоста |

### Архитектурные границы

- Order Service содержит код отправки email (функция `sendGuestOrderEmail`)
- Библиотека email встраивается в сборку, не как внешний сервис
- Поле `guest` опционально → обратная совместимость
- При ошибке email заказ не откатывается

### Плюсы

1. **Закрывает Gap «Нет интеграции с email»** без отдельного сервиса — быстрее к MVP
2. **Проще для демо-стенда:** один сервис, меньше инфраструктуры
3. **Обратная совместимость:** существующие клиенты `/quote` продолжают работать (поле `guest` опционально)

### Минусы / риски

1. **Нарушает принцип «зависимостей нет»** — даже встроенная библиотека это зависимость (хотя и статическая)
2. **Order Service становится ответственным за email:** сбой SMTP влияет на perceived latency (даже с таймаутом)
3. **Масштабирование:** отправка email в том же процессе consumes ресурсы Order Service

### Влияние

| Компонент | Изменения |
|---|---|
| `src/server.mjs` | Парсинг поля `guest`; вызов `sendGuestOrderEmail(guest, orderId)` |
| `src/pricing.mjs` | Валидация `guest.email` (RFC-5322 basic), `guest.phone` (basic format), `guest.address` |
| БД (опционально) | Таблица `guest_orders` для хранения привязки email → order_id |
| Tests | Тесты сценария с `guest`, моки email-отправки |
| Frontend | Форма с полями email/телефон/адрес |

### Оценка усилий

**M** (средняя) — требуется встроить email-библиотеку, настроить SMTP, добавить валидацию.

## Концепт 3 — «Быстрый MVP» (deferred email)

### Суть

Order Service принимает и валидирует поле `guest`, но не отправляет email. Вместо этого в ответе возвращается `guestToken` — хеш, по которому фронтенд может запросить отправку письма отдельным запросом (или письмо отправляется фоновой задачей, которую запускает отдельный скрипт). Для MVP это позволяетRELEASE функциональность «оформить заказ» без блокировки на email-интеграцию.

### CATWOE

| Измерение | Описание |
|---|---|
| **C** Customer | Покупатель оформляет заказ, получает token. Письмо придёт позже (cron/фон) или по запросу |
| **A** Actor | Order Service: парсит `guest`, валидирует, сохраняет. Background worker: отправляет письма по очереди |
| **T** Transformation | Вход: `{items, guest: {email}}` → Выход: `{goods, delivery, total, guestToken}` (email deferred) |
| **W** Worldview | MVP-first: разблокировать оформление заказа, отложить надёжную отправку письма |
| **O** Owner | PO (быстрый релиз), Архитектор (временное решение) |
| **E** Environment | Ограничение: требуется хранилище для `guest_orders` и фоновый процесс. Для демо — можно в памяти |

### Архитектурные границы

- Order Service НЕ отправляет email (только сохраняет запрос)
- Background worker (отдельный процесс или cron) читает очередь и отправляет
- Поле `guest` только `email` (телефон/адрес добавляются позже)
- Обратная совместимость: поле `guest` опционально

### Плюсы

1. **Минимальные изменения в Order Service:** только парсинг и базовая валидация email
2. **Не блокирует MVP:** заказы оформляются, письмо можно доставлять асинхронно
3. **Обратная совместимость:** поле `guest` опционально

### Минусы / риски

1. **Технический долг:** deferred email — временное решение, требует доработки
2. **UX риск:** покупатель может не получить письмо быстро (зависит от фонового процесса)
3. **Два флоу:** оформление заказа (сейчас) и полноценное письмо (потом) — разрыв в пользовательском опыте

### Влияние

| Компонент | Изменения |
|---|---|
| `src/server.mjs` | Парсинг поля `guest` (только email). Сохранение в хранилище (в памяти для демо) |
| `src/pricing.mjs` | Базовая валидация email (contains `@`, не пустой) |
| Хранилище | In-memory map `email → [{orderId, timestamp}]` или файл |
| Background worker | Новый процесс/скрипт для отправки писем |
| Tests | Тесты сценария с `guest` |

### Оценка усилий

**S** (малая) — минимальные изменения в сервисе, но требует отдельный фоновый процесс.

## Открытые вопросы и worldviews

### Какие вопросы закрывает каждый концепт

| Вопрос | Концепт 1 | Концепт 2 | Концепт 3 |
|---|---|---|---|
| **Какой провайдер email, как интегрируется?** | Отдельный Email Service → любые провайдеры | Встроенная библиотека → SMTP | Deferred → позже |
| **Существует ли User Service, схема профилей?** | Не требуется для MVP (таблица `guest_orders`) | Не требуется для MVP | Не требуется |
| **Как хранить промежуточные данные гостя?** | Отдельная таблица `guest_orders` | Отдельная таблица или in-memory | In-memory для демо |
| **Что при самостоятельной регистрации (не по ссылке)?** | Эндпоинт `/merge-guest-order` | Требуется логика слияния | Deferred |

### Конфликты worldviews

| Конфликт | Концепт 1 | Концепт 2 | Концепт 3 |
|---|---|---|---|
| **Утечка приватности vs UX** | ✅ Email проверяется в Email Service, утечки нет | ⚠️ Валидация в Order Service — риск подсказки «email занят» | ✅ Email только сохраняется |
| **Email service vs Зависимости** | ✅ Слабая связность через события | ⚠️ Библиотека — нарушение принципа | ✅ Order Service не отправляет |
| **Дубли профилей vs UX** | ✅ Ключ (email, order_id) → дублей нет | ⚠️ Требуется стратегия | ⚠️ Ignored |

## Резюме

Представлено три концепта:

1. **Концепт 1 — «Чистовая архитектура»** (event-based): Order Service публикует событие, отдельный Email Service отправляет письмо. Требует message broker, но соблюдается принцип разделения ответственности.

2. **Концепт 2 — «Компромисс»** (inline email): Order Service отправляет email через встроенную библиотеку. Быстрее к MVP, но нарушает принцип «зависимостей нет».

3. **Концепт 3 — «Быстрый MVP»** (deferred email): Order Service принимает гостевой email, но не отправляет письмо — фоновый процесс отправляет позже. Минимальные усилия, но высокий техдолг.
