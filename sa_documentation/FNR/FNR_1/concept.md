# FNR-1: Концепты решений

## Задача

Добавить плату за упаковку по числу посылок в эндпоинт `POST /quote`.

**Требования:**
- 1 посылка вмещает до 5 единиц товара
- 50 ₽ за каждую посылку
- Упаковка платится всегда (даже при бесплатной доставке)
- Ответ должен включать поле `packages`
- `delivery` = базовая доставка + упаковка

## Анализ текущего состояния

**Зона воздействия:** `src/pricing.mjs`

Текущая структура:
- `subtotal(items)` — сумма товаров
- `deliveryFee(amount)` — фиксированная 300 ₽ или 0
- `quote(items)` — агрегирует результаты

**Ограничения:**
- Без внешних зависимостей
- Чистые функции в `pricing.mjs`
- Обратная совместимость поля `goods`
- Валидация пустого заказа сохраняется

## Концепты решений

### 1. Правильное: Минимальное расширение quote()

**Суть:** Добавить расчёт посылок и упаковки прямо в функцию `quote()`, новая константа `PACKAGING_FEE`.

**Изменения:**
- `src/pricing.mjs:8` — добавить `export const PACKAGING_FEE = 50;`
- `src/pricing.mjs:10` — добавить `export const PACKAGES_CAPACITY = 5;`
- `src/pricing.mjs:48-52` — расширить `quote()`

```javascript
export function quote(items) {
  const goods = subtotal(items);
  const units = items.reduce((sum, item) => sum + item.qty, 0);
  const packages = Math.ceil(units / PACKAGES_CAPACITY);
  const packaging = packages * PACKAGING_FEE;
  const delivery = deliveryFee(goods) + packaging;
  return { goods, packages, delivery, total: goods + delivery };
}
```

**Плюсы:**
- Минимальные изменения (2 константы + 5 строк логики)
- Следует существующей структуре файла
- Константы экспортируются для тестов
- Чистая функция, тестируется изолированно

**Минусы:**
- `quote()` становится немного менее декларативной
- Расчёт единиц смешан с агрегацией

**Усилия:** 15 минут
**Риски:** Низкие — локальное изменение, не затрагивает валидацию

---

### 2. Прагматичное: Выделенная функция countPackages()

**Суть:** Вынести расчёт посылок в отдельную чистую функцию, аналогично `deliveryFee()`.

**Изменения:**
- `src/pricing.mjs:8-10` — константы
- `src/pricing.mjs:46` — новая функция
- `src/pricing.mjs:48-52` — обновление `quote()`

```javascript
export const PACKAGING_FEE = 50;
export const PACKAGES_CAPACITY = 5;

/**
 * Количество посылок для набора позиций.
 * @param {Item[]} items
 */
export function countPackages(items) {
  const units = items.reduce((sum, item) => sum + item.qty, 0);
  return Math.ceil(units / PACKAGES_CAPACITY);
}

/**
 * Стоимость упаковки для числа посылок.
 * @param {number} packages
 */
export function packagingFee(packages) {
  return packages * PACKAGING_FEE;
}

export function quote(items) {
  const goods = subtotal(items);
  const packages = countPackages(items);
  const delivery = deliveryFee(goods) + packagingFee(packages);
  return { goods, packages, delivery, total: goods + delivery };
}
```

**Плюсы:**
- Чёткое разделение ответственности
- Функции тестируются независимо
- Легко изменить логику расчёта посылок в будущем
- Следует паттерну файла (мелкие чистые функции)

**Минусы:**
- Больше строк кода
- Две функции вместо одной (слегка усложняет API модуля)

**Усилия:** 20 минут
**Риски:** Низкие — функции изолированы

---

### 3. Быстрый костыль: Inline в quote()

**Суть:** Магические числа прямо в `quote()`, без констант и вспомогательных функций.

**Изменения:**
- Только `src/pricing.mjs:48-52`

```javascript
export function quote(items) {
  const goods = subtotal(items);
  const units = items.reduce((sum, item) => sum + item.qty, 0);
  const packages = Math.ceil(units / 5);
  const delivery = deliveryFee(goods) + packages * 50;
  return { goods, packages, delivery, total: goods + delivery };
}
```

**Плюсы:**
- Самый быстрый вариант
- Минимум кода

**Минусы:**
- Магические числа (50, 5) без именования
- Невозможность переиспользования логики посылок
- Сложно тестировать изолированно
- Нарушает стиль файла (все остальные значения вынесены в константы)

**Усилия:** 10 минут
**Риски:** Средние — технический долг,_Style mismatch с остальным файлом

---

### 4. Креативный хак: Через объект конфигурации

**Суть:** Ввести объект `PACKAGING_CONFIG` и работать с ним, чтобы легко менять параметры.

**Изменения:**
- `src/pricing.mjs:8-12` — конфиг
- `src/pricing.mjs:46-52` — функции

```javascript
export const PACKAGING_CONFIG = {
  feePerPackage: 50,
  capacity: 5,
};

export function countPackages(items) {
  const units = items.reduce((sum, item) => sum + item.qty, 0);
  return Math.ceil(units / PACKAGING_CONFIG.capacity);
}

export function packagingFee(packages) {
  return packages * PACKAGING_CONFIG.feePerPackage;
}

export function quote(items) {
  const goods = subtotal(items);
  const packages = countPackages(items);
  const delivery = deliveryFee(goods) + packagingFee(packages);
  return { goods, packages, delivery, total: goods + delivery };
}
```

**Плюсы:**
- Легко менять параметры без поиска по коду
- Расширяемо (можно добавить tiered pricing, скидки)

**Минусы:**
- Избыточно для текущих требований
- Не соответствует стилю файла (константы плоские)
- Сложнее для понимания новичком

**Усилия:** 25 минут
**Риски:** Низкие — хорошая архитектура, но overengineering

---

### 5. «Не трогай»: Конфиг через переменные окружения

**Суть:** Вынести параметры в `process.env`, чтобы менять без деплоя.

**Изменения:**
- `src/pricing.mjs` — чтение `process.env.PACKAGING_FEE` и `process.env.PACKAGES_CAPACITY`
- `src/server.mjs` — возможно, документация env-переменных
- Документация — описание новых переменных

**Плюсы:**
- Гибкость без деплоя
- Можно A/B тестировать цены упаковки

**Минусы:**
- Противоречит принципу «без внешних зависимостей» (env = конфиг снаружи)
- Сложнее тестировать (нужно мокать process.env)
- Невозможно проверить значение в коде (сложно для статанализа)

**Усилия:** 30 минут
**Риски:** Средние — усложнение тестирования, отступление от архитектуры

# Архитектурные дебаты

## Раунд 1: Защита

### Архитектор (защищает Концепт 2)

**Тезис:** Концепт 2 (выделенная функция `countPackages()`) — оптимальный баланс между простотой и качеством.

**Аргументы:**

1. **Следует паттерну файла** — В `src/pricing.mjs` уже есть паттерн: мелкие чистые функции с понятными именами (`subtotal`, `deliveryFee`). Добавление `countPackages()` и `packagingFee()` продолжает эту традицию. Смотри строки 21-42: каждая функция делает одну вещь и тестируется независимо.

2. **Тестируемость из коробки** — Новые функции можно проверить в изоляции:
   ```javascript
   assert(countPackages([{qty: 3}]) === 1);
   assert(countPackages([{qty: 6}]) === 2);
   assert(packagingFee(2) === 100);
   ```
   Это важнее, чем кажется: расчёт посылок — бизнес-логика, которую будут менять.

3. **Расширяемость без переписывания** — Если завтра появится правило "посылки с разными товарами считаются отдельно" или "скидка на 5+ посылок", мы изменим только `countPackages()`, а не трогаем `quote()`.

4. **Без зависимостей** — Все изменения локальны в `pricing.mjs`, никаких `process.env` или внешних конфигов.

### Адвокат Дьявола (атакует Концепт 2)

**Контраргумент 1: YAGNI для настоящей проблемы**

Задача — добавить плату за упаковку по числу посылок. Это 15 минут работы. Концепт 2 требует 20 минут и две новые функции. Но на самом деле базовая логика не изменится: это всегда `Math.ceil(units / 5)`. Почему мы создаём абстракцию для того, что не будет меняться?

**Контраргумент 2: Ложная расширяемость**

"Расширяемость" звучит хорошо, но давайте честно: правка расчёта посылок — редкое событие. Если завтра будет сложная логика, мы всё равно перепишем. А пока `countPackages()` — это обёртка вокруг одной строчки `Math.ceil(units / 5)`. Это не инвестиция, это бюрократия.

**Контраргумент 3: Концепт 1 настолько же тестируем**

Тесты покрывают то же самое:
```javascript
// Для Концепта 1 — проверяем quote() целиком
assert(quote([{qty: 6}]).packages === 2);
```
Разница в тестируемости между концептами 1 и 2 — иллюзорная. Мы тестируем одно и то же, только через разные функции.

**Контраргумент 4: Концепт 2 усложняет API модуля**

Сейчас `pricing.mjs` экспортирует три функции. Концепт 2 добавляет ещё две (`countPackages`, `packagingFee`). Но нужны ли они кому-то снаружи? `quote()` — публичный контракт, а остальное — детали реализации. Почему мы публикуем их?

## Раунд 2: Пересмотр

### Архитектор (учитывает критику)

**Согласие:** Контраргумент 3 верен — тестируемость не усилится. Мы будем тестировать одно и то же.

**Ответ на Контраргумент 1:** YAGNI применим, когда мы уверены, что логика не изменится. Но бизнес-логика доставки — это область частых изменений: бесплатные пороги, категории товаров, regional fees. Создать структуру сейчас — это не бюрократия, это подготовка к inevitability.

**Ответ на Контраргумент 2:** Расширяемость не ложная. Посмотри на `src/pricing.mjs:40-42` — `deliveryFee()` тоже простая тернарная операция. Но она вынесена в отдельную функцию, и это позволяет легко изменить логику (например, tiered delivery). Мы следуем тому же паттерну.

**Усиление позиции:** Концепт 2 — это инвестиция в согласованность. Файл уже имеет паттерн "мелкие чистые функции". Концепт 2 продолжает его. Концепт 1 нарушает: делает `quote()` более процедурной.

### Адвокат Дьявола (проверяет сценарии)

**Сценарий А: Через полгода изменится формула посылок**

Допустим, теперь 1 посылка вмещает 3 единицы, а не 5. Концепт 2 меняет одну константу. Концепт 1 — тоже одну константу (даже меньше строк). Разницы нет.

**Сценарий Б: Появится логика "посылки с разными SKU не объединяются"**

Концепт 2 придётся переписывать `countPackages()` целиком — текущая реализация (`reduce((sum, item) => sum + item.qty, 0)`) не учитывает SKU. Концепт 1 тоже перепишет `quote()`. Разницы нет.

**Сценарий В: Нужно добавить A/B тестирование цены упаковки**

Концепт 2 не поможет — нужны `process.env` (Концепт 5). Инвестиция в функцию не окупилась.

**Критический вопрос:** А что если существующий паттерн файла — это legacy? `deliveryFee()` вынесена, но нужна ли она? Может, `quote()` был бы понятнее без этой микроскопической функции?

## Раунд 3: Вердикт

### Архитектор (итоговая позиция)

**Признание:** Адвокат прав в главном: для текущей задачи все концепты (1, 2, 4) решают её одинаково хорошо. Разница — в Philosophy, а не в функциональности.

**Окончательный аргумент:** Вопрос в том, какое свойство системы мы ценим больше:
- **Минимальность кода** → Концепт 1
- **Структурную консистентность** → Концепт 2

`src/pricing.mjs` — файл с чётким стилем: константы сверху, мелкие функции в середине, агрегация в `quote()`. Концепт 2 продолжает этот стиль. Концепт 1 делает `quote()` более процедурной, что нарушает декларативность.

### Адвокат Дьявола (итоговая позиция)

**Признание:** Консистентность имеет значение. Если файл уже имеет паттерн, его следует продолжать. Мой главный аргумент — "Концепт 2 не даёт преимуществ" — был слабее, чем "Концепт 2 нарушает nothing".

**Остаточная критика:** Но я настаиваю — Концепт 2 не "прагматичен". Он "структурно консистентен", но за цену 20 минут вместо 15. Это надстройка ради Philosophy, а не ради пользы.

### Вердикт

**Решение:** Принять Концепт 2 с уточнением описания.

**Обоснование:**
1. Архитектурная консистентность важнее радиуса "мелкие чистые функции", который уже устоялся в файле.
2. Инвестиция в структуру оправдана: файл `pricing.mjs` — сердце бизнес-логики, и его читабельность критична.
3. Адвокат не нашёл сценария, где Концепт 2 проигрывает Концепту 1 функционально. Разница только в philosophy.

**Модификация концепта:**
- Убрать qualification "Прагматичное" — это "Консистентное с существующей структурой"
- Уточнить, что экспорт `countPackages` и `packagingFee` — это intention для тестируемости, даже если они формально private

**Забракованные концепты:**
- **Концепт 3:** Магические числа — anti-pattern
- **Концепт 4:** Overengineering для текущей задачи
- **Концепт 5:** Нарушает принцип "без внешних зависимостей"

**Запасной вариант:** Концепт 1, если команда предпочитает minimalism над consistency.
