# FNR-1: Концепты решений

## Задача

Промо-код в расчёте заказа: эндпоинт `POST /quote` не поддерживает промо-коды, что приводит к расхождениям между суммой в чате и фактической оплатой.

**Зона воздействия:** `src/pricing.mjs`, `src/server.mjs`, `tests/pricing.test.mjs`

**Ключевая неопределённость:** Где хранить валидные промо-коды?

---

## Концепт 1: Прагматичное решение (рекомендуется для MVP)

**Суть:** Хранить промо-коды локальным объектом в `src/pricing.mjs`.

**Описание:**
Простая константа `PROMO_CODES` в файле расчёта с отображением кода на процент скидки. Функция `quote` расширяется опциональным параметром `promoCode`, который валидируется и применяется к расчёту.

**Изменения в файлах:**

- `src/pricing.mjs`:
  ```javascript
  export const PROMO_CODES = {
    'WELCOME10': 10,
    'SUMMER20': 20,
    'FALL15': 15,
  };

  export function discountAmount(goods, promoCode) {
    if (!promoCode) return 0;
    const percent = PROMO_CODES[promoCode];
    if (percent === undefined) {
      throw new Error('неизвестный промо-код');
    }
    return goods * percent / 100;
  }

  export function quote(items, promoCode = null) {
    const goods = subtotal(items);
    const discount = discountAmount(goods, promoCode);
    const delivery = deliveryFee(goods); // Порог считается ДО скидки
    return { goods, discount, delivery, total: goods - discount + delivery };
  }
  ```

- `src/server.mjs`:
  ```javascript
  return send(res, 200, quote(body?.items, body?.promo));
  ```

**Плюсы:**
- ✓ Минимальные изменения, только в существующих файлах
- ✓ Чистые функции, соответствует архитектуре
- ✓ Легко тестировать
- ✓ Без новых зависимостей
- ✓ Обратная совместимость (promo опционально)

**Минусы:**
- ✗ Добавление нового кода требует деплоя
- ✗ Нет истории использования кодов
- ✗ Нет ограничений по использованию (один раз на клиента и т.п.)

**Усилия:** 2-4 часа

**Риски:** Низкие — изменение локализовано в чистых функциях

## Концепт 2: Правильное решение (будущее-ориентированное)

**Суть:** Вынести хранение промо-кодов во внешнюю конфигурацию или сервис.

**Описание:**
Промо-коды хранятся отдельно от кода расчёта — либо в JSON-файле, либо в ENV-переменных, либо во внешнем HTTP-сервисе. Это позволяет менять коды без пересборки приложения и готовит почву для полноценной системы скидок.

**Варианты реализации:**

### 2a. JSON-конфиг (промежуточный шаг)
```
config/promo-codes.json:
{
  "WELCOME10": {"percent": 10, "active": true},
  "SUMMER20": {"percent": 20, "active": true}
}
```

**Изменения:**
- Новый файл `config/promo-codes.json`
- `src/pricing.mjs` читает конфиг при старте

### 2b. HTTP-сервис (полноценное решение)
```
GET /promo/{code} → {"percent": 10, "active": true}
```

**Изменения:**
- `src/pricing.mjs` добавляет асинхронную `promoService.lookup(code)`
- `src/server.mjs` становится асинхронным в обработке /quote

**Плюсы:**
- ✓ Коды можно менять без деплоя
- ✓ Готовность к интеграциям (CMS, CRM)
- ✓ Можно добавить метаданные (срок действия, лимиты)
- ✓ Разделение ответственности

**Минусы:**
- ✗ 2a: всё ещё требует рестарта при изменении JSON
- ✗ 2b: вводит зависимость от внешнего сервиса (SLO, таймауты)
- ✗ 2b: асинхронная сложность в чистых функциях
- ✗ Больше кода для поддержки

**Усилия:** 2a: 4-6 часов; 2b: 1-2 дня

**Риски:** Средние — усложнение архитектуры ради функции, которая пока нужна в минимальном объёме

## Концепт 3: Быстрый костыль (минимальное изменение)

**Суть:** Жёстко прописать только код `WELCOME10` без структуры под расширение.

**Описание:**
Вместо объекта кодов — простая проверка `if (promo === 'WELCOME10')`. Максимально быстро, но не масштабируется.

**Изменения в `src/pricing.mjs`:**

```javascript
export function quote(items, promo = null) {
  const goods = subtotal(items);
  const discount = promo === 'WELCOME10' ? goods * 0.10 : 0;
  if (promo && discount === 0) {
    throw new Error('неизвестный промо-код');
  }
  const delivery = deliveryFee(goods);
  return { goods, discount, delivery, total: goods - discount + delivery };
}
```

**Плюсы:**
- ✓ Минимально возможное изменение
- ✓ Работает для HowToDemo

**Минусы:**
- ✗ Добавление второго кода требует переписывания логики
- ✗ Магическая строка 'WELCOME10' разбросана по коду
- ✗ Нет гибкости (процент захардкожен)

**Усилия:** 30-60 минут

**Риски:** Средние — технический долг, который быстро превратится в проблему при запросе второго кода

## Концепт 4: Креативный хак (самодокументирующиеся коды)

**Суть:** Извлекать процент скидки прямо из названия промо-кода.

**Описание:**
Коды вида `WELCOME10`, `SUMMER20`, `FALL5` парсятся регулярным выражением, и процент берётся из названия. Неизвестные коды — те, что не заканчиваются на число или не входят в белый список префиксов.

**Изменения в `src/pricing.mjs`:**

```javascript
const PROMO_PREFIXES = ['WELCOME', 'SUMMER', 'FALL', 'BLACKFRIDAY'];

function parsePromoCode(code) {
  const match = code.match(/^([A-Z]+)(\d+)$/);
  if (!match) return null;
  const [, prefix, percentStr] = match;
  if (!PROMO_PREFIXES.includes(prefix)) return null;
  return parseInt(percentStr, 10);
}

export function quote(items, promo = null) {
  const goods = subtotal(items);
  let discount = 0;
  if (promo) {
    const percent = parsePromoCode(promo);
    if (percent === null) throw new Error('неизвестный промо-код');
    discount = goods * percent / 100;
  }
  const delivery = deliveryFee(goods);
  return { goods, discount, delivery, total: goods - discount + delivery };
}
```

**Плюсы:**
- ✓ Новые коды без деплоя (если префикс уже в списке)
- ✓ Процент виден прямо в названии (WELCOME20 = 20%)
- ✓ Компактный код

**Минусы:**
- ✗ Ограниченная гибкость (только целые проценты)
- ✗ Нельзя сделать коды вроде `FRIENDS` без цифры
- ✗ Нет индивидуальных параметров (срок действия, лимиты)

**Усилия:** 2-3 часа

**Риски:** Средние — решение работает, пока все коды укладываются в схему именования

#### Адвокат Дьявола:

**Атака на Концепт 1:**

**Критика 1: Масштабируемость**

> *"Добавление нового кода требует деплоя"*

Это реальный риск. Если маркетинг захочет запустить промо-акцию "завтра", придётся:
1. Добавить код в `PROMO_CODES`
2. Запустить CI/CD
3. Дождаться деплоя

**Критика 2: Технический долг**

Концепт 1 — это "промежуточное" решение, которое придётся переписывать. Почему сразу не делать Концепт 2a?

Концепт 2a (JSON-конфиг) тоже требует рестарта при изменении JSON. Разница в усилиях (2-4 часа против 4-6 часов) не даёт преимущества.

**Критика 3: Нет истории использования**

Концепт 1 не даёт ответа на вопросы:
- Сколько раз использовали код `WELCOME10`?
- Есть ли злоупотребления?

Это требует БД или внешнего сервиса — то есть Концепт 2b с усилиями 1-2 дня.

#### Адвокат Дьявола:

**Проверка крайних случаев:**

**Вопрос 1: Что если через месяц понадобится второй код?**

Концепт 1 позволяет добавить строку в объект. Это не проблема.

Но что если понадобится **динамическая скидка**? Сценарий: код `FRIENDS` даёт 10% для первого клиента и 15% для второго. Концепт 1 не поддерживает это.

**Вопрос 2: Что если промо-коды истекают?**

Сценарий: `WELCOME10` работает только до 1 сентября.

Концепт 1 потребует дату в конфиге, но дата захардкожена. Когда наступит 1 сентября, снова нужен деплой.

**Вопрос 3: Что если API для промо-кодов уже существует?**

Если в боевой системе уже есть сервис `/promo/{code}`, не дублировать ли логику?

### Раунд 3: Вердикт

#### Архитектор (итоговая позиция):

**Мой вердикт:** Концепт 1 принимается **с модификациями**.

**Модификации по критике Адвоката:**

1. **Дата истечения кодов:** Добавить поле `activeUntil` в объект `PROMO_CODES`
2. **Валидация при запуске:** Проверять коды при старте сервера
3. **Документирование пути миграции:** Явно указать в комментариях, как перейти к Концепту 2b

**Усиленная реализация:**
```javascript
export const PROMO_CODES = {
  'WELCOME10': { percent: 10, activeUntil: null },
  'SUMMER20': { percent: 20, activeUntil: '2025-09-01' },
};

function validatePromoCode(code, now = new Date()) {
  const config = PROMO_CODES[code];
  if (!config) return null;
  if (config.activeUntil && new Date(config.activeUntil) < now) return null;
  return config.percent;
}
```

Это решает критику про истекающие коды без деплоя — проверка идёт в рантайме.

Если через 2 месяца запросят внешнее хранение — будет evident, что нужен Концепт 2b, и рефакторинг будет простым.
