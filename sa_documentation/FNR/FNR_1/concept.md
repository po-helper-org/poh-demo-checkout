## 1. Постановка: корень, зона, ограничения

**Корень** (task.md, раздел 4): версия хранится как метаданные пакета
(`package.json:3`, `"version": "0.1.0"`) и не связана ни с одной строкой
исполняемого кода; у ветки `/healthz` (`src/server.mjs:107-115`) нет доступа к
этому значению в рантайме, а альтернативного источника идентификации сборки
репозиторий не создаёт.

**Что требуется:** тело ответа `/healthz` пополняется версией сервиса, значение
берётся из `package.json` (ФТ-1, ФТ-2). Проверка готовности — HowToDemo из
issue: запрос → поле в JSON-теле.

**Зона воздействия** (task.md, раздел 6) — четыре категории артефактов сразу:

| Категория | Файл | Что фиксирует |
|---|---|---|
| Код | `src/server.mjs:107-115` | литерал тела `{status, uptime_sec}` — единственное место состава ответа |
| Тесты | `tests/healthz.test.mjs:15-20`, `tests/server.test.mjs:154-161,184-189` | контракт **по полям**; ассерта на версию нет нигде |
| Документация | `README.md:34` | пример тела `{"status":"ok","uptime_sec":123}` |
| Delivery-контракт | `.delivery/checks.json:15-18` | `expect_json: {"status":"ok"}` и текстовое описание состава ответа |

**Ограничения** (task.md, разделы 6.6–7):

- Node.js ≥ 22 (`package.json:11-12`), ES-модули (`package.json:5`), образ
  `node:22-slim` (`.delivery/checks.json:7`).
- Зависимостей у сервиса нет; каждая новая требует обоснования рядом с кодом
  (`CLAUDE.md`, «Границы кода»).
- `src/server.mjs` — «тонкая обёртка»: только разбор запроса и коды ответов;
  арифметика — в `src/pricing.mjs` чистыми функциями.
- Новая логика — новый тест (`CLAUDE.md`, «Проверки»).
- Файл-цель — хотспот: health 5.45, hotspot 0.67, `test_gap: true`, со-изменения
  с `tests/server.test.mjs` весом 6.88 (`task.md:150-153`).

## 2. Пространство для манёвра (что уже есть и переиспользуется)

### 2.1 Готовые механизмы, которые можно взять без новых зависимостей

| Механизм | Где | Как помогает |
|---|---|---|
| `readFileSync` уже импортирован | `src/server.mjs:5` | чтение `package.json` не требует нового импорта |

| `send(res, code, body, extraHeaders)` | `src/server.mjs:29-37` | сериализация общая для всех JSON-ответов; менять её не нужно, но `extraHeaders` — готовый канал для заголовка версии |
| Прецедент вынесения состояния в модуль | `src/metrics.mjs` (замыкание `counters`) | показывает, что модуль-сосед с экспортом значения — нормальный ход в этом репо |

| Импорт-атрибуты JSON-модулей | язык, Node ≥ 22 (`package.json:11-12`) | `import pkg from '../package.json' with { type: 'json' }` — чтение манифеста силами самого рантайма, без `node:fs` и без ручного `JSON.parse` |
| Тесты фиксируют тело **по полям** | `tests/healthz.test.mjs:15-20`, `tests/server.test.mjs:154-161` | добавление поля существующие проверки не ломает; `deepEqual` на теле `/healthz` в репо нет (единственный `deepEqual` тела — `/stats`, `tests/server.test.mjs:86`) |

### 2.2 Что жёстко связано и меняется неохотно

- `src/server.mjs` ↔ `tests/server.test.mjs` — пара со-изменений (6.88); правка
  ветки `/healthz` почти всегда тянет тестовый файл за собой.
- `.delivery/checks.json` — исполняется снаружи репозитория Delivery-Agent'ом;
  репо отвечает за корректность описания («агент не имеет права додумывать»,
  `.delivery/checks.json:2`).
- `README.md:34` — единственное задокументированное тело ответа.

### 2.3 Допущения (не доказаны из репо, приняты разумными)

1. **Имя поля — `version`** (открытый вопрос task.md 9.1). Проверено по репо:
   ключа `version` нет ни в коде, ни в тестах, ни в `expect_json` (grep по
   `src/`, `static/`, `tests/`, `.delivery/` — пусто). Все концепты ниже
   используют `version`; окончательное имя — за дебатами.
2. **Семантика `expect_json` в delivery — подмножество, а не точное равенство**
   (открытый вопрос 9.2), и это выводится из репо: сегодня тело отвечает
   `{status, uptime_sec}` (`src/server.mjs:111-114`), тогда как `expect_json`
   фиксирует только `{"status": "ok"}` (`.delivery/checks.json:15-17`). При
   точном равенстве проверка была бы красной уже сейчас — а сервис числится
   работающим. Вывод: расширение тела delivery-проверку не ломает. Подтверждение
   у владельца Delivery-Agent всё равно нужно — но это подтверждение, а не
   риск-вопрос.
3. HowToDemo проверяет **наличие** поля, а не его различительную силу (открытый
   вопрос 9.3 — значение `0.1.0` не менялось в видимой истории). Ни один
   концепт этой границы не пересекает, но и БТ-1 по смыслу ни один не закрывает,
   если версию не поднимать от релиза к релизу.

| 2 | `tests/server.test.mjs:154-161` | тот же ассерт в одноимённом кейсе (файл — пара со-изменений сервера, вес 6.88) |

единственный `fetch`, к `/quote`) — правок в `static/` нет ни в одном концепте.

## 4. Концепты (по убыванию архитектурной чистоты)

### К1. Правильное: сборка тела `/healthz` — чистый модуль, версия — импорт-атрибут JSON-модуля

**Категория:** Правильное.

**Суть.** Состав ответа здоровья перестаёт быть литералом внутри `app` и
выносится в чистый модуль `src/health.mjs`, который экспортирует версию из
`package.json` и функцию сборки тела. Версия попадает в код силами самого
рантайма — импорт-атрибутом JSON-модуля, то есть без `node:fs`, без ручного
`JSON.parse` и без новых зависимостей. Сервер возвращается к своей конвенции
(«только разбор запроса и коды ответов»), а новая логика получает тест без сети
— по образцу `src/pricing.mjs` и `tests/pricing.test.mjs`.

**Что менять.**

Новый файл `src/health.mjs`:

```js
// Состав ответа /healthz. Вынесен из server.mjs по той же причине, что и
// pricing.mjs: тело — контракт, и проверяется тестом построчно, без сети.
// Версия — импорт-атрибут JSON-модуля (Node ≥ 22, package.json engines):
// значение читает сам рантайм, и прочесть его неправильно нельзя.
import pkg from '../package.json' with { type: 'json' };

export const VERSION = pkg.version;

/**
 * Тело ответа /healthz.
 * @param {number} uptimeSec — Math.floor(process.uptime())
 */
export function healthBody(uptimeSec) {
  return { status: 'ok', version: VERSION, uptime_sec: uptimeSec };
}
```

Правки в существующих файлах:

| Файл | Правка |
|---|---|
| `src/server.mjs:9-10` (импорты) | добавить `import { healthBody } from './health.mjs';` |
| `src/server.mjs:111-114` (ветка `/healthz`) | `return send(res, 200, healthBody(Math.floor(process.uptime())));` — литерал тела уходит из сервера |
| `tests/healthz.test.mjs` | ассерт `body.version === '0.1.0'` (или непустая строка) |
| новый `tests/health.test.mjs` | `deepEqual(healthBody(42), { status: 'ok', version: '0.1.0', uptime_sec: 42 })` + сверка `VERSION` с независимо прочитанным `package.json` — чистый тест без поднятия сокета |
| `README.md:34`, `.delivery/checks.json:15-18` | см. таблицу раздела 3 |

**Плюсы.**

- Единственное место правды о составе тела; имя поля и его значение живут в
  одном модуле, а не в ветке обработчика.
- Новая логика тестируется без сети — ровно та граница, которую репо проводит
  между `pricing.mjs` и `server.mjs`; тест идёт в `node --test` без сокета.
- Чтение манифеста — механизм языка, а не написанный код: меньше строк, которые
  могут сломаться, и нулевой риск ошибиться в обработке `JSON.parse`.
- Сервер уменьшается, а не растёт — правка идёт в хотспот против тренда
  (`task.md:150-153`).
- Никаких зависимостей и никакого расширения контракта, которого не требует
  issue.

**Минусы.**

- Импорт-атрибуты — самый молодой из используемых здесь механизмов языка:
  команда и агенты контура встречают его реже, чем `readFileSync`.
- JSON-модуль загружается один раз при старте: версия замораживается на время
  жизни процесса. Для версии это корректная семантика, но её нужно проговорить
  (см. К2 — там поведение то же, а видимость «живого чтения» создаёт ложное
  ожидание).
- Появляется четвёртый модуль в `src/` ради одного поля — для кодовой базы в 3
  файла это заметная надстройка (цена, которую платят за тестируемость).
- Файл-цель всё равно меняется: от хотспота никуда не уйти, правка по
  `app`-ветке остаётся.

**Усилия.** 0.5–1 день: модуль + два тестовых файла, синхронизация README и
delivery-контракта, Issue → ветка → PR → ревью.

**Риски.**

- Если `package.json` отсутствует или бит — процесс не стартует (SyntaxError на
  загрузке модуля). Это отказ-фаст и он виден в `npm start`, но в контуре, где
  стенд поднимает Delivery-Agent, красный старт хуже красного поля в ответе.
- Импорт-атрибуты нужно проверить прогоном на месте: механизм гарантирован
  Node ≥ 22 (`package.json:11-12`, образ `node:22-slim` — `.delivery/checks.json:7`),
  но в этой сессии запуск `node` недоступен, и проверка «одна строка — один
  запуск теста» переносится на стадию реализации.
- Откат тривиален: revert PR, литерал тела возвращается в ветку.

**HowToDemo:** проходит — `GET /healthz` содержит `version`.

### К2. Прагматичное: константа `VERSION` в `src/server.mjs` через уже импортированный `readFileSync`

**Категория:** Прагматичное.

**Суть.** Тот же источник и то же имя поля, что в К1, но без нового модуля:
`package.json` читается один раз при загрузке сервера — рядом с уже
существующим `STATIC_DIR`, средствами уже импортированного `readFileSync` — и
складывается в константу, которую ветка `/healthz` подставляет в свой литерал.
Минимальный дифф в одном файле, ровно то, что написано в ФТ-2.

**Что менять.**

| Файл | Правка |
|---|---|
| `src/server.mjs:13` (после `STATIC_DIR`) | `const VERSION = JSON.parse(readFileSync(join(__dirname, '../package.json'), 'utf8')).version;` |
| `src/server.mjs:111-114` | добавить `version: VERSION` в литерал тела |
| `tests/healthz.test.mjs`, `tests/server.test.mjs:154-161` | ассерты на `body.version` (тест остаётся сетевым — чистого теста здесь не появляется) |
| `README.md:34`, `.delivery/checks.json:15-18` | см. раздел 3 |

**Плюсы.**

- Самый короткий путь до HowToDemo: одна строка + одно поле + сопутствующие
  правки.
- Не появляется ни нового модуля, ни нового механизма языка — только идиом,
  уже живущих в этом файле (`__dirname`, `join`, `readFileSync` — строки 5, 12-13).
- Легко ревьюить и легко откатывать: дифф помещается на один экран.
- Поведение идентично К1 (одно чтение на процесс, отказ-фаст на битый манифест)
  при заметно меньшей цене.

**Минусы.**

- Файловый I/O в «тонкой обёртке» — натяжка конвенции `CLAUDE.md` («server.mjs —
  только разбор запроса и коды ответов»). Чтение одноразовое и не арифметика,
  но прецедент «в обёртке можно читать файлы ради ответа» создаётся, и следующий
  автор воспользуется им шире.
- Состав тела остаётся непроверяемым без сети: ассерт на версию можно написать
  только через HTTP-запрос (как сегодня `tests/healthz.test.mjs:6-23`).
  Конвенция «новая логика — новый тест» выполняется формально.
- Имя поля и формат тела остаются внутри `app` — то место, у которого
  `complex_method` и `change_entropy` в биомаркерах (`task.md:150-153`), не
  разгружается.
- `try/catch` вокруг чтения с фолбэком `'unknown'` соблазнителен и вреден:
  молча деградировать — значит отдавать поле, которое врёт. Честный вариант —
  без catch (см. риски К1; здесь они совпадают).

**Усилия.** 2–4 часа реализации + сопутствующие правки; суммарно с контуром
Issue → PR — около половины дня.

**Риски.**

- Тот же отказ-фаст на недоступном/битом `package.json`, что в К1, — но здесь
  он выглядит неожиданнее: падает «просто сервер», а не явно объявленный
  импорт манифеста.
- Исключение уйдёт в загрузку модуля и убьёт старт целиком, включая `/quote` —
  то есть ошибка в косметическом поле кладёт основной маршрут. Вероятность
  низкая (деплой — запуск из исходников вместе с манифестом), но радиус больше,
  чем у К1 (там и так падает весь старт, разница только в понятности причины).
- Откат: revert PR.

**HowToDemo:** проходит.

### К3. Быстрый костыль: версия из переменной окружения с литералом-фолбэком

**Категория:** Быстрый костыль.

**Суть.** Файловых чтений нет вовсе: ветка `/healthz` отдаёт
`process.env.APP_VERSION || '0.1.0'`. Переменную можно задать при деплое,
литерал гарантирует, что поле есть в ответе даже без настройки окружения.
Работает сегодня, записывает в репо второй источник истины о версии.

**Что менять.**

| Файл | Правка |
|---|---|
| `src/server.mjs:111-114` | `version: process.env.APP_VERSION \|\| '0.1.0'` в литерал тела |
| `tests/healthz.test.mjs`, `tests/server.test.mjs` | ассерт на наличие поля (значение в тесте зависит от окружения — проверяется только тип/непустота) |
| `README.md:34`, `.delivery/checks.json:15-18` | см. раздел 3 + задокументировать переменную `APP_VERSION` в разделе «Сервис» |

**Плюсы.**

- Час работы, включая сопутствующие правки; нет ни I/O, ни нового модуля.
- Побочный бонус, которого нет у К1–К2: переменная окружения — готовый канал
  для штампа сборки без заведения build-стадии (которая за границей задачи,
  `task.md:246-250`).
- Не может уронить старт: отсутствующее значение деградирует в литерал, процесс
  всегда поднимается.

**Минусы.**

- Прямое противоречие ФТ-2: значение **не** берётся из `package.json` — оно
  берётся из окружения или из литерала, продублированного из `package.json:3`.
  Требование из issue нарушается в единственном месте, ради которого фича
  задумана.
- Два источника правды, а дисциплины версионирования в репо нет (открытый
  вопрос 9.3): следующий релиз поднимет `package.json` и забудет про литерал —
  поле останется в ответе и начнёт врать. Для БТ-1 это хуже отсутствия поля:
  дежурный на разборе инцидента получает активную дезинформацию.
- Тест на значение невозможен: `process.env` в тесте придётся патчить, и тест
  начнёт проверять сам себя, а не логику. В `node --test` файлы запускаются
  отдельными процессами, так что вариант «выставить env до импорта» ломает
  соседние тесты того же файла.
- Тихая деградация: опечатка в имени переменной не даёт ни ошибки, ни пропавшего
  поля — отдаётся литерал.

**Усилия.** до 1 часа.

**Риски.**

- Главный риск не технический, а смысловой: поле есть, HowToDemo формально

  на первом же реальном инциденте.
- Откат тривиален (revert), но накопленный техдолг — вторая запись версии —
  остаётся в README и в head'ах тех, кто уже настроил `APP_VERSION`.

**HowToDemo:** проходит формально (поле есть), содержательно — нет.

### К4. Креативный хак: `process.env.npm_package_version` — версию подставляет сам npm

**Категория:** Креативный хак.

**Суть.** npm при запуске скриптов подставляет в окружение потомка
`npm_package_*` — в том числе `npm_package_version`, прочитанный им из
`package.json`. То есть требование ФТ-2 «значение из `package.json`»
выполняется вообще без строк кода, читающего `package.json`: ветка `/healthz`
просто читает готовую переменную окружения. Ноль I/O, ноль новых модулей, одна
строка.

**Что менять.**

| Файл | Правка |
|---|---|
| `src/server.mjs:111-114` | `version: process.env.npm_package_version` в литерал тела |
| `README.md:34` + раздел о способе запуска, `.delivery/checks.json:15-18` | см. раздел 3 + обязательная приписка «поле имеет смысл только при запуске через `npm start`» |
| `tests/healthz.test.mjs`, `tests/server.test.mjs` | ассерт возможен только при ручной установке переменной — то есть тест воспроизводит не механизм, а свою же заглушку |

**Плюсы.**

- Минимально возможный дифф: одно поле в литерале, никаких чтений.
- Значение действительно приходит из `package.json` — руками его никто не
  дублирует, расхождение источников исключено по построению.
- Бесплатно объясняет команде неочевидное свойство npm-скриптов.

**Минусы (и почему хак не выживает в этом стенде).**

- Механизм работает **только при запуске через `npm run <script>`**. Стенд
  поднимается прямой командой `node src/server.mjs` (`.delivery/checks.json:5`,
  тот же способ — `package.json:8` при вызове вне npm): переменной в окружении
  нет, `process.env.npm_package_version` — `undefined`, а `JSON.stringify` в
  `send()` (`src/server.mjs:29-37`) ключ с `undefined` молча **выбрасывает**.
  Поле просто исчезает из ответа — без ошибки, без 500, без лога.
- Следствие: демо у разработчика (через `npm start`) проходит, delivery-проверка
  на стенде — падает или, хуже, проходит мимо поля. Хак падает ровно в том
  окружении, ради которого завели issue #165.
- Зависимость от незадокументированного контракта npm (состав `npm_package_*`
  переменных не специфицирован и менялся между мажорами npm; pnpm/yarn
  подставляют имена по-своему). В репо, где зависимостей нет намеренно, это
  внешняя зависимость, замаскированная под стандартную библиотеку.
- Тест на механизм написать нельзя: `node --test` не запускает код через npm,
  значит ассерт всегда будет проверять переменную, выставленную самим тестом.

**Усилия.** до 1 часа (и столько же на разбор, почему на стенде поле пропало).

**Риски.**

- Высокий: отказ не поднимается как ошибка — поле тихо пропадает. Это худший
  режим для наблюдаемости, которую этим issue и добавляют.
- Откат тривиален.

**HowToDemo:** проходит при запуске через `npm start`, падает при запуске
способом Delivery-Agent'а (`.delivery/checks.json:5`) — то есть не проходит
границу MVP.

### К5. «Не трогай»: контракт `/healthz` не менять — версию печатать в лог при старте

**Категория:** «Не трогай» (отказ от изменения контракта).

**Суть.** Единственный внешний канал наблюдаемости не расширяется: тело
`/healthz` остаётся `{status, uptime_sec}`, ни один из четырёх артефактов зоны
воздействия не трогается. Вместо поля в ответе версия печатается одной строкой
в стандартный вывод при старте, рядом с существующим `console.log` — дежурный
определяет версию по логу запуска, а не входом в контейнер.

**Что менять.**

| Файл | Правка |
|---|---|
| `src/server.mjs:180-182` | строка запуска дополняется версией: чтение `package.json` тем же способом, что в К2 (одна строка), и вывод в `console.log` |
| `README.md` (раздел «Проверки» или «Сервис») | приписка «версия сервиса печатается в лог при старте» |

**Плюсы.**

- Нулевой риск по обоим открытым вопросам о потребителях (9.2, 9.4): контракт
  не меняется, значит не важно, кто и как сверяет тело.
- Не требуется синхронизация четырёх артефактов; дифф в две строки.
- Частично закрывает БТ-1: вход в контейнер заменяется чтением лога запуска.

**Минусы.**

- **Не проходит HowToDemo задачи**: ФТ-1 требует версию в JSON-теле ответа,
  её там нет. Этот концепт — не решение issue #165, а аргумент к
  переформулированию issue (если владельцы посчитают, что поле в контракте
  вредно).
- Лог — канал без гарантий: ротация, пересоздание контейнера, несколько
  рестартов — и «какой процесс сейчас отвечает» снова неочевиден. `uptime_sec`
  в теле ответа остаётся единственным различителем процессов, которым он не
  является (`task.md:64-68`).
- БТ-1 закрывается хуже, чем «не закрывать»: дежурный теперь уверен, что версию
  он узнать может, хотя канал ненадёжный.

**Усилия.** 0.5 часа.

**Риски.**

- Продуктовый, не технический: issue закрывается как не выполненный, либо
  выполняется и тут же переоткрывается на первом инциденте.
- Откат не нужен — откатывать нечего.

**HowToDemo:** не проходит (поля в теле нет).

### Раунд 1: Защита концепта К1 («Правильное»: `src/health.mjs` + импорт-атрибут JSON-модуля)

**Архитектор:**

- **К1 — единственный концепт, выполняющий ФТ-2 без нарушения записанной
  конвенции репо.** `CLAUDE.md` («Границы кода») прямо запрещает логику в
  обёртке — «логика в обёртке — логика, которую тест не увидит»; шапка файла
  повторяет то же своими словами: «здесь остаётся только разбор запроса и коды
  ответов». К2 добавляет в обёртку файловое чтение и значение — новая логика
  остаётся невидимой для теста без сети; К1 уносит сборку тела из обёртки.
  Доказательство: `CLAUDE.md` раздел «Границы кода»; `src/server.mjs:1-2`,
  `:111-114`.
- **Новая логика получает тест без сети — по прецеденту, который в репо уже
  дважды.** `pricing.mjs` ↔ `pricing.test.mjs`, `metrics.mjs` ↔
  `metrics.test.mjs`, где модуль импортируется напрямую и проверяется без
  сокета (`src/pricing.mjs:1-3`, `src/metrics.mjs:11-43`,
  `tests/metrics.test.mjs:3-9`). `healthBody(uptimeSec)` — чистая функция,
  проверяется `deepEqual` без поднятия порта; конвенция «новая логика — новый
  тест» выполняется по смыслу. У К2 единственный способ проверить новую логику —
  HTTP через реальный сокет (`tests/healthz.test.mjs:10-12`).
- **Чтение манифеста — механизм языка, а не написанный код.** Импорт-атрибут
  убирает из репо `JSON.parse`, ручную сборку пути и соблазн `try/catch`-фолбэка
  — той самой деградации «поле, которое врёт» (раздел 6). Меньше строк, которые
  могут сломаться молча, — а именно тихий отказ здесь объявлен главным злом
  (`CLAUDE.md`, «Проверки»; К4 — живой пример тихого отказа).
- **Правка идёт в хотспот против тренда, а не по нему.** `src/server.mjs` —
  health 5.45, hotspot 0.67, тренд increasing; К1 уменьшает файл (литерал тела
  на `src/server.mjs:111-114` заменяется одной строкой вызова), К2 —
  увеличивает. Доказательство: `sa_documentation/FNR/FNR_1/repowise-dialog.md:30-33`,
  `task.md:150-153`.
- **Риск «молодого механизма» с момента концепта сузился до одного прогона.**
  Известны фактические рантаймы: CI ставит `'22'` — плавающую мажорную, то есть
  последний 22.x (`.github/workflows/ci.yml:26-28`), стенд — `node:22-slim`
  (`.delivery/checks.json:7`), в среде анализа — v22.23.2. JSON-модули
  стабильны начиная с 22.12; проверка — тот же обязательный прогон
  `node --test "tests/*.test.mjs"`, которого требует `CLAUDE.md` для любой
  новой логики: неподдержанный атрибут роняет новый тест на импорте в PR, а не
  на стенде.

**Адвокат Дьявола:**

- **Аргумент 1 честен наполовину: К1 снимает натяжку конвенции, но втягивает
  `package.json` в граф модулей рантайма.** Манифест становится load-bearing
  исходником: перемещение файла, копирование `src/health.mjs` в другой проект,
  любой рантайм без поддержки атрибута — `SyntaxError` на импорте, и падает
  **весь** сервис вместе с `/quote`, потому что `src/server.mjs:9-10`
  импортирует соседей на верхнем уровне; тестовая прогонка падает целиком
  (`tests/server.test.mjs:3`, `tests/healthz.test.mjs:4`). У К2 радиус тот же
  (чтение на верхнем уровне сервера), но механизм не новый — то есть
  единственный дифференциатор К1 платит повышением минимальных требований к
  рантайму всего сервиса ради одного поля, а `engines: ">=22"`
  (`package.json:11-12`) границу 22.12, с которой механизм стабилен, не
  отсекает.
- **Четвёртый модуль в `src/` из трёх файлов — ради одного поля.** Гранулярность
  «одна забота — один модуль» здесь действительно есть, но прецеденты
  неравносильны: `pricing.mjs` несёт расчёт с ветвлением, `metrics.mjs` —
  состояние с мутацией (`src/metrics.mjs:21-32`). Забота К1 — «положить готовую
  строку в литерал». Это не следование прецеденту, а его растяжение.
- **Выигрыш «тест без сети» наполовину иллюзорен.** Чистая `healthBody`
  проверяет сборку словаря, но не то, что ветка `/healthz` **вызывает** её:
  провод от обработчика к модулю накрывается только HTTP-тестом
  (`tests/healthz.test.mjs:6-23`, `tests/server.test.mjs:154-161`), который в
  любом случае обязан появиться. Итого два тестовых файла вместо одного
  ассерта, и форма тела фиксируется дважды.
- **К1 не снимает ни один из вопросов, от которых зависит успех задачи.**
  Семантика `expect_json` (открытый вопрос 9.2) и различительная сила версии
  (9.3) остаются; стоимость синхронизации четырёх артефактов (раздел 3) К1
  платит та же, что К2. Дополнительная цена К1 — модуль, новый механизм,
  риск старта — покупает «чистоту», но не снижает проектный риск.
- **«Сервер уменьшается» — косметика, а не лечение хотспота.** Хотспотность
  создаётся ветвлением `app` и парой со-изменений с `tests/server.test.mjs`
  (биомаркеры `complex_method`, `change_entropy`, `test_gap` —
  `repowise-dialog.md:30-33`); вынос одного литерала профиль churn не меняет,
  пара со-изменений остаётся.

### Раунд 2: Пересмотр

**Архитектор:**

- **По радиусу отказа.** Принимаю факт, и он не дифференцирует: у К1 и К2 падает
  весь старт одинаково (это признано и в концепте: «разница только в понятности
  причины»). Спор не про радиус, а про возраст механизма — и он закрывается не
  спором, а фиксацией пола: (а) обязательный прогон тестов ловит неподдержанный
  атрибут в PR; (б) модификация — поднять `engines.node` с `>=22` до `>=22.12`
  (`package.json:11-12`): одна строка, способ хранения версии не трогает,
  сопровождающая правка в границе задачи (утверждает владелец issue). После
  этого «молодой механизм» — не риск старта, а зафиксированное требование к
  рантайму.
- **По четвёртому модулю.** Модуль появляется не ради поля, а ради единственного
  места правды о составе тела: сегодня этот состав выводят из себя четыре
  артефакта (`src/server.mjs:111-114`, два тестовых файла, `README.md:34`,
  `.delivery/checks.json:15-18`), и в коде они держатся на одном литерале внутри
  обработчика. Репо уже делает такой ход для соседнего ответа: тело `/stats`
  собирается вне обёртки — `counters.getStats()` (`src/metrics.mjs:38-41`,
  вызов `src/server.mjs:121`). Так что это не растяжение прецедента, а тот же
  прецедент. Связь с манифестом — одно ребро, грепается одной строкой.
- **По «иллюзорному выигрышу» — модификация плана тестов.** Согласен: провод
  ветки к модулю чистым тестом не накрывается. Поэтому ответственность тестов
  разделяется, а не дублируется. Чистый `tests/health.test.mjs` проверяет
  **значение**: `deepEqual(healthBody(42), {status:'ok', version:'0.1.0',
  uptime_sec:42})` плюс сверка `VERSION` с независимо прочитанным
  `package.json`. HTTP-тесты (`tests/healthz.test.mjs`,
  `tests/server.test.mjs:154-161`) проверяют **наличие провода**: `body.version`
  — непустая строка, без конкретного значения. Форма фиксируется один раз,
  поднятая версия не ломает HTTP-тесты, отвалившийся вызов ловят они.
- **По «риск не снижен».** Уточняю, что именно покупается: К2 удовлетворяет
  «новая логика — новый тест» формально — единственный тест новой логики идёт
  через сокет, и каждая следующая правка состава тела наследует то же. К1
  создаёт паттерн один раз; следующее поле — одна строка в модуле и одна строка
  чистого теста. Снижение стоимости следующего изменения — единственное, чем
  хотспот реально лечится, и оно достигается здесь.
- **По «косметике».** Принимается: заявка концепта — «правка в хотспот против
  тренда», а не «лечение хотспота». Лечение `app` — отдельная задача, в эту
  границу не входит.

**Адвокат Дьявола (проверка усиленного варианта, включая сценарии «через полгода»):**

- **Через полгода просят штамп сборки (git SHA, дата).** Усиленный К1 даёт новому
  полю **место**, но не **механизм**: build-стадии в репо нет (`task.md:246-250`),
  значение придётся брать из окружения — а это К3 с его нарушением ФТ-2.
  Настоящая причина разрыва — дисциплина версионирования (открытый вопрос 9.3),
  и её не создаёт ни К1, ни К2. Значит, эволюционная ценность модуля ограничена,
  а сам вопрос — SubIssue с `root-issue: #165`, не аргумент за модуль.
  Архитектор на это и не претендовал; замечание принято как граница.
- **Через полгода появляется контейнеризация, и `package.json` перестаёт лежать
  на `../package.json` от `src/`.** У К1 ломается один импорт в одном файле, у
  К2 — одна строка в `server.mjs`: разницы нет, ловится CI
  (`.github/workflows/ci.yml:28`) и delivery-проверкой раньше стенда. Риск
  локализован и симметричен — не дифференциатор.
- **Через полгода стенду нужно переопределять версию (канарейка, тестовый
  деплой).** Ни К1 (`VERSION` заморожена на импорте), ни К2 (одно чтение на
  процесс) этого не умеют; умеет только К3, запрещённый ФТ-2. Граница задачи,
  не дифференциатор.
- **Delivery остаётся единственным шагом, способным уронить стенд после
  мерджа.** Если семантика `expect_json` — точное равенство, а правка
  `.delivery/checks.json:15-18` не сделана синхронно, smoke-проверка станет
  красной; если подмножество — правка профилактическая, но строка `source`
  (`.delivery/checks.json:18`) всё равно становится фактически неверной.
  Требую зафиксировать в вердикте: подтверждение семантики у владельца
  Delivery-Agent — обязательный шаг, а не опция.
- **Фолбэк `'unknown'`.** Запрет из раздела 6 подтверждаю: молча врущее поле
  хуже отсутствующего. Дополнительный довод в пользу К1, который признаю:
  механизм языка делает такой фолбэк невозможным без намеренно написанного кода.

### Раунд 3: Финальная позиция

**Архитектор:** К1 выполняет ФТ-1/ФТ-2, не добавляя логики в обёртку, которую
тест не видит, и возвращает `server.mjs` к его собственной конвенции; оба его
реальных риска — возраст механизма и радиус отказа — закрываются одним прогоном
тестов и одной строкой `engines`. К2 остаётся запасным ходом ровно на один
случай: если прогон стадии реализации покажет проблему с атрибутом в окружении
стенда.

**Адвокат Дьявола:** К1 приемлем при трёх жёстких условиях: имя поля
зафиксировано как `version`; ответственность тестов разделена (значение —
чистым тестом, провод — HTTP); семантика `expect_json` подтверждена у владельца
Delivery-Agent до мерджа. Различительную силу версии (открытый вопрос 9.3) К1
не решает — она обязана уйти в SubIssue, иначе БТ-1 останется открытой при

## ВЕРДИКТ

**Выбранный концепт:** К1 «Правильное» — сборка тела `/healthz` выносится в
чистый модуль `src/health.mjs`; версия читается импорт-атрибутом JSON-модуля
(`import pkg from '../package.json' with { type: 'json' }`).

**Модификации:**

1. **Имя поля — `version`** (открытый вопрос 9.1 закрыт: конфликтов нет ни в
   коде, ни в тестах, ни в `expect_json`; имя зеркалит ключ `package.json:3`,
   так что связь «откуда значение» читается без документации).
2. **Разделить ответственность тестов:** `tests/health.test.mjs` — `deepEqual`
   тела и сверка `VERSION` с независимо прочитанным `package.json`;
   `tests/healthz.test.mjs` и `tests/server.test.mjs:154-161` — только наличие
   непустого `body.version` (ловят провод, а не значение; поднятая версия их не
   ломает).
3. **Отказ-фаст сохраняется:** без `try/catch`-фолбэка `'unknown'` (раздел 6
   концепта; обе стороны подтвердили).
4. **Синхронно обновить `.delivery/checks.json:15-18`** (`version` в
   `expect_json`, переписать строку `source`); **подтверждение семантики
   `expect_json` у владельца Delivery-Agent — обязательный шаг до мерджа**

   `node --test "tests/*.test.mjs"`: снимает «неподтверждённость прогона» для
