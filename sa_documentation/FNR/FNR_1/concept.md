# Концепты решений: Скидка по промокоду в корзине

## Основание для концептов

**Задача:** Добавить механизм применения промокодов для скидки на сумму товаров в сервисе расчёта стоимости заказа.

**Ограничения из task.md:**
- Скидка только на товары, доставка не скидывается
- Хардкод `SALE10` → 10% скидки
- Неизвестный промокод — понятное сообщение
- Обратная совместимость: `promoCode` — опциональное поле
- Арифметика в чистых функциях, HTTP-слой только обёртка

**Файлы для изменения:**
- `src/pricing.mjs` — арифметика
- `src/server.mjs` — HTTP-обёртка
- `tests/pricing.test.mjs` — тесты

## Концепт 1: Минимальное расширение API (Правильное)

**Суть:** Расширить существующий контракт `quote()` вторым опциональным параметром `promoCode`, добавить в ответ поля `discount` и `promoStatus`. Логика промокодов — inline в `quote()`.

**Изменения в файлах:**

### `src/pricing.mjs`
```javascript
// Добавить константу промокода
export const PROMO_CODES = {
  SALE10: { discount: 0.10, description: 'Скидка 10%' }
};

// Обновить JSDoc и сигнатуру quote
export function quote(items, promoCode = null) {
  const goods = subtotal(items);
  const delivery = deliveryFee(goods);

  let discount = 0;
  let promoStatus = 'none';

  if (promoCode) {
    const promo = PROMO_CODES[promoCode];
    if (promo) {
      discount = goods * promo.discount;
      promoStatus = 'applied';
    } else {
      promoStatus = 'unknown';
    }
  }

  return { goods, delivery, discount, promoStatus, total: goods - discount + delivery };
}
```

### `src/server.mjs`
```javascript
// Передавать promoCode из запроса
return send(res, 200, quote(body?.items, body?.promoCode));
```

**Плюсы:**
- ✅ Сохраняет архитектурное разделение (арифметика → pricing, HTTP → server)
- ✅ Обратная совместимость (promoCode опционален)

## Концепт 2: Модуль промокодов (Прагматичное)

**Суть:** Выделить логику промокодов в отдельный модуль `src/promo.mjs` с чистыми функциями, готовый к расширению (типы скидок, ограничения, менеджмент).

**Изменения в файлах:**

### Новый файл `src/promo.mjs`
```javascript
/**
 * Реестр промокодов
 */
export const PROMO_CODES = {
  SALE10: { type: 'percent', value: 0.10, description: 'Скидка 10%' },
  // Место для будущих промокодов
};

/**
 * Применить промокод к сумме товаров
 * @param {number} goods — сумма товаров до скидки
 * @param {string|null} code — код промокода
 * @returns {{discount: number, status: string}}
 */
export function applyPromoCode(goods, code) {
  if (!code) {
    return { discount: 0, status: 'none' };
  }

  const promo = PROMO_CODES[code];
  if (!promo) {
    return { discount: 0, status: 'unknown' };
  }

  if (promo.type === 'percent') {
    return { discount: goods * promo.value, status: 'applied' };
  }

  // Заготовка для других типов
  return { discount: 0, status: 'invalid_type' };
}
```

### `src/pricing.mjs`
```javascript
import { applyPromoCode } from './promo.mjs';

export function quote(items, promoCode = null) {
  const goods = subtotal(items);
  const delivery = deliveryFee(goods);
  const { discount, status } = applyPromoCode(goods, promoCode);
  return { goods, delivery, discount, promoStatus: status, total: goods - discount + delivery };
}
```

### `src/server.mjs`
```javascript
// Передавать promoCode из запроса
return send(res, 200, quote(body?.items, body?.promoCode));
```

## Концепт 3: Inline-проверка в quote() (Быстрый костыль)

**Суть:** Минимальная правка: добавить `if (promoCode === 'SALE10')` прямо в `quote()` без вынесения в константы.

**Изменения в файлах:**

### `src/pricing.mjs`
```javascript
export function quote(items, promoCode = null) {
  const goods = subtotal(items);
  const delivery = deliveryFee(goods);

  let discount = 0;
  let promoStatus = 'none';

  if (promoCode === 'SALE10') {
    discount = goods * 0.10;
    promoStatus = 'applied';
  } else if (promoCode) {
    promoStatus = 'unknown';
  }

  return { goods, delivery, discount, promoStatus, total: goods - discount + delivery };
}
```

### `src/server.mjs`
```javascript
return send(res, 200, quote(body?.items, body?.promoCode));
```

### `tests/pricing.test.mjs`
Минимальные тесты для SALE10 и unknown

**Плюсы:**
- ✅ Самый быстрый в реализации
- ✅ Минимум кода

**Минусы:**
- ❌ Магическое число `0.10` в коде
- ❌ Магическая строка `'SALE10'` в коде
- ❌ Не готов к расширению
- ❌ Нарушает принцип "не повторяйся" (если промокодов будет несколько)
- ❌ Сложно тестировать крайние случаи

**Усилия:** 1-2 часа

**Риски:** Средние — технический долг, рефакторинг потребуется при втором промокоде

## Концепт 4: Pattern matching с Object (Креативный хак)

**Суть:** Использовать деструктуризацию и pattern matching для лаконичного кода, готового к расширению через Object.

**Изменения в файлах:**

### `src/pricing.mjs`
```javascript
// Паттерн-матчинг через объект-функцию
const promoDiscount = {
  SALE10: (goods) => goods * 0.10,
  // Будущие промокоды:
  // SAVE100: (goods) => Math.min(goods * 0.15, 100),
  // WELCOME5: (goods) => goods < 5000 ? 0 : 250,
};

export function quote(items, promoCode = null) {
  const goods = subtotal(items);
  const delivery = deliveryFee(goods);

  const discount = promoCode && promoDiscount[promoCode]
    ? promoDiscount[promoCode](goods)
    : 0;

  const promoStatus = promoCode
    ? (promoDiscount[promoCode] ? 'applied' : 'unknown')
    : 'none';

  return { goods, delivery, discount, promoStatus, total: goods - discount + delivery };
}
```

### `src/server.mjs`
```javascript
return send(res, 200, quote(body?.items, body?.promoCode));
```

### `tests/pricing.test.mjs`
Тесты для проверенных промокодов и крайних случаев

**Плюсы:**
- ✅ Лаконичный код
- ✅ Лёгкое добавление промокодов с разной логикой
- ✅ Функциональный стиль подходит для чистых функций
- ✅ Поддержка кастомной логики на промокод (conditional discounts)

**Минусы:**
- ❌ Менее очевидно для новичков
- ❌ Сложнее добавить метаданные (description, сроки действия)
- ❌ Проверка типа промокода требует отдельной логики

**Усилия:** 2-3 часа

**Риски:** Низкие — расширяемый подход, но менее структурированный, чем Концепт 2

## Архитектурные дебаты

### Раунд 1 — Защита

**Архитектор (за Концепт 2):**

Я выбираю **Концепт 2 (Модуль промокодов)** как оптимальный баланс между архитектурной чистотой и усилиями.

**Аргументы:**

1. **Следует существующей архитектуре** — pricing.mjs содержит чистые функции ([src/pricing.mjs:631-633](../src/pricing.mjs:631-633)), server.mjs — тонкая HTTP-обёртка ([src/server.mjs:686-687](../src/server.mjs:686-687)). Концепт 2 сохраняет это разделение.

2. **Принцип единой ответственности** — логика промокодов выделяется в отдельный модуль `src/promo.mjs`. При росте типов скидок (фиксированная сумма, "2+1", бесплатная доставка) это естественное место для расширения.

3. **Обратная совместимость** — `promoCode` остаётся опциональным параметром ([task.md:121](task.md:121)), существующие клиенты не ломаются.

4. **Изолированное тестирование** — модуль промокодов тестируется независимо, следуя паттерну существующих тестов ([tests/pricing.test.mjs:742-795](../tests/pricing.test.mjs:742-795)).

5. **Усилия незначительно больше** — 3-4 часа vs 2-3 часа у Концепта 1, но архитектурно правильнее.

---

**Адвокат Дьявола (атака на Концепт 2):**

Слабые места Концепта 2:

1. **YAGNI-нарушение** — MVP требует **один** хардкодный промокод `SALE10`, а мы строим модульную структуру под "будущие типы скидок". Задача ([task.md:96-100](task.md:96-100)) явно говорит: типы кроме процентных — out scope.

2. **Ложная масштабируемость** — "готов к расширению" звучит хорошо, но расширение вообще не в scope. Когда оно появится — промокоды могут потребовать совершенно другой структуры (сроки действия, минимальная сумма, ограничение по пользователям).

3. **Ненужный файл** — новый `src/promo.mjs` = новый контракт для поддержки ради 10 строк кода. При наличии тестов изменение inline-логики в `quote()` не опаснее.

4. **Концепт 1 делает то же за меньшее время** — 2-3 часа vs 3-4 часа. Разница в час не оправдывает дополнительный файл.

**Вердикт Адвоката Раунда 1:** Концепт 2 — over-engineering под несуществующие требования.

---

### Раунд 2 — Пересмотр

**Архитектор (ответ на критику):**

Принимаю критику по YAGNI — это справедливо. Пересматриваю позицию:

1. **Концепт 2 действительно избыточен для текущего scope** — у нас один промокод, один тип скидки (процент), никаких ограничений. Модульная структура здесь не окупается.

2. **Но Концепт 3 (Inline) неприемлем** — магические числа `0.10` и строка `'SALE10'` прямо в коде ([concept.md:185-190](concept.md:185-190)) нарушают принцип "не повторяйся" и создают технический долг уже при втором промокоде.

3. **Пивот на Концепт 1** — это тот же Концепт 2, но без отдельного файла. Вынесение `PROMO_CODES` в константу внутри `pricing.mjs` решает проблему магических чисел, не создавая новой сущности.

**Пересмотренный выбор:** Концепт 1 (Минимальное расширение API) с уточнением — константа `PROMO_CODES` экспортируется для будущего выноса в конфиг.

---

**Адвокат Дьявола (what-if проверка Концепта 1):**

Проверяю Концепт 1 на устойчивость:

**✅ Что если промокодов станет 5-10?**
```javascript
export const PROMO_CODES = {
  SALE10: { discount: 0.10, description: 'Скидка 10%' },
  WELCOME5: { discount: 0.05, description: 'Скидка 5%' },
  // ... ещё 8 промокодов
};
```
Вынос в отдельный модуль становится естественным рефакторингом, а не вынужденным. Сейчас — не критично.

**❌ Что если промокоду нужна кастомная логика?**
Например: "Скидка 15%, но не более 500 рублей" или "Бесплатная доставка для новых клиентов".

В Концепте 1 это потребует менять структуру `PROMO_CODES` и логику в `quote()`. Но это уже **новая задача** с новыми требованиями — out scope текущего MVP ([task.md:100-101](task.md:100-101)).

**✅ Что если промокод не найден?**
Концепт 1 возвращает `promoStatus: 'unknown'` ([concept.md:47-48](concept.md:47-48)) — это соответствует требованиям ([task.md:93](task.md:93)) и не требует отдельной ошибки 400.

**⚠️ Что если доставка должна скидываться по промокоду?**
Концепт 1 считает доставку по `goods` ДО скидки ([concept.md:38](concept.md:38)) — это соответствует требованию "доставка не скидывается" ([task.md:39](task.md:39)). Но если requirement изменится, придётся рефакторить.

**Вердикт Адвоката Раунда 2:** Концепт 1 приемлем для MVP, но несёт риск изменения формата данных при будущих требованиях.
