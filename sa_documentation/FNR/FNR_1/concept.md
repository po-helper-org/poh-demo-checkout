# FNR-1: Концепты решений

**Задача:** Запрос на изменение визуальной стилистики в стиле Threads  
**Проблема:** В проекте отсутствует визуальный интерфейс (UI)  
**Статус:** Анализ вариантов решения

---

## Диагноз ситуации

Запрос пользователя *"Поменять цвета на стилистику Threads"* обращается к компоненте, которая в проекте отсутствует. Проект `poh-demo-checkout` представляет собой:

- **Чистый HTTP-JSON API** (`src/server.mjs`) без фронтенда
- **Бизнес-логика расчёта стоимости** (`src/pricing.mjs`) без представления
- **Тестовый Coverage** только арифметики (`tests/pricing.test.mjs`)

Доказательства отсутствия UI:
- Нет файлов `.html`, `.css`, `.jsx`, `.tsx`, `.vue`, `.svelte`
- Нет директорий `frontend/`, `web/`, `client/`, `static/`, `public/`, `assets/`
- `grep -r "color\|background\|style" src/` — пустой результат

---

## Концепты решений

### 1. Правильное: Создание веб-интерфейса в стиле Threads

**Суть:** Создать полноценный UI-слой для существующего API с визуальной стилистикой Threads.

**Что делать:**
- Создать директорию `web/` с HTML/CSS/JS
- Реализовать форму ввода заказа (позиции: SKU, цена, количество)
- Стилизовать под Threads: чёрно-белая палитра, минимализм, крупная типографика
- Подключить к существующему endpoint `/quote`
- Добавить тесты UI (Playwright или类似的)

**Затронутые файлы:**
- `web/index.html` (новый)
- `web/styles.css` (новый)
- `web/app.js` (новый)
- `src/server.mjs` (добавить serving static files)
- `tests/ui.test.mjs` (новый, если выбран подходящий инструмент)

**Плюсы:**
- Полноценное решение запроса пользователя
- Демонстрация работы API через визуальный интерфейс
- Потенциально полезно для демо-стенда

**Минусы:**
- Значительное увеличение scope проекта
- Нарушение принципа "без зависимостей" (нужен UI-фреймворк или хотя бы вендоринг)
- Уход от фокуса контура (тестирование автоматизации производства, а не UI-разработка)

**Усилия:** 2-3 дня

**Риски:**
- Выбор технологии (vanilla vs framework) потребует решения
- UI-тестирование не покрывается существующей инфрой CI

---

### 2. Прагматичное: Минимальный HTML-интерфейс

**Суть:** Создать максимально простой интерфейс для демонстрации работы API без стилизации под Threads.

**Что делать:**
- Один файл `static/index.html` с формой
- Vanilla JS для отправки запроса на `/quote`
- Базовая стилизация (без привязки к Threads)
- Сerving static через существующий `server.mjs`

**Затронутые файлы:**
- `static/index.html` (новый)
- `src/server.mjs` (добавить route для статических файлов)

**Плюсы:**
- Быстрый MVP (2-4 часа)
- Не нарушает принцип "без зависимостей"
- Достаточно для демонстрации API
- Не усложняет CI

**Минусы:**
- Не соответствует запросу "стиль Threads"
- Пользователь может быть недоволен несоответствием ожиданиям

**Усилия:** 2-4 часа

**Риски:**
- Нужно уточнить: устроит ли пользователя "любой интерфейс" без Threads-стилистики

---

### 3. Быстрый костыль: Отказ с объяснением

**Суть:** Закрыть Issue с объяснением, что визуального интерфейса в проекте нет и это не является багой.

**Что делать:**
- Комментарий в Issue #8 с диагнозом
- Предложение alternatives: создать отдельный проект для UI
- Закрытие Issue с меткой `wontfix` или `out-of-scope`

**Затронутые файлы:**
- Никаких (только комментарий в Issue)

**Плюсы:**
- Мгновенное решение (5 минут)
- Честно: проект позиционируется как демо-стенд контура, а не UI-сервис
- Не усложняет кодовую базу

**Минусы:**
- Пользователь получает отказ
- Запрос может быть симптомом непонимания назначения проекта

**Усилия:** 5-10 минут

**Риски:**
- Пользователь может повторить запрос, если не поймёт объяснение

---

### 4. "Не трогай": Категоризация как out-of-scope

**Суть:** Интерпретировать запрос как выход за границы назначения проекта и закрыть без изменений.

**Обоснование:**
Проект `poh-demo-checkout` существует как **демо-стенд контура производства** (Issue → Аналитика → Разработка → PR → Ревью), а не как пользовательский сервис. Добавление UI уводит фокус от тестируемого контура.

**Что делать:**
- Закрыть Issue с меткой `out-of-scope`
- Ссылка на README.md: назначение проекта — контур, а не UI
- Предложение завести отдельный Issue: "Добавить UI к демо-стенду" (другая задача)

**Затронутые файлы:**
- Никаких

**Плюсы:**
- Чёткое соблюдение границ проекта
- Не раздувает scope демо-стенда
- Сохраняет простоту кодовой базы

**Минусы:**
- Формальный отказ
- Требует коммуникативного навыка объяснения

**Усилия:** 5 минут

**Риски:**
- Может быть воспринято как "нежелание работать"

## Рекомендуемый путь

**Предлагается:** Концепт 3 (Быстрый костыль) с переходом к Концепту 2 при уточнении требований.

**Обоснование:**
1. Запрос противоречит текущей архитектуре (нет UI → нельзя изменить стиль)
2. Проект — демо-стенд контура, а не пользовательский сервис
3. Быстрый отказ с объяснением честнее чем реализация того, что не запрашивалось

**Следующие шаги:**
1. Уточнить у пользователя: действительно ли нужен UI для этого API?
2. Если да — уточнить минимальный набор функций (MVP)
3. Если минимальный набор определён — перейти к Концепту 2

## Альтернатива: Если пользователь подтверждает потребность в UI

Вариант модификации Концепта 2:

**Hybrid-подход:** Создать отдельный репозиторий `poh-demo-checkout-ui` который:
- Consumes JSON API из `poh-demo-checkout`
- Реализует Threads-стилистику
- Не усложняет контур (отдельный проект, отдельный lifecycle)

**Плюсы:**
- Чистое разделение ответственности
- Контур не усложняется
- Можно реально стилизовать под Threads

**Минусы:**
- Два репозитория вместо одного
- Необходимо решить вопрос развертывания (как запустить оба вместе)

# Архитектурные дебаты

## Раунд 1: Защита

### Архитектор (защищает Концепт 3 → Концепт 2 с уточнением)

**Выбор:** Концепт 3 (Быстрый костыль) с переходом к Концепту 2 (Минимальный HTML-интерфейс) при уточнении.

**Аргументы:**

1. **Диагноз ситуации:** Запрос "Поменять цвета на стилистику Threads" подразумевает наличие визуального интерфейса, которого в проекте нет. Доказательство: `find repo -type f \( -name "*.html" -o -name "*.css" -o -name "*.jsx" \)` — пустой результат.

2. **Соответствие назначению проекта:** CLAUDE.md:3 — "Гайд для Claude Code в этом репозитории. Он же демо-стенд контура производства". Проект существует для тестирования автоматики производства (Issue-Agent, OpenHands, PR-Agent), а не как пользовательский сервис.

3. **Принцип "без зависимостей":** CLAUDE.md:61-62 — "Зависимостей у сервиса нет. Новая заводится, только если задачу нечем закрыть из стандартной библиотеки". Концепт 1 (полный UI) потребует UI-фреймворк или сложный вендоринг.

4. **Асимметричная информация:** Пользователь может не понимать архитектуру проекта. Быстрый диагноз (Концепт 3) честнее чем реализация того, что не запрашивалось.

### Адвокат Дьявола (атака)

**Контраргументы:**

1. **Уход от ответственности:** Концепт 3 — это формальный отказ, который может быть воспринят как "нежелание работать". Если пользователь действительно нужен UI для демо-стенда, отказ блокирует ценность.

2. **Ложная дилемма:** Противопоставление "нет UI" против "полный UI в стиле Threads" игнорирует промежуточные варианты. Почему бы не создать минимальный интерфейс сразу, без предварительного отказа?

3. **Риск повторного запроса:** Пользователь может не понять объяснение и создать новый Issue с той же просьбой, что приведёт к циклическому диалогу.

4. **Упущенная возможность:** Демо-стенд с визуальным интерфейсом был бы мощнее для демонстрации работы контура. Возможно, запрос пользователя — это не недопонимание, а ценное предложение по улучшению.

## Раунд 2: Пересмотр

### Архитектор (учитывает критику)

**Усиление позиции:**

1. **Признание:** Адвокат прав — Концепт 3 (чистый отказ) несёт риск быть воспринятым как нежелание работать. Это может создать негативный паттерн взаимодействия.

2. **Пивот к Гибридному подходу (модификация Концепта 2):**
   - Немедленная реализация минимального HTML-интерфейса (2-4 часа)
   - Без привязки к Threads-стилистике
   - С комментарием: "UI создан в минимальном варианте. Threads-стилистика требует отдельного обсуждения scope"

3. **Почему не полный Threads-стиль (Концепт 1):**
   - Threads — это чёрно-белая минималистичная эстетика с крупной типографикой
   - Для качественной реализации потребуются: CSS-фреймворк или сложный кастомный CSS
   - Это нарушает принцип "без зависимостей" (CLAUDE.md:61-62)
   - Уводит от фокуса проекта (тестирование контура, а не UI-разработка)

4. **Адресация риска повторного запроса:** Гибридный подход создаёт артефакт (минимальный UI), который можно демонстрировать. Если пользователь insists на Threads-стилистике — это становится отдельной задачей с явным scope.

### Адвокат Дьявола (проверка на устойчивость)

**Вопросы "А что если":**

1. **"А что если через полгода scope проекта изменится?"** Гибридный подход создаст технический долг: минимальный UI будет поддерживаться, а полноценный Threads-UI — отдельная ветка. Не лучше ли сразу сделать правильно?

2. **"А что если пользователь — стейкхолдер с реальными потребностями?"** Отказ или минимальный UI может создать впечатление, что команда не способна на качественную UI-работу. Не повредит ли это репутации контура?

3. **"А что если Threads-стиль — это просто пример, а суть в любом интерфейсе?"** Тогда мы зря тратим время на диагностику. Быстрый MVP (Концепт 2) мог бы быть delivered уже сейчас.

## Раунд 3: Вердикт

### Архитектор (итоговая позиция)

**Финальное решение:** Гибридный подход (модифицированный Концепт 2).

**Обоснование:**

1. **Диагноз → Действие:** Вместо чистого отказа (Концепт 3) создаём минимальный UI, который:
   - Демонстрирует работу API визуально
   - Занимает 2-4 часа (вместо 2-3 дней на полный Threads-UI)
   - Не нарушает принцип "без зависимостей" (vanilla HTML/CSS/JS)
   - Не усложняет CI

2. **Коммуникация:** В Issue добавляется комментарий:
   ```
   Создан минимальный веб-интерфейс для API. Threads-стилистика требует отдельного обсуждения scope, так как существенно увеличивает объём работы.
   Если Threads-стиль критичен — создам отдельный Issue с оценкой.
   ```

3. **Следующие шаги:**
   - Реализация `static/index.html` с формой заказа
   - Модификация `src/server.mjs` для serving статических файлов
   - Тест (можно manual, так как UI не критичен для контура)

### Адвокат Дьявола (итоговая позиция)

**Согласие с модификациями:**

1. **Гибридный подход приемлем:** Он создаёт артефакт (минимальный UI), который можно демонстрировать, и оставляет дверь открытой для Threads-стилистики как отдельной задачи.

2. **Риск acknowledged:** "Повторный запрос" mitigation — наличие работающего UI снижает вероятность повторной просьбы "что-то визуальное".

3. **Остаточная concern:** Если пользователь действительно важен и Threads-стиль критичен, мы создадим два интерфейса (минимальный + Threads). Это could be inefficient. Однако это рискуем, так как full Threads-UI — это 2-3 дня против 2-4 часов.

# Вердикт

## Решение: Концепт 2 (Прагматичное) с модификацией — Гибридный подход

**Принято:** Создать минимальный HTML-интерфейс без Threads-стилистики с прозрачной коммуникацией о scope.

**Что будет сделано:**

1. **Артефакты:**
   - `static/index.html` — форма заказа (SKU, цена, количество)
   - `static/app.js` — vanilla JS для отправки на `/quote`
   - `static/style.css` — базовая стилизация (без Threads)
   - Модификация `src/server.mjs` — serving статических файлов

2. **Коммуникация:**
   - Комментарий в Issue #8 с диагнозом и объяснением
   - Предложение: если Threads-стиль критичен — отдельный Issue с оценкой

3. **Время реализации:** 2-4 часа

4. **Соответствие ограничениям:**
   - ✅ Принцип "без зависимостей" (vanilla HTML/CSS/JS)
   - ✅ Фокус на контуре производства (UI не усложняет CI)
   - ✅ MVP first ( Threads-стиль как potential enhancement)

**Потенциальные following steps (если пользователь подтвердит потребность):**

1. Отдельный Issue: "Добавить Threads-стилистику к веб-интерфейсу"
2. Там же: оценка scope (2-3 дня), выбор подхода (vanilla CSS vs framework)
3. Решение о dependencies (если Threads-стиль требует CSS-фреймворк)
