- **Изоляция:** `/healthz` не считается посещением
- **Хранение:** в памяти, без персистентности

## Концепты решений

### Концепт 1: Правильное (Separated Metrics Module)

**Суть:** Выделение метрик в отдельный модуль с чистыми функциями и явным состоянием.

**Описание:**
Создаём модуль `src/metrics.mjs`, экспортирующий:
- Счётчики как замкнутые переменные модуля
- Функции `incVisit()`, `incSuccess()`, `getStats()`
- Типизированную структуру ответа

`server.mjs` импортирует функции метрик и вызывает их в нужных точках.

**Затрагиваемые файлы:**
- **Новый:** `src/metrics.mjs` — весь код метрик
- **Изменения:** `src/server.mjs` — импорт и вызовы в 2 точках

**Плюсы:**
- Чёткое разделение ответственности (SRP)
- Легко тестировать метрики изолированно
- Расширяемость: легко добавить новые метрики
- Следует архитектурным принципам проекта
- `pricing.mjs` остаётся нетронутым

**Минусы:**
- Новый файл в проекте
- Легковесный overhead для двух счётчиков

**Усилия:** 2-3 часа

**Риски:** Низкие — изолированный модуль, не затрагивает существующую логику

---

### Концепт 2: Прагматичное (Closures in server.mjs)

**Суть:** Замыкания внутри `server.mjs` для инкапсуляции состояния без нового модуля.

**Описание:**
В начале `server.mjs` создаём замыкание:

```javascript
const counters = (() => {
  let visits = 0;
  let successes = 0;
  return {
    incVisit: () => { visits += 1; },
    incSuccess: () => { successes += 1; },
    get: () => ({ visits, successes })
  };
})();
```

Используем `counters.incVisit()` и `counters.incSuccess()` в нужных точках.
Доступ к значениям через новый эндпоинт `GET /stats`.

**Затрагиваемые файлы:**
- **Изменения:** `src/server.mjs` — добавление замыкания и эндпоинта `/stats`

**Плюсы:**
- Всё в одном файле — нет новых модулей
- Инкапсуляция состояния через замыкание
- Не ломает существующую структуру
- Быстрый путь к MVP

**Минусы:**
- Меньшая тестируемость (метрики не separable)
- Менее явное разделение ответственности
- При росте метрик нужен будет рефакторинг в модуль

**Усилия:** 1-2 часа

**Риски:** Низкие — локальные изменения в одном файле

---

### Концепт 3: Быстрый костыль (Inline Globals)

**Суть:** Глобальные переменные в верхнем уровне `server.mjs`.

**Описание:**
Просто добавляем в начало `server.mjs`:

```javascript
let visitCount = 0;
let successCount = 0;
```

Инкрементируем в нужных местах через `visitCount++` и `successCount++`.
Экспозим через `/stats` или `console.log` при каждом запросе.

**Затрагиваемые файлы:**
- **Изменения:** `src/server.mjs` — минимальные правки

**Плюсы:**
- Максимально быстро — 15-30 минут работы
- Понятно любому разработчику
- Минимум кода

**Минусы:**
- Глобальное состояние — плохая практика
- Нет инкапсуляции — можно случайно изменить
- Сложно тестировать изолированно
- Технический долг — понадобится рефакторинг

**Усилия:** 0.5-1 час

**Риски:** Низкие для функциональности, высокие для качества кода

---

### Концепт 4: Креативный хак (Response Headers)

**Суть:** Передача счётчиков через HTTP-заголовки ответа без нового эндпоинта.

**Описание:**
Инкрементируем счётчики в памяти (как в Концепте 2), но вместо `/stats`
добавляем заголовки в каждый ответ `/quote`:

```
X-Visits: 42
X-Successes: 37
```

Клиент может читать метрики из любого успешного ответа.
Опционально `/stats` для чтения без запроса котировки.

**Затрагиваемые файлы:**
- **Изменения:** `src/server.mjs` — заголовки в функцию `send()`

**Плюсы:**
- Нет нового эндпоинта
- Метрики всегда доступны клиенту
- Интересный подход для отладки

**Минусы:**
- Заголовки видны клиенту — утечка метаданных
- Нестандартный API
- Мешает кэшированию (если будет)
- Нет отдельного способа читать без side-effect

**Усилия:** 1-2 часа

**Риски:** Средние — нетрадиционный подход, может запутать

---

### Концепт 5: «Не трогай» (External Observability)

**Суть:** Не внедрять счётчики в приложение, использовать внешние средства.

**Описание:**
Отказаться от внедрения метрик в код. Использовать:
- `strace`/`dtrace` для системных вызовов
- TCP-сниффер для подсчёта HTTP запросов
- Внешний прокси (nginx, haproxy) для метрик

**Затрагиваемые файлы:**
- **Никаких** — код не меняется

**Плюсы:**
- Ноль изменения кода
- Промышленные инструменты уже готовы
- Отделение наблюдаемости от бизнес-логики

**Минусы:**
- Не соответствует требованиям задачи (ФТ-1, ФТ-2, ФТ-3)
- Требует внешней инфраструктуры
- Нет доступа к значению «успешной транзакции» (только HTTP коды)
- Демо-стенд не настроен для этого

**Усилия:** 2-4 часа (настройка инфраструктуры)

**Риски:** Не соответствует задаче — скорее маркетинговый ответ

# Архитектурные дебаты

**Дата проведения:** 2026-08-21
**Метод:** 3 раунда структурированных дебатов (Архитектор vs Адвокат Дьявола)
**Цель:** Выбрать оптимальный концепт для реализации

---

## Раунд 1 — Защита

### Архитектор (защищает Концепт 2: Прагматичное)

**Выбор:** Концепт 2 (Closures in server.mjs)

**Аргументы:**

1. **Баланс скорости и качества**
   - 1-2 часа усилий vs 2-3 часа на Концепт 1
   - Замыкания дают инкапсуляцию без overhead нового модуля

2. **Соответствие архитектурным принципам проекта**
   - Доказательство: `src/pricing.mjs:1-3` — «Чистые функции без ввода-вывода»
   - Метрики — HTTP-слой concern, поэтому server.mjs — правильное место
   - pricing.mjs остаётся нетронутым (НФТ-2 выполнен)

3. **MVP-подход с путём эволюции**
   - Быстрый старт к рабочему решению
   - Легкий рефакторинг в Концепт 1 при росте требований:
   ```javascript
   // Текущий замыкание легко выносится в отдельный модуль
   const counters = (() => { /* ... */ })();
   // → export const counters = (() => { /* ... */ })();  // metrics.mjs
   ```

4. **Покрывает все ФТ и НФТ**
   - ФТ-1: инкремент visits на входе `/quote` (server.mjs:29)
   - ФТ-2: инкремент success после `quote()` (server.mjs:39)
   - ФТ-3: эндпоинт `/stats` для чтения
   - НФТ-1: только stdlib
   - НФТ-3: `/healthz` не затрагивается (server.mjs:27)

### Адвокат Дьявола (атакует Концепт 2)

**Критика 1: Тестируемость метрик**

- Замыкание в `server.mjs` невозможно протестировать изолированно
- Для тестов нужно поднимать HTTP-сервер — интеграционный, а не unit-тест
- Доказательство: `tests/*.test.mjs` — текущая схема тестирует `quote()` напрямую

**Критика 2: Смешение ответственности**

- `server.mjs` сейчас: HTTP-роутинг + разбор JSON + коды ответов
- Добавление: счётчики + эндпоинт `/stats`
- SRP нарушается: один модуль отвечает за太多 вещей

**Критика 3: Рост сложности при расширении**

- Требуется: separate counters для 400/500, тайминги, percentiles
- В Концепте 2: всё смешается в `server.mjs`, станет грязно
- Рефакторинг неизбежен — почему не сделать сразу?

**Критика 4: Неявное состояние**

- Замыкание `counters` создается при загрузке модуля
- При hot-reload в dev-режиме состояние теряется неявно
- Нет явного lifecycle: init → use → reset

## Раунд 2 — Пересмотр

### Архитектор (учитывает критику)

**Признание слабых мест:**

1. Тестируемость — Адвокат прав: unit-тесты на метрики невозможны
2. При росте требований — mixin в server.mjs станет проблемой

**Возможный пивот на Концепт 1?**

- Концепт 1 решает обе проблемы:
  - `src/metrics.mjs` → тестируется изолированно
  - Расширяемость: новые метрики → новые функции в том же модуле

**Но остаётся вопрос:**

- Для 2 счётчиков — это overengineering?
- 2-3 часа vs 1-2 часа — стоит ли дополнительные усилия?

**Проверка через what-if:**

> Что если через неделю PO попросит добавить counters для 400 и 500?

- Концепт 2: рефакторинг нужен, код уже "грязный"
- Концепт 1: добавляем `incError400()`, `incError500()` — чистое расширение

### Адвокат Дьявола (what-if сценарии)

**Сценарий 1: Расширение через месяц**

- Требуется:タイミги (p95, p99), отдельные счётчики по промокодам
- Концепт 2: `server.mjs` становится монстром на 200+ строк
- Концепт 1: `src/metrics.mjs` растёт органично, можно разделить на `src/metrics/*.mjs`

**Сценарий 2: Требование к персистентности**

- Требуется: экспорт метрик в Prometheus/StatsD
- Концепт 2: HTTP-слой contaminated с export-логикой
- Концепт 1: `src/metrics.mjs` → `src/metrics/exporters.mjs` — чистая граница

**Сценарий 3: Fork/Cluster deployment**

- Node.js cluster mode → разделяемые счётчики?
- Концепт 2: замыкание не шарится между воркерами
- Концепт 1: та же проблема, но модульная структура позволяет добавить shared state
- Адвокат признаёт: оба концепта требуют доработки для cluster

**Ключевой вопрос Адвоката:**

> Если мы знаем, что метрики будут расширяться, почему не построить правильную архитектуру с первого дня?

### Архитектор (ответ на what-if)

**Контекст проекта:**

- Это демо-стенд для обучения (`poh-demo-checkout`)
- Текущий codebase: 55 строк (server.mjs) + 83 строки (pricing.mjs)
- Задача: добавить счётчики, а не построить фреймворк метрик

**Реалистичная оценка:**

- Через месяц — проект может быть уже неактивен (демо-стенд)
- Если станет активным — рефакторинг в Концепт 1 займёт 30 минут, не 2 часа

**Но Архитектор признаёт:**

- Для production-сервиса Концепт 1 — очевидный выбор
- Для демо-стенда с непредсказуемым future — Концепт 2 достаточен
- **Однако**: если целью проекта является обучение clean architecture, то Концепт 1 правильнее

## Раунд 3 — Вердикт

### Финальная позиция Архитектора

**Признание:**

- Концепт 2 прагматичен для быстрого MVP
- Но Архитектор соглашается: Концепт 1 более robust для неизвестного будущего

**Пересмотр приоритетов:**

1. Тестируемость — критически важна (как в pricing.mjs)
2. Расширяемость — не "через полгода", а "через неделю" при росте
3. Чистая архитектура — обучение правильному подходу

**Новая позиция: Концепт 1**

### Финальная позиция Адвоката Дьявола

**Подтверждение:**

- Концепт 1 удовлетворяет всем критикам:
  - Unit-тесты на метрики изолированно
  - SRP: metrics.mjs → метрики, server.mjs → HTTP
  - Расширяемость: органический рост структуры

**Риски Концепта 1 признаны минимальными:**

- 2-3 часа усилий — приемлемо для качества
- Новый файл — не overhead, а правильная граница

### Итоговый вердикт

**Концепт 1 (Separated Metrics Module) — ПРИНЯТ**

**Обоснование:**

1. **Тестируемость:** метрики тестируются изолированно, как pricing.mjs
2. **Чистая архитектура:** явное разделение ответственности с первого дня
3. **Расширяемость:** готовность к росту требований без рефакторинга
4. **Соответствие проекту:** следует паттерну pricing.mjs (чистый модуль)

**Модификации к Концепту 1:**

1. **Структура metrics.mjs:**
   ```javascript
   export const counters = (() => {
     let visits = 0;
     let successes = 0;
     return {
       incVisit: () => { visits += 1; },
       incSuccess: () => { successes += 1; },
       get: () => ({ visits, successes })
     };
   })();
   ```
   Замыкание сохраняется, но вынесено в отдельный модуль.

2. **Тесты обязательны:** создание `tests/metrics.test.mjs` одновременно с кодом

3. **Documentation:** JSDoc на все функции metrics.mjs

**Отклонённые концепты:**

- **Концепт 2:** хорош для MVP, но уступает по тестируемости и расширяемости
- **Концепт 3:** техдолг, не соответствует стандартам качества проекта
- **Концепт 4:** нетрадиционный подход, усложняет API
- **Концепт 5:** не соответствует ФТ-1, ФТ-2, ФТ-3
