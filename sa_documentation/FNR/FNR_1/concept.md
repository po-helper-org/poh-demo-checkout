# FNR-1: Валидация Content-Type для POST /quote
## Концепты решений

---

## Контекст задачи

**Проблема:** Эндпоинт `POST /quote` не проверяет заголовок `Content-Type` перед попыткой парсинга JSON, что приводит к некорректному статусному коду (400 вместо 415) при отправке данных с неправильным типом контента.

**Зона воздействия:**
- `src/server.mjs:20-25` — функция `readJson()`
- `src/server.mjs:37-61` — обработчик `/quote`
- `tests/server.test.mjs:10-70` — helper-функция `request()`

**Ограничения:**
- Нельзя менять `src/pricing.mjs` (бизнес-логика не затронута)
- Нельзя менять другие эндпоинты (`/healthz`, `/stats`)
- Новые зависимости не заводятся
- Обратная совместимость обязательна

---

## Концепт 1: Выделенная функция валидации (Правильное)

**Суть:**

Вынести проверку Content-Type в отдельную чистую функцию `requireJsonContentType()`, которая выбрасывает ошибку с типом `UnsupportedMediaTypeError`. Обработчик `/quote` перехватывает этот специфический тип ошибки и возвращает 415.

**Изменения:**

| Файл | Изменения |
|------|-----------|
| `src/server.mjs` | Добавить функцию `requireJsonContentType(req)` |
| `src/server.mjs` | Добавить класс `UnsupportedMediaTypeError` |
| `src/server.mjs` | Модифицировать обработчик `/quote` |
| `tests/server.test.mjs` | Добавить параметр `headers` в `request()` |
| `tests/server.test.mjs` | Добавить 5 новых тестов |

**Плюсы:**
- Чистое разделение ответственности: валидация отдельно от парсинга
- Переиспользуемость: функция может быть применена к другим эндпоинтам в будущем
- Тестируемость: функция изолирована и легко тестируется
- Правильные коды статусов для всех сценариев
- Следует HTTP-семантике

**Минусы:**
- Требует больше строк кода
- Введение нового типа ошибки

**Усилия:** 1-2 часа

**Риски:** Низкие — изменение локализовано, существующие тесты сохранятся

---

## Концепт 2: Инлайн-проверка в обработчике (Прагматичное)

**Суть:**

Добавить проверку Content-Type непосредственно в обработчик `/quote` перед вызовом `readJson()`. При несоответствии сразу возвращать 415.

**Изменения:**

| Файл | Изменения |
|------|-----------|
| `src/server.mjs:37-61` | Добавить 3-4 строки проверки Content-Type |
| `tests/server.test.mjs:10-70` | Добавить параметр `headers` в `request()` |
| `tests/server.test.mjs` | Добавить 5 новых тестов |

**Плюсы:**
- Минимум изменений в коде
- Логика видна сразу в обработчике
- Нет новых абстракций
- Быстрая реализация

**Минусы:**
- Логика валидации смешана с обработкой
- Менее переиспользуемо для других эндпоинтов
- Сложнее тестировать валидацию изолированно

**Усилия:** 30-45 минут

**Риски:** Очень низкие — минимальное изменение

---

## Концепт 3: Проверка внутри readJson() (Быстрый костыль)

**Суть:**

Добавить проверку Content-Type внутрь функции `readJson()` и возвращать специальный объект/ошибку при несоответствии. Обработчик `/quote` интерпретирует это как 415.

**Изменения:**

| Файл | Изменения |
|------|-----------|
| `src/server.mjs:20-25` | Модифицировать `readJson()` |
| `src/server.mjs:37-61` | Обработка нового случая |
| `tests/server.test.mjs` | Добавить параметр `headers` в `request()` |
| `tests/server.test.mjs` | Добавить 5 новых тестов |

**Плюсы:**
- Изменение только в одном месте (readJson)
- Обработчик `/quote` почти не меняется

**Минусы:**
- Нарушение Single Responsibility: readJson теперь и парсит, и валидирует
- Функция перестаёт быть чистой (зависит от req.headers)
- Менее явное поведение: неудобно при чтении кода
- Проблемы с переиспользованием: если понадобится чтение JSON без валидации Content-Type

**Усилия:** 30 минут

**Риски:** Средние — смешение ответственности может усложнить future-proofing

---

## Концепт 4: Middleware-обёртка (Креативный хак)

**Суть:**

Создать функцию-обёртку `withJsonContentType(handler)`, которая проверяет Content-Type и вызывает переданный handler только при соответствии. Обработчик `/quote` оборачивается в эту функцию.

**Изменения:**

| Файл | Изменения |
|------|-----------|
| `src/server.mjs` | Добавить `withJsonContentType(handler, req, res)` |
| `src/server.mjs:37-61` | Применить обёртку к обработчику |
| `tests/server.test.mjs` | Добавить параметр `headers` в `request()` |
| `tests/server.test.mjs` | Добавить 5 новых тестов |

**Плюсы:**
- Декоративный паттерн: легко применяется к любому обработчику
- Чистое разделение: валидация изолирована в обёртке
- Масштабируется на другие эндпоинты

**Минусы:**
- Требует изменения сигнатуры обработчика или дополнительной индирекции
- Более сложная структура для простой задачи
- Может быть избыточным для одного эндпоинта

**Усилия:** 1-1.5 часа

**Риски:** Низкие — паттерн well-known, но может быть overhead для текущего scope

---

## Концепт 5: "Не трогай" (Статус-кво обоснование)

**Суть:**

Оставить текущее поведение без изменений.

**Аргументация:**

1. **Прагматика:** текущее поведение "работает" — клиенты с неправильным Content-Type всё равно получают понятное сообщение об ошибке, пусть и с кодом 400 вместо 415.

2. **Отсутствие реальных проблем:** в логах/метриках нет случаев, когда этот баг вызывал проблемы у пользователей.

3. **Принцип YAGNI:** никто не просил строгое соблюдение HTTP-семантики, изменение — чистое "technical debt" без бизнес-ценности.

4. **Риск breaking changes:** существующие клиенты могут полагаться на текущее поведение (например, парсить 400 как ошибку валидации).

**Против:**

- Нарушение HTTP-спецификации
- Неправильные коды статусов затрудняют интеграцию с HTTP-клиентами, которые могут обрабатывать 415 отдельно
- Технический долг accumulating

**Решение:** Принимается только если нет реальных обращений от пользователей и приоритет ниже P3.

---

## Рекомендация

**Рекомендуемый концепт:** Концепт 2 (Инлайн-проверка в обработчике)

**Обоснование:**

1. **Баланс простоты и корректности:** Минимальные изменения при правильном поведении
2. **Время реализации:** 30-45 минут — соответствует приоритету P2
3. **Понятность:** Логика видна непосредственно в месте использования
4. **Обратная совместимость:** Не ломает существующие workflow
5. **Тесты:** Покрытие всех граничных случаев обеспечивает уверенность

**Альтернатива для future-proofing:** Концепт 1 (Выделенная функция) — если планируется расширение API и добавление других JSON-эндпоинтов в ближайшем будущем.

# АРХИТЕКТУРНЫЕ ДЕБАТЫ: FNR-1 Валидация Content-Type

## Раунд 1 — Защита

### Архитектор (защищает Концепт 2: Инлайн-проверка)

**Выбор:** Концепт 2 (Инлайн-проверка в обработчике)

**Аргументы:**

1. **Принцип KISS для текущего scope** — в проекте всего один JSON-эндпоинт (`/quote`), два других (`/healthz`, `/stats`) — GET без body. См. `src/server.mjs:28-64` — всего 27 строк для всей обработки, включая error handling. Вводить абстракцию (Концепт 1) или middleware (Концепт 4) для одного места — overengineering.

2. **Локальность изменений** — инлайн-проверка добавляется только в `src/server.mjs:37-61`, то есть в 3-4 строки непосредственно перед вызовом `readJson()`. Существующая структура обработчика не меняется, минимизируется риск regression.

3. **Читаемость кода** — логика валидации видна сразу в месте использования:
```javascript
if (req.url === '/quote' && req.method === 'POST') {
  // ← Здесь будет проверка Content-Type
  if (!req.headers['content-type']?.startsWith('application/json')) {
    return send(res, 415, { error: 'ожидается Content-Type: application/json' });
  }
  // Продолжение существующей логики
```
При чтении кода обработчика не нужно прыгать к другой функции (Концепт 1) или middleware (Концепт 4).

4. **Обратная совместимость** — существующие клиенты, которые отправляют правильный Content-Type, не заметят изменений. Те, кто не отправляет его, начнут получать 415 вместо 400 — это корректное поведение по HTTP-спеке.

5. **Усилия 30-45 минут** — соответствует приоритету P2. Минимум кода → минимум тестов → быстрый merge.

### Адвокат Дьявола (атакует)

**Возражения:**

1. **Нарушение DRY и отсутствие масштабируемости** — инлайн-проверка копипастится. Если через 2 месяца появится второй JSON-endpoint (например, `POST /order`), проверку нужно будет продублировать. Это technical debt, который накопится.

2. **Смешивание ответственности** — в одном обработчике оказываются: маршрутизация, валидация Content-Type, парсинг JSON, бизнес-логика, обработка ошибок. См. `src/server.mjs:37-61` — там уже 4 разных ответственности. Добавление пятой делает код "god function" по mini-шкале.

3. **Тестируемость** — инлайн-логику сложнее тестировать изолированно. Для Концепта 1 можно написать unit-тест на `requireJsonContentType()` без поднятия всего обработчика. Для инлайн-версии нужен integration-тест через `app()`.

4. **Что если boundary изменится?** — Текущая задача говорит "только `/quote`", но это artifact постановки, а не закон природы. За 6 месяцев проект может evolve в полноценный API с 5-10 эндпоинтами. Тогда придётся рефакторить инлайн в abstraction — double work.

5. **Ошибка в оценке усилий** — 30 минут звучат optimistically. Нужно ещё: добавить параметр `headers` в `request()` в тестах (`tests/server.test.mjs:10-70`), написать 5 новых тестов, прогнать CI. Реально 1-1.5 часа.

## Раунд 2 — Пересмотр

### Архитектор (учитывает критику)

**Усиление аргументации:**

1. **По масштабируемости** — защита от overengineering сейчас важнее защиты от hypothetical future. Проект — demo-stand с 3 эндпоинтами, см. `.delivery/checks.json`: всего 4 проверки, одна из них POST. YAGNI: абстракция без второго случая — premature generalisation.

2. **По смешению ответственности** — обработчик `/quote` уже thin wrapper, см. `src/server.mjs:50-57`: вся бизнес-логика делегирована `quote()` из `pricing.mjs`. В обработчике осталась только glue-логика: разбор запроса и коды ответов. Добавление проверки Content-Type — это not_new_responsibility, а расширение существующей glue-логики.

3. **По тестируемости** — существующие тесты уже integration-уровня, см. `tests/server.test.mjs:10-70` — helper `request()` сразу мокает HTTP. Новый тест для 415 будет выглядеть так же, как существующие:
```javascript
test('POST /quote с text/plain возвращает 415', async () => {
  const res = await request('/quote', 'POST', 'text', { headers: { 'content-type': 'text/plain' } });
  assert.equal(res.statusCode, 415);
});
```
Разницы между unit и integration здесь нет — overhead одинаковый.

4. **По изменению boundary** — если API расширится, тогда появится естественное место для абстракции: не факт, что это будет `requireJsonContentType()`. Возможно, middleware-паттерн (Концепт 4) окажется лучше, или вообще framework (Express/Fastify). Abstraction now locks us into specific pattern before we know the shape of future.

5. **Пивот на Концепт 1?** — НЕ пивотим. Концепт 1 хуже для current scope: больше строк кода, новый класс ошибки (`UnsupportedMediaTypeError`), whomping complexity для одного эндпоинта. Концепт 2 — правильный balance простоты и корректности.

### Адвокат Дьявола (what-if проверки)

**Атаки на boundary conditions:**

1. **Что если существующий клиент НЕ отправляет Content-Type?** — См. `.delivery/checks.json`: все тесты используют `application/json`. Но production-traffic может отличаться. Если есть legacy-клиент без заголовка, он начнёт получать 415 вместо 400. Это breaking change?

2. **Что если порядок валидации важен?** — Текущий код в `src/server.mjs:40-46` ловит `JSON.parse()` ошибку и возвращает 400. Если мы добавим проверку Content-Type ДО `readJson()`, изменится порядок: Content-Type проверяется сначала. Это правильно по HTTP, но что если кто-то полагался на 400 для всех ошибок?

3. **Что если `readJson()` используется в другом контексте?** — См. `src/server.mjs:20-25`: функция `readJson()` чистая и переиспользуема. Концепт 3 модифицирует её, что breaks её чистоту. Но Концепт 2 не трогает `readJson()` — это plus.

4. **Что если приоритет P2 оправдан?** — Задача из issue #126, приоритет P2. Если это не fire, зачем abstraction? P2 = "следующий спринт", не "архитектура навсегда". Концепт 2 fits.

5. **What-if: тесты не покрывают edge cases?** — Концепт 2 требует добавления 5 тестов (см. `task.md:71-77`). Это минимум, чтобы убедиться, что: `application/json; charset=utf-8` проходит, `text/plain` падает, отсутствие заголовка падает. Без этих тестов refactor dangerous.

### Архитектор (ответ на what-if)

**Закрытие возражений:**

1. **По клиентам без Content-Type** — это баг текущего поведения. 400 вместо 415 — wrong по RFC 9110 Section 8.3. Если клиент полагается на 400, он уже broken relative к HTTP spec. Исправление — это не breaking change, а bugfix к compliance.

2. **По порядку валидации** — порядок correct: Content-Type проверяется ДО парсинга. Если Content-Type wrong, нет смысла пытаться парсить тело — это waste of CPU и misleading error message.

3. **По переиспользованию `readJson()`** — Концепт 2 сохраняет её чистоту. Концепт 3 делает её грязной, что плохо. Концепт 2 here is better than 3.

4. **По приоритету P2** — P2 = "fix before next release", но не "hack it". Концепт 2 proper fix без overengineering. Правильно.

5. **По тестам** — 5 тестов обязательны, это часть концепта. Без них acceptance criteria не met.

## Раунд 3 — Вердикт

### Итоговые позиции

**Архитектор:** Концепт 2 — оптимальный balance простоты, корректности и efforts для текущего scope. Не overengineer, не hack, proper fix.

**Адвокат Дьявола:** Концепт 2 acceptable IF:
- Добавлены все 5 тестов
- Нет планов расширения API в ближайшие 3 месяца
- Готовность к potential refactor если появится второй JSON-endpoint

**Отклонены концепты:**
- **Концепт 1:** overengineering для одного эндпоинта
- **Концепт 3:** нарушает чистоту `readJson()`
- **Концепт 4:** overhead для одного случая
- **Концепт 5:** HTTP compliance mandatory, не optional

### ВЕРДИКТ

**Принято:** Концепт 2 (Инлайн-проверка в обработчике)

**Условия принятия:**

2. Проверка Content-Type использует `startsWith('application/json')` для поддержки charset
3. Изменение локализовано в `src/server.mjs:37-61`
4. `request()` в тестах получает параметр `headers`

**Follow-up watch:** Если в ближайшие 3 месяца появится второй JSON-endpoint, рассмотреть рефактор на Концепт 1 или 4.
