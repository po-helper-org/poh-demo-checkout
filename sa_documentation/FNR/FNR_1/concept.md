# Концепты решений — FNR-1: Эндпоинт GET /healthz с временем работы процесса

**FNR ID:** FNR-1
**Дата генерации:** 2026-08-24
**Статус:** Черновик

---

## Краткое резюме задачи

Эндпоинт `GET /healthz` в текущей реализации (`src/server.mjs:28`) возвращает `{ ok: true }`, но требуется формат `{ status: "ok", uptime_sec: <целое> }`, где `uptime_sec` — число секунд с момента старта процесса.

---

## Концепт 1: Минимальное изменение (Правильное)

**Категория:** Правильное

### Суть решения

Однострочное изменение тела ответа в существующем обработчике + добавление специализированного теста для HTTP-эндпоинта.

### Реализация

**Изменения в `src/server.mjs:28`:**
```javascript
// Было:
if (req.url === '/healthz') return send(res, 200, { ok: true });

// Стало:
if (req.url === '/healthz') return send(res, 200, {
  status: 'ok',
  uptime_sec: Math.floor(process.uptime())
});
```

**Новый файл `tests/healthz.test.mjs`:**
```javascript
import assert from 'node:assert/strict';
import { test } from 'node:test';
import { createServer } from 'node:http';
import { app } from '../src/server.mjs';

test('GET /healthz возвращает статус и время работы', async () => {
  const server = createServer(app);
  const port = 0; // случайный свободный порт

  await new Promise(resolve => server.listen(port, resolve));

  const res = await fetch(`http://localhost:${server.address().port}/healthz`);
  const body = await res.json();

  assert.equal(res.status, 200);
  assert.equal(res.headers.get('content-type'), 'application/json; charset=utf-8');
  assert.equal(body.status, 'ok');
  assert.equal(typeof body.uptime_sec, 'number');
  assert.ok(Number.isInteger(body.uptime_sec));
  assert.ok(body.uptime_sec >= 0);

  server.close();
});
```

### Затрагиваемые компоненты

| Компонент | Тип воздействия |
|-----------|----------------|
| `src/server.mjs:28` | Изменение |
| `tests/healthz.test.mjs` | Добавление |

### Плюсы

- Минимальное изменение — одна строка
- Использует стандартный API `process.uptime()` — без новых зависимостей
- Соответствует архитектурным границам (логика остаётся тонкой)
- Покрывается тестом

### Минусы

- Нет (это эталонное решение)

### Оценка усилий

- **Время:** 15-30 минут
- **Сложность:** Низкая

### Риски

## Концепт 2: Выделение uptime-утилиты (Прагматичное)

**Категория:** Прагматичное

### Суть решения

Вынести логику расчёта uptime в отдельную утилиту, чтобы избежать дублирования, если uptime понадобится в других эндпоинтах (например, `/stats`).

### Реализация

**Новая утилита `src/health.mjs`:**
```javascript
export function getHealthStatus() {
  return {
    status: 'ok',
    uptime_sec: Math.floor(process.uptime())
  };
}
```

**Изменения в `src/server.mjs:28`:**
```javascript
import { getHealthStatus } from './health.mjs';

// В обработчике:
if (req.url === '/healthz') return send(res, 200, getHealthStatus());
```

**Тест в `tests/healthz.test.mjs`** — аналогичен Концепту 1, но также проверяет утилиту.

### Затрагиваемые компоненты

| Компонент | Тип воздействия |
|-----------|----------------|
| `src/health.mjs` | Добавление |
| `src/server.mjs:28` | Изменение |
| `tests/healthz.test.mjs` | Добавление |

### Плюсы

- Переиспользуемая утилита для потенциального будущего использования
- Логика health-статуса централизована
- Утилиту легко тестировать изолированно

### Минусы

- Заинженеривание для одного использования (YAGNI)
- Дополнительный файл ради одной функции

### Оценка усилий

- **Время:** 30-45 минут
- **Сложность:** Низкая

### Риски

### Затрагиваемые компоненты

## Концепт 4: «Не трогай» (Альтернативный взгляд)

**Категория:** «Не трогай»

### Суть решения

Признать текущий формат `{ ok: true }` допустимым и изменить требование спецификации, а не код.

### Обоснование

Формат `{ ok: true }` семантически эквивалентен `{ status: "ok" }`. Если потребителями API являются внутренние сервисы, можно договориться о формате `{ ok: true, uptime_sec: N }` — добавление поля не ломает обратную совместимость.

### Реализация

Изменение только в `src/server.mjs:28`:
```javascript
if (req.url === '/healthz') return send(res, 200, {
  ok: true,
  uptime_sec: Math.floor(process.uptime())
});
```

### Плюсы

- Сохраняет обратную совместимость по полю `ok`
- Меньше изменений в коде

### Минусы

- Не соответствует исходному требованию (поле `status`, а не `ok`)
- Дублирует смысловое поле (и `ok`, и `status`)

### Оценка усилий

- **Время:** 10 минут
- **Сложность:** Минимальная

### Риски

- Требование подтверждения от PO/Product

## Раунд 1: Защита

### Архитектор: Защита Концепта 1

Выбираю **Концепт 1 (Минимальное изменение)** как основной.

**Аргументы:**

1. **Соответствие архитектурным границам** — `src/server.mjs` — это тонкий HTTP-слой. Комментарий в [`src/server.mjs:1-2`](../../src/server.mjs:1-2) прямо говорит: «Тонкая намеренно: вся арифметика в pricing.mjs и проверяется без сети, здесь остаётся только разбор запроса и коды ответов». Вычисление `process.uptime()` — не бизнес-логика, а стандартный API Node.js, поэтому место ему — в обработчике, а не в отдельной утилите.

2. **Соблюдение принципа тестирования** — [`CLAUDE.md:59`](../../CLAUDE.md:59) требует: «Новая логика — новый тест». Концепт 1 добавляет специализированный тест `tests/healthz.test.mjs`, который проверяет именно HTTP-эндпоинт. Это следует паттерну существующего `tests/pricing.test.mjs`, который использует `node:test` + `node:assert/strict` ([`tests/pricing.test.mjs:1-2`](../../tests/pricing.test.mjs:1-2)).

3. **Отсутствие новых зависимостей** — [`CLAUDE.md:66`](../../CLAUDE.md:66) запрещает новые зависимости: «Зависимостей у сервиса нет. Новая заводится, только если задачу нечем закрыть из стандартной библиотеки». `process.uptime()` — встроенный API Node.js, никаких внешних пакетов не требуется.

4. **Минимальная зона изменения** — только одна строка в [`src/server.mjs:28`](../../src/server.mjs:28). Чем меньше меняем, тем ниже риск регрессии.

### Адвокат Дьявола: Атака на Концепт 1

**Контраргументы:**

1. **Смешивание форматирования и логики** — Текущая реализация возвращает `{ ok: true }`. Концепт 1 меняет это на `{ status: "ok", uptime_sec: N }`. Это не просто добавление поля — это изменение контракта. Если есть существующие потребители, которые проверяют `response.ok === true`, они сломаются. Обратная совместимость не учтена.

2. **Дублирование кода в будущем** — Что если в будущем понадобится добавить другие health-метрики? Например, `{ status: "ok", uptime_sec: N, memory_mb: M, version: "1.0" }`. Тогда Концепт 1 приведёт к раздуванию обработчика. Почему не выделить утилиту сейчас (Концепт 2)?

3. **Проблема тестирования HTTP-слоя** — Концепт 1 предлагает запускать реальный сервер на случайном порту через `createServer(app)`. Это интеграционный тест, а не юнит-тест. Он медленнее и может быть флактирным из-за занятости портов. Почему не мокнуть `req` и `res` напрямую?

4. **Концепт 4 не рассмотрен серьёзно** — Если формат ответа `{ ok: true }` уже существует в проде, может проблема в требованиях, а не в коде? Почему автоматически предполагать, что нужно менять код, а не спецификацию?

## Раунд 2: Пересмотр

### Архитектор: Ответ на критику

**По поводу обратной совместимости:**

Проверяю контекст. Из [`task.md:14-24`](./task.md) следует, что текущая реализация `{ ok: true }` — это демо-реализация от коммита `ca11525c` «feat: демо-стенд контура производства». Это **не прод**, а демо-стенд. Критерий приёмки в [`task.md:86-91`](./task.md) чётко требует `status: "ok"`, а не `ok: true`. Следовательно, обратная совместимость здесь не применима — мы исправляем несоответствие требованиям, а не сломанный прод-код.

**По поводу дублирования:**

Аргумент «а если в будущем понадобится» — это YAGNI (You Aren't Gonna Need It). [`CLAUDE.md:66`](../../CLAUDE.md:66) прямо говорит: логика в обёртке — это логика, которую тест не увидит. Если в будущем понадобится расширить `/healthz`, мы выделим утилиту тогда. Сейчас у нас один эндпоинт с одним полем — преждевременная абстракция (Концепт 2) усложняет код без реальной пользы.

**По поводу тестирования:**

Согласен, что интеграционный тест с `createServer` тяжелее юнит-теста. Но альтернативы хуже:
- Мокать `req` и `res` = тесная связка с внутренней реализацией `send()`. Любое изменение внутри `send()` сломает тест.
- Тестировать `process.uptime()` изолированно = не проверить именно HTTP-контракт.

Существующий `tests/pricing.test.mjs` проверяет чистые функции без сети. Для HTTP-эндпоинта нужен именно HTTP-тест. Паттерн из [`tests/pricing.test.mjs`](../../tests/pricing.test.mjs) — использовать `node:test` — сохраняется.

**По поводу Концепта 4:**

Концепт 4 предлагает изменить требования вместо кода. Но [`task.md:86-91`](./task.md) — это критерии приёмки, а не предложение. Продукт требует `status: "ok"`, а не `ok: true`. Менять требования = выход за scope задачи. Наша работа — реализовать требование, а не переформулировать его.

### Адвокат Дьявола: Проверка на слабые места

**Вопрос 1: Что если условие X изменится через полгода?**

Представьте: через 6 месяцев `/healthz` должен вернуть не только `uptime_sec`, но и `memory_mb`, `disk_usage_pct`, `version`. Концепт 1 приведёт к тому, что обработчик в `server.mjs` раздуется до 20 строк. Концепт 2 (утилита `getHealthStatus()`) был бы готов к этому. Не стоит ли заплатить небольшую цену сейчас (один дополнительный файл) ради гибкости в будущем?

**Ответ Архитектора:**

Через 6 месяцев мы увидим реальную потребность и выделим утилиту. Сейчас цена абстракции выше цены будущего рефакторинга. Принцип «Правь это дважды» (Rule of Three) говорит: выделяйте абстракцию, когда код повторяется **третий** раз, а не первый. У нас пока ноль повторений.

**Вопрос 2: Что если тест с портом будет флакать?**

Случайный порт `port = 0` обычно свободен, но на CI может быть race condition. Не лучше ли либить тест от порта через мок?

**Ответ Архитектора:**

Это валидное беспокойство. Но практика `node:test` + `createServer` для HTTP-тестирования — стандартная в Node.js. Если тест флакает, мы добавим ретраи или фиксированный порт с таймаутом. Проблема решаемая, а архитектурный риск — нет.

## Раунд 3: Вердикт

### Итоговая позиция Архитектора

**Остаётся при Концепте 1**. Причины:

1. Это минимальное изменение, которое точно соответствует требованиям.
2. Никаких premature abstractions — YAGNI соблюдён.
3. Тест покрывает реальный HTTP-контракт, а не моки.
4. Обратная совместимость не применима (это демо-стенд, не прод).
5. Архитектурные границы проекта соблюдены (тонкий HTTP-слой).

Концепт 2 (утилита) — это преждевременная абстракция для одного использования.
Концепт 3 (без теста) — нарушает принцип из [`CLAUDE.md:59`](../../CLAUDE.md:59).
Концепт 4 (менять требования) — выход за scope задачи.

### Итоговая позиция Адвоката Дьявола

Принимаю позицию Архитектора с оговоркой.

**Согласен с тем, что:**
- Обратная совместимость здесь не применима (демо-стенд).
- YAGNI важен — Концепт 2 преждевременно абстрагирует.
- Концепт 3 (без теста) неприемлем.

**Остающиеся беспокойства:**

Эти беспокойства не блокируют Концепт 1, но должны быть записаны как технический долг на случай осложнений.
