# Концепты решений для FNR-1

**Задача:** Пороговая скидка за объём заказа в `/quote`
**Дата:** 2025-08-19
**Файл:** `sa_documentation/FNR/FNR_1/concept.md`

---

## Резюме

Добавить логику скидки за объём заказа в эндпоинт `POST /quote` с тремя порогами:
- до 5000₽ — 0%
- 5000–15000₽ — 5%
- от 15000₽ — 10%

Ответ API должен включать поле `discount`, а `total` считать как `goods - discount + delivery`.

**Критическое ограничение:** Порог бесплатной доставки (`3000₽`) проверяется по `goods`, а не по `goods - discount`.

---

## Концепты

### 1. Правильное: Чистая функция `discountRate()` + расширение `quote()`

**Суть:**
Добавить чистую функцию `discountRate(amount)` в `pricing.mjs`, которая возвращает ставку скидки по порогам. Функция `quote()` вызывает `discountRate()`, вычисляет `discount = Math.floor(goods * rate)` и добавляет поле в ответ.

**Изменения:**
- `src/pricing.mjs`: добавить `discountRate()` и модифицировать `quote()`
- `tests/pricing.test.mjs`: тесты на границы порогов (0, 4999, 5000, 14999, 15000)

**Псевдокод:**
```javascript
// Новая функция в pricing.mjs
export function discountRate(amount) {
  if (amount >= 15000) return 0.10;  // 10%
  if (amount >= 5000) return 0.05;   // 5%
  return 0;                          // 0%
}

export function quote(items) {
  const goods = subtotal(items);
  const delivery = deliveryFee(goods);        // По goods, не по goods - discount!
  const discount = Math.floor(goods * discountRate(goods));
  return { goods, discount, delivery, total: goods - discount + delivery };
}
```

**Плюсы:**
- ✅ Чистая функция (тестируется без сети)
- ✅ Соответствует архитектуре (арифметика в `pricing.mjs`)
- ✅ Простая читаемость (`discountRate()` явно показывает пороги)
- ✅ Без новых зависимостей
- ✅ Легко менять пороги в будущем (одна функция)

**Минусы:**
- ⚠️ Меняет структуру ответа API (breaking change для клиентов, проверяющих число полей)

**Усилия:** 2–3 часа
**Риски:** Низкие — ограниченный API, демо-стенд без внешних клиентов

---

### 2. Прагматичное: Инлайн-логика в `quote()` без отдельной функции

**Суть:**
Не заводить отдельную функцию `discountRate()`, а вычислить скидку внутри `quote()` через тернарный оператор или `if`. Меньше кода, быстрее написать.

**Изменения:**
- `src/pricing.mjs`: модифицировать только `quote()`
- `tests/pricing.test.mjs`: те же тесты

**Псевдокод:**
```javascript
export function quote(items) {
  const goods = subtotal(items);
  const delivery = deliveryFee(goods);
  const rate = goods >= 15000 ? 0.10 : (goods >= 5000 ? 0.05 : 0);
  const discount = Math.floor(goods * rate);
  return { goods, discount, delivery, total: goods - discount + delivery };
}
```

**Плюсы:**
- ✅ Меньше кода (одна функция вместо двух)
- ✅ Быстрее написать
- ✅ Всё ещё чистая функция
- ✅ Без новых зависимостей

**Минусы:**
- ⚠️ Менее читаемо при изменении порогов
- ⚠️ Логика скидки "зашита" в `quote()`, трудно переиспользовать

**Усилия:** 1–2 часа
**Риски:** Низкие — для демо-стенда приемлемо

---

### 3. Быстрый костыль: Вычисление скидки в `server.mjs`

**Суть:**
Не трогать `pricing.mjs`, а посчитать скидку в HTTP-обёртке (`server.mjs`) после вызова `quote()`. Добавить поле `discount` в ответ перед отправкой.

**Изменения:**
- `src/server.mjs`: добавить логику скидки в обработчик `/quote`
- `tests/pricing.test.mjs` — **не покрывает** (логика в сети)

**Псевдокод:**
```javascript
// В server.mjs, обработчик /quote
const result = quote(body?.items);
const goods = result.goods;
const rate = goods >= 15000 ? 0.10 : (goods >= 5000 ? 0.05 : 0);
const discount = Math.floor(goods * rate);
return send(res, 200, {
  ...result,
  discount,
  total: goods - discount + result.delivery
});
```

**Плюсы:**
- ✅ Не трогает проверенную логику в `pricing.mjs`
- ✅ Быстро написать

**Минусы:**
- ❌ **Нарушает архитектуру**: арифметика в HTTP-слое
- ❌ **Не тестируется без сети**: логика скидки остаётся непокрытой
- ❌ Дублирует логику расчёта `total`
- ❌ Противоречит `AGENTS.md`: "логика в обёртке — логика, которую тест не увидит"

**Усилия:** 30–60 минут
**Риски:** Высокие — непокрытый код, нарушение архитектуры

---

### 4. Креативный хак: Константы-пороги в массиве, `find()`

**Суть:**
Вынести пороги в массив пар `[threshold, rate]` и искать ставку через `find()`. Позволяет легко добавлять пороги без изменения кода.

**Изменения:**
- `src/pricing.mjs`: добавить массив `DISCOUNT_TIERS` и функцию поиска
- `tests/pricing.test.mjs`: те же тесты

**Псевдокод:**
```javascript
// В pricing.mjs
export const DISCOUNT_TIERS = [
  [15000, 0.10],  // от 15000 — 10%
  [5000, 0.05],   // от 5000 — 5%
  [0, 0]          // по умолчанию — 0%
];

export function discountRate(amount) {
  const [, rate] = DISCOUNT_TIERS.find(([threshold]) => amount >= threshold);
  return rate;
}
```

**Плюсы:**
- ✅ Легко добавлять новые пороги (просто дописать в массив)
- ✅ Декларативно: пороги видны как данные
- ✅ Всё ещё чистые функции
- ✅ Без зависимостей

**Минусы:**
- ⚠️ Менее привычно для читающего код первый раз
- ⚠️ `find()` ищет сверху вниз, порядок важен (пороги должны быть по убыванию)

**Усилия:** 2–3 часа
**Риски:** Низкие — интересный подход, легко расширяемый

---

### 5. «Не трогать»: Не реализовывать

**Суть:**
Отказаться от реализации, сославшись на то, что демо-стенд не предназначен для реальной эксплуатации, а скидка — бизнес-логика, которая выходит за рамки "простого сервиса расчёта стоимости".

**Плюсы:**
- ✅ Никаких изменений в коде
- ✅ Нет рисков сломать существующую логику

**Минусы:**
- ❌ Игнорирует явную задачу из Issue #13
- ❌ Демо-стенд теряет демонстрационную ценность (не показывает полный цикл)
- ❌ Контур производства не проходит полный прогон

**Усилия:** 0 часов
**Риски:** Нулевые (но и пользы ноль)

## Рекомендация

**Для MVP и демо-стенда:** Концепт 1 (Правильное) — чистая функция `discountRate()` + расширение `quote()`.

**Почему:**
- Соответствует архитектуре (арифметика в `pricing.mjs`, тестируется без сети)
- Читаем и расширяем (легко добавить новые пороги)
- Покрывается тестами (критично для репозитория, где "расчёт — единственное, что может сломаться молча")
- Без зависимостей
- Порог доставки проверяется корректно (`deliveryFee(goods)` вызывается до расчёта скидки)

**Альтернатива:** Концепт 4 (Креативный) — если важна расширяемость порогов без изменения кода. Для демо-стенда избыточно, но интересный подход.

**НЕ推荐:** Концепт 3 — нарушает архитектуру и оставляет логику непокрытой тестами.

**Выбранный концепт для защиты:** Концепт 1 — Чистая функция `discountRate()` + расширение `quote()`

---

### Раунд 1: Защита

**Архитектор:**
Выбираю концепт 1 как наиболее соответствующий архитектуре проекта. Основные аргументы:

1. **Следует существующему паттерну:** В `pricing.mjs` уже есть `deliveryFee(amount)` — чистая функция с одним аргументом, возвращающая число. Добавление `discountRate(amount)` продолжает этот паттерн: одна ответственность, тестируемость без сети.

2. **Архитектурная граница соблюдена:** Согласно `CLAUDE.md`: "Арифметика — в `src/pricing.mjs`, чистыми функциями. `src/server.mjs` только разбирает запрос и отдаёт коды". Концепт 1 размещает расчёт скидки именно там, где указал архитектор проекта.

3. **Тестируемость:** Новая функция `discountRate()` покрывается теми же тестами, что и существующая логика — `tests/pricing.test.mjs`. Это критично, так как в репозитории указано: "Расчёт здесь единственное, что может сломаться молча".

4. **Проверка критического ограничения:** Вызов `deliveryFee(goods)` происходит **до** расчёта скидки (строки 49-50 в текущем коде), что гарантирует корректную проверку порога бесплатной доставки по `goods`, а не по `goods - discount`.

**Адвокат Дьявола:**
Принимаю выбор базового концепта, но нахожу слабые места:

1. **Breaking change без версии:** Добавление поля `discount` меняет структуру ответа API. Даже если демо-стенд не имеет внешних клиентов, это нарушает контракт. Как клиент поймёт, почему `total != goods + delivery`? Поле `discount` объясняет, но старый код, проверяющий равенство, сломается.

2. **Дублирование порогов:** Пороги скидки (5000, 15000) захардкожены в `discountRate()`. Через полгода бизнес захочет добавить новый порог или изменить ставки — придётся менять функцию. Почему не массив, как в концепте 4?

3. **Гранулярность тестов:** В concept.md указаны тесты на "границы порогов (0, 4999, 5000, 14999, 15000)". Но в `task.md` есть важный edge-кейс: `goods=3000, discount=300` → доставка должна быть 0. Покрывает ли концепт 1 этот сценарий явно, или полагается на side-effect?

4. **Округление:** `Math.floor(goods * rate)` для 4999.99 даст 249, а для 5000 — 250. Это ошибка округления или особенность бизнес-логики? Клиент с заказом на 4999.99₽ не получит скидку, хотя его "почти 5000". Не приведёт ли это к спорам?

---

### Раунд 2: Пересмотр

**Архитектор:**
Принимаю критику. Усиливаю аргументацию:

1. **По breaking change:** Это осознанный компромисс. Альтернатива — новая версия API `/v2/quote`, но для демо-стенда избыточно. Добавление поля в JSON обычно обратно совместимо: старые клиенты просто игнорируют неизвестное поле, а новые — используют его. Явная документация в `task.md` (сценарии 1-3) снижает риск.

2. **По дублированию порогов:** Справедливо. Концепт 4 (массив `DISCOUNT_TIERS`) решает эту проблему лучше. **Пивот:** предлагаю усилить концепт 1 идеей из концепта 4 — вынести пороги в константу-массив, но оставить простой код (не `find()`, а понятный цикл или прямая проверка). Это даст расширяемость без усложнения чтения.

3. **По edge-кейсам:** Сценарий с `goods=3000, discount=300` покрывается автоматически: `deliveryFee(goods)` вызывается с исходной суммой, скидка не влияет. Но вы прав — нужно добавить явный тест на этот случай в `pricing.test.mjs` как regression test.

4. **По округлению:** Это особенность, а не ошибка. `Math.floor()` — стандартное округление вниз в финансовых расчётах. Границы включительные (5000₽ → 5%) заданы бизнесом, а 4999.99₽ просто не попал в порог. Это documented behavior, а не баг.

**Адвокат Дьявола:**
Проверка гипотезы "что если":

1. **Условие X через полгода:** Бизнес захочет динамические пороги из базы. Массив `DISCOUNT_TIERS` не поможет — всё равно придётся перетаскивать в БД. Концепт 1 с простым `if/else` не хуже массива в этом смысле — оба потребуют рефакторинга.

2. **А что если `discountRate()` понадобится в другом месте?** Например, для превью скидки в корзине до оформления заказа. Сейчас `quote()` вызывается только из `/quote`, но в будущем — может и из UI. Выносить в отдельную функцию правильно.

3. **Производительность:** Для больших заказов (1000+ позиций) `subtotal()` уже делает `reduce()`. Добавление `discountRate()` — O(1), не влияет. Концепт 3 (вычисление в `server.mjs`) имел бы тот же O(1), но нарушал бы архитектуру.

4. **Последний удар:** В `CLAUDE.md` указано "Зависимостей у сервиса нет. Новая заводится, только если задачу нечем закрыть из стандартной библиотеки". Концепт 1 не требует зависимостей. Но концепт 4 с `find()` тоже стандартная библиотека. Почему не пивотнуть на концепт 4 полностью?

**Адвокат Дьявола (итоговая позиция):**
Принимаю концепт 1 с усилениями. Слабые места устранены:
- Breaking change задокументирован, для демо-стенда приемлем

Риски снижены до "низких". Концепты 2 (инлайн) и 3 (в server.mjs) уступают по читаемости и тестируемости. Концепт 4 интересен, но для демо-стенда избыточен — `find()` менее явно показывает пороги при чтении.
