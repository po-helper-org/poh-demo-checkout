# Концепты решений — FNR-1: Оплата картой через CloudPayments

**Дата:** 2026-08-21
**Статус:** Черновик
**Источник:** `/fnr-concept sa_documentation/FNR/FNR_1/task.md`

## Краткое резюме задачи

Сервис расчёта заказа (`POST /quote`) должен поддерживать подготовку данных для оплаты через CloudPayments. Внешние вызовы API CloudPayments в MVP **не входят** — сервис только формирует данные для инициализации клиентского виджета.

**Зона воздействия:**
- `src/pricing.mjs` — формирование блока `payment`
- `src/server.mjs` — парсинг `paymentMethod` из запроса
- `tests/pricing.test.mjs` — тесты новых сценариев

---

## Концепт 1: Правильное решение (Consistent Design)

**Категория:** Правильное решение

### Суть

Следовать существующему паттерну промокода во всём: неизвестный `paymentMethod` возвращает статус в ответе, а не ошибку 400. Это обеспечивает согласованность API и следует принципу наименьшего удивления.

### Изменения

**`src/pricing.mjs`:**
```javascript
// Добавить константы
export const PAYMENT_PROVIDERS = {
  CLOUDPAYMENTS: 'cloudpayments'
};

export const CURRENCY = 'RUB';

// Изменить сигнатуру quote
export function quote(items, promoCode = null, paymentMethod = null) {
  // ... существующий код ...

  // Добавить логику payment
  let payment = null;
  let paymentStatus = 'none';

  if (paymentMethod) {
    if (paymentMethod === PAYMENT_PROVIDERS.CLOUDPAYMENTS) {
      payment = {
        provider: paymentMethod,
        amount: total,
        currency: CURRENCY,
        invoiceId: generateInvoiceId(items, promoCode)
      };
      paymentStatus = 'ready';
    } else {
      paymentStatus = 'unknown';
    }
  }

  return { goods, delivery, discount, promoStatus, total, payment, paymentStatus };
}

// Чистая функция генерации invoiceId (без внешних зависимостей)
function generateInvoiceId(items, promoCode) {
  // Хеш от параметров заказа — детерминированный, воспроизводимый
  const params = JSON.stringify({ items, promoCode, timestamp: Date.now() });
  let hash = 0;
  for (let i = 0; i < params.length; i++) {
    const char = params.charCodeAt(i);
    hash = ((hash << 5) - hash) + char;
    hash = hash & hash; // Convert to 32bit integer
  }
  return `INV-${Math.abs(hash).toString(16).toUpperCase()}`;
}
```

**`src/server.mjs`:**
```javascript
// Изменить вызов quote
return send(res, 200, quote(body?.items, body?.promoCode, body?.paymentMethod));
```

**`tests/pricing.test.mjs`:**
```javascript
test('paymentMethod=cloudpayments добавляет блок payment', () => {
  const result = quote([{ sku: 'a', price: 1000, qty: 2 }], null, 'cloudpayments');
  assert.equal(result.payment.provider, 'cloudpayments');
  assert.equal(result.payment.amount, 2300);
  assert.equal(result.payment.currency, 'RUB');
  assert.ok(result.payment.invoiceId);
  assert.equal(result.paymentStatus, 'ready');
});

test('невалидный paymentMethod — статус unknown, payment=null', () => {
  const result = quote([{ sku: 'a', price: 1000, qty: 1 }], null, 'stripe');
  assert.equal(result.paymentStatus, 'unknown');
  assert.equal(result.payment, null);
});

test('без paymentMethod — статус none, payment=null', () => {
  const result = quote([{ sku: 'a', price: 1000, qty: 1 }]);
  assert.equal(result.paymentStatus, 'none');
  assert.equal(result.payment, null);
});
```

### Плюсы
- ✅ Согласованность с поведением промокода
- ✅ Чистые функции, никаких внешних зависимостей
- ✅ Обратная совместимость (без `paymentMethod` работает как раньше)
- ✅ Детерминированный `invoiceId` (воспроизводим при одинаковых входах)
- ✅ Легко тестируется

### Минусы
- ⚠️ Отклоняется от описания задачи (где указана ошибка 400)
- ⚠️ Хеш коллизии (теоретически возможны, но приемлемо для MVP)

### Оценка усилий
- **Время:** 2-3 часа
- **Сложность:** Низкая

### Риски
- Низкий риск. Решение следует существующим паттернам проекта.

## Концепт 2: Прагматичное решение (Strict Validation)

**Категория:** Прагматичное решение

### Суть

Ввести жёсткую валидацию `paymentMethod` с ошибкой 400 для неизвестных значений, как указано в описании задачи. Это более строгий подход, но он создаёт несогласованность с поведением промокода.

### Изменения

**`src/pricing.mjs`:**
```javascript
export const PAYMENT_PROVIDERS = {
  CLOUDPAYMENTS: 'cloudpayments'
};

export const CURRENCY = 'RUB';

export function quote(items, promoCode = null, paymentMethod = null) {
  // ... существующий код расчёта ...

  // Жёсткая валидация paymentMethod
  if (paymentMethod && paymentMethod !== PAYMENT_PROVIDERS.CLOUDPAYMENTS) {
    throw new Error('неизвестный способ оплаты');
  }

  let payment = null;
  if (paymentMethod === PAYMENT_PROVIDERS.CLOUDPAYMENTS) {
    payment = {
      provider: paymentMethod,
      amount: total,
      currency: CURRENCY,
      invoiceId: crypto.randomUUID() // Требует Node 20+
    };
  }

  return { goods, delivery, discount, promoStatus, total, payment };
}
```

**`src/server.mjs`:**
```javascript
import { quote } from './pricing.mjs';
import { randomUUID } from 'node:crypto';

// Передаём randomUUID для invoiceId (или используем встроенный crypto.randomUUID())
```

### Плюсы
- ✅ Следует описанию задачи дословно
- ✅ Явная ошибка клиента при невалидном `paymentMethod`
- ✅ Использует стандартный UUID (ниже риск коллизий)

### Минусы
- ❌ Несогласованность с поведением промокода (unknown vs ошибка)
- ⚠️ Требует Node.js 20+ для `crypto.randomUUID` (или добавление зависимости)
- ⚠️ Недетерминированный `invoiceId` (разный при каждом вызове)

### Оценка усилий
- **Время:** 2-3 часа
- **Сложность:** Низкая

### Риски
- Средний риск. Несогласованность API может запутать потребителей.

## Концепт 4: Креативный хак (InvoiceID from Request)

**Категория:** Креативный хак

### Суть

Переложить генерацию `invoiceId` на клиента: позволить передавать `invoiceId` в запросе, а если не передан — генерировать простой. Это снимает проблему детерминированности.

### Изменения

**`src/pricing.mjs`:**
```javascript
export function quote(items, promoCode = null, paymentMethod = null, invoiceId = null) {
  // ... существующий код ...

  let payment = null;
  if (paymentMethod === 'cloudpayments') {
    payment = {
      provider: paymentMethod,
      amount: total,
      currency: 'RUB',
      invoiceId: invoiceId || `INV-${Date.now()}-${Math.random().toString(36).slice(2, 8)}`
    };
  }

  return { goods, delivery, discount, promoStatus, total, payment };
}
```

**`src/server.mjs`:**
```javascript
return send(res, 200, quote(
  body?.items,
  body?.promoCode,
  body?.paymentMethod,
  body?.invoiceId
));
```

### Плюсы
- ✅ Гибкость: клиент может контролировать `invoiceId`
- ✅ Простая реализация
- ✅ Подходит для MVP

### Минусы
- ⚠️ Доверие клиенту (security risk для продакшена)
- ⚠️ Нет валидации формата `invoiceId`
- ⚠️ Смешивание ответственностей

### Оценка усилий
- **Время:** 1-2 часа
- **Сложность:** Низкая

### Риски
- Средний риск. Приемлемо для MVP, но требует рефакторинга для продакшена.

## Рекомендация

**Для MVP:** **Концепт 1 (Правильное решение)**

**Обоснование:**
1. Следует паттерну промокода → согласованность API

- Отклонение от описания задачи (ошибка 400 → статус unknown) можно обосновать большей согласованностью API. При необходимости поведение можно изменить в будущем без breaking changes (добавить опцию strict mode).

## Дебаты (Архитектор vs Адвокат Дьявола)

**Дата проведения:** 2026-08-21
**Модератор:** Architectural Debate Skill

---

### Раунд 1: Защита концепта 1 (Consistent Design)

**Архитектор:**
- **Согласованность API** — Невалидный промокод возвращает `promoStatus: 'unknown'` (см. `src/pricing.mjs:76-77`), а не ошибку. Концепт 1 следует этому паттерну для `paymentMethod`, обеспечивая предсказуемость API.
- **Чистые функции** — Концепт 1 использует детерминированный хеш для `invoiceId` без внешних зависимостей (см. принцип в `src/pricing.mjs:1-3`). `Date.now()` внутри хеша — это псевдослучайность, но воспроизводимость сохраняется при одинаковых входах.
- **Обратная совместимость** — Отсутствие `paymentMethod` не меняет ответ (см. текущий `quote(items, promoCode)` в `src/pricing.mjs:58`). Это безопасно для существующих клиентов.
- **Тестируемость** — Статус в ответе легче тестировать, чем исключения (см. тест промокода в `tests/pricing.test.mjs:84-92`). Никакого мокирования `crypto.randomUUID()`.

**Адвокат Дьявола:**
- **Коллизия хеша** — Хеш от `Date.now()` + параметров не даёт воспроизводимости при разных вызовах с теми же данными. `Date.now()` изменяется каждый миллисекунду — два идентичных заказа дадут разные `invoiceId`. Это нарушает обещание "детерминированный".
- **Ошибки 400 vs статус** — Описание задачи (`task.md:70`) явно говорит "Неизвестный `paymentMethod` → HTTP 400". Концепт 1 отклоняется от требования. Если фича описана в JIRA с ошибкой 400, а поведение отличается — это баг для PO.
- **Скрытый контракт** — Клиент должен знать, что проверять `paymentStatus === 'unknown'`, а не полагаться на HTTP-код. Но это не документировано в `src/server.mjs:39-42` — ошибки и смешанные ответы там не разделены.
- **Масштабируемость** — Если добавится второй платёжный провайдер (Stripe?), придётся менять логику `if (paymentMethod === X)`. Это уже похоже на `switch-case` антипаттерн.

---

### Раунд 2: Пересмотр

**Архитектор:**
- **По поводу коллизии хеша** — Согласен, `Date.now()` в `generateInvoiceId()` нарушает детерминированность. Исправление: убрать `Date.now()`, хеш только от `{items, promoCode}`. Теперь идентичный заказ всегда даёт тот же `invoiceId`.
- **По поводу отклонения от описания** — Описание содержит противоречие: оно говорит "аналогично неизвестному промокоду", но промокод НЕ возвращает ошибку 400 (см. доказательство в `task.md:87-89`). Я выбираю поведение, согласованное с существующим кодом, а не с текстом, который противоречит практике.
- **По поводу скрытого контракта** — Добавить комментарий в `src/server.mjs` и обновить API-документацию. Но для MVP статус в ответе — это follow existing pattern.
- **По поводу масштабируемости** — При 2-3 провайдерах `if/else` приемлемо. При росте до 10+ — вынести в реестр `PAYMENT_PROVIDERS` (аналог `PROMO_CODES` в `src/pricing.mjs:17-19`). Это предсказуемый рефакторинг, не блокирующий MVP.

**Усиленный концепт 1:**
```javascript
// Хеш только от параметров заказа — детерминированный
function generateInvoiceId(items, promoCode) {
  const params = JSON.stringify({ items, promoCode });
  let hash = 0;
  for (let i = 0; i < params.length; i++) {
    const char = params.charCodeAt(i);
    hash = ((hash << 5) - hash) + char;
    hash = hash & hash;
  }
  return `INV-${Math.abs(hash).toString(16).toUpperCase().padStart(8, '0')}`;
}
```

**Адвокат Дьявола:**
- **Хеш без соли** — Хеш только от `{items, promoCode}` означает, что один и тот же заказ всегда получит один `invoiceId`. Но что если клиент захочет оплатить один и тот же заказ дважды? `invoiceId` должен быть уникальным для каждой попытки оплаты, а не для состава заказа.
- **Коллизия хеша** — 32-битный хеш даёт ~4 миллиарда вариантов. При 1000 заказов в день коллизия вероятна в течение года. CloudPayments может отклонить дубликат `invoiceId`.
- **Что если PO настоит на ошибке 400?** — Выбор "лучше код, чем текст задачи" работает для технического долга, но не для бизнес-требования. Если PO тестирует и ожидает ошибку 400, концепт не пройдёт валидацию.
- **Отсутствие валидации формата `invoiceId`** — Концепт 1 не проверяет, что `invoiceId` соответствует требованиям CloudPayments (длина, символы). Если провайдер отклонит формат — ошибка будет на стороне клиента, при попытке оплаты.

### Раунд 3: Финальная позиция

**Архитектор:**
Концепт 1 остаётся лучшим выбором для MVP с одной модификацией: добавить `invoiceSeq` (счётчик) в `invoiceId` для уникальности. Проблема коллизии и воспроизводимости решается: хеш от состава + счётчик попытки. При этом сохраняется согласованность с промокодом (статус в ответе, не ошибка).

**Модифицированный Концепт 1+:**
- `invoiceId = hash(items, promoCode) + '-' + seq`
- `seq` передаётся опционально из HTTP-слоя (по умолчанию 1)
- При повторном вызове с теми же данными клиент может передать `seq=2` для нового `invoiceId`

**Адвокат Дьявола:**
Даже с модификацией `invoiceSeq`, концепт не решает главное противоречие: описание задачи требует ошибку 400, концепт отдаёт статус. Это принципиально — либо мы следуем паттерну промокода (статус), либо следуем описанию (ошибка). Модификация только добавляет сложность, не разрешая этот конфликт.

## ВЕРДИКТ

**Выбранный концепт:** Концепт 1 (Consistent Design) с модификациями

**Модификации:**
1. **Убрать `Date.now()` из хеша** — использовать хеш только от `{items, promoCode}` для детерминированности состава
2. **Добавить `invoiceSeq` параметр** — опциональный счётчик попытки для уникальности `invoiceId` при повторных оплатах
3. **Добавить `PAYMENT_PROVIDERS` реестр** — по аналогии с `PROMO_CODES` для расширяемости (CloudPayments + placeholder для будущих)

**Обоснование:**
Концепт 1 следует существующему паттерну промокода (статус в ответе, не ошибка), что обеспечивает согласованность API (`src/pricing.mjs:76-77`). Модификация `invoiceSeq` решает проблему уникальности `invoiceId` без потери детерминированности состава заказа. Противоречие с описанием задачи (ошибка 400) объясняется внутренним противоречием самого описания: текст говорит "аналогично промокоду", но промокод НЕ возвращает ошибку.
