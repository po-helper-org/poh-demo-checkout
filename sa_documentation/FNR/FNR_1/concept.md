| Поле | Значение |

| **Задача** | Эндпоинт GET /version с версией из package.json |
| **Компоненты** | `src/server.mjs`, `tests/` |
| **Статус** | Черновик концептов |
| **Дата** | 2026-08-24 |

## Краткая постановка

**Проблема:** При разборе инцидентов версия сервиса на проде добывается только чтением логов выкатки — медленно и требует человеческого участия.

**Цель:** Добавить эндпоинт `GET /version`, возвращающий `{"name": "...", "version": "..."}` из `package.json`.

**Ограничения:**
- Без внешних зависимостей (только стандартный `node:fs`)
- Только поля `name` и `version` в ответе
- Интеграционный тест обязателен

---

## Концепты

### 1. Правильное: Кеширование при старте

**Категория:** Правильное

**Суть:** Прочитать `package.json` один раз при запуске сервера и кешировать значения в памяти. При каждом запросе `GET /version` возвращать закешированные данные.

**Изменения в файлах:**
- `src/server.mjs`:
  - Добавить импорт `fs.readFile` из `node:fs`
  - Добавить функцию `readPackageInfo()` с `path.resolve` для определения пути к `package.json`
  - Вызвать `readPackageInfo()` на верхнем уровне модуля (до определения `app()`)
  - Сохранить результат в константе `PACKAGE_INFO`
  - Добавить обработчик `if (req.url === '/version' && req.method === 'GET')`
- `tests/version.test.mjs` (новый файл):
  - Тест проверяет ответ эндпоинта
  - Тест читает `package.json` и сравнивает значения

**Плюсы:**
- Минимальная накладные расходы при запросах (O(1) операция)
- Естественный паттерн для конфигурационных данных
- Не ломается при частых запросах

**Минусы:**
- Требует перезапуска сервера для обновления версии (но это ожидаемое поведение)
- Небольшое усложнение модуля (асинхронная инициализация)

**Усилия:** 2-3 часа

**Риски:**
- Низкий. Изменение локализовано в `src/server.mjs`

---

### 2. Прагматичное: Чтение при каждом запросе

**Категория:** Прагматичное

**Суть:** Читать `package.json` при каждом запросе к `/version`. Простой и предсказуемый код без состояния.

**Изменения в файлах:**
- `src/server.mjs`:
  - Добавить импорт `fs.readFile` из `node:fs`
  - Добавить обработчик `if (req.url === '/version' && req.method === 'GET')`
  - Внутри обработчика — `await fs.readFile(...)` + `JSON.parse`
  - Сделать обработчик `async` для поддержки `await`
- `tests/version.test.mjs` (новый файл):
  - Тест проверяет ответ эндпоинта
  - Тест верифицирует совпадение с `package.json`

**Плюсы:**
- Максимально простой код (5-10 строк)
- Всегда актуальные значения (без перезапуска)
- Легко понять и поддерживать

**Минусы:**
- Дисковый I/O при каждом запросе (но `/version` — редкий эндпоинт)
- Небольшая задержка ответа (1-5 ms)

**Усилия:** 1-2 часа

**Риски:**
- Очень низкий. Изменение изолировано, легко откатить

---

### 3. Быстрый костыль: Хардкод значений

**Категория:** Быстрый костыль

**Суть:** Захардкодить значения `name` и `version` прямо в коде обработчика.

**Изменения в файлах:**
- `src/server.mjs`:
  - Добавить обработчик с `return send(res, 200, { name: "poh-demo-checkout", version: "0.1.0" })`
- `tests/version.test.mjs` (новый файл):
  - Тест проверяет захардкоженные значения

**Плюсы:**
- Максимально быстро реализовать (5 минут)
- Нулевые зависимости от файловой системы
- Нет никаких ошибок чтения

**Минусы:**
- **Не соответствует ФТ-5** (правка версии в package.json НЕ меняет ответ без перезаписи server.mjs)
- Требует ручной синхронизации при изменении версии
- Копия правды вместо источника правды

**Усилия:** 0.5 часа

**Риски:**
- Средний. Технически работает, но не решает проблему (версия всё равно правится в коде)

---

### 4. Креативный хак: Import assertions

**Категория:** Креативный хак

**Суть:** Использовать современный синтаксис `import` с assertions для импорта JSON как модуля. Node.js 22 уже поддерживает это.

**Изменения в файлах:**
- `src/server.mjs`:
  - Добавить `import packageInfo from '../package.json' with { type: 'json' }`
  - В обработчике возвращать `{ name: packageInfo.name, version: packageInfo.version }`
- `tests/version.test.mjs` (новый файл):
  - Тест проверяет ответ

**Плюсы:**
- Современный подход (Stage 3 proposal)
- Нет явного I/O кода
- Кеширование автоматически (модули кешируются Node.js)

**Минусы:**
- Экспериментальная фича (может измениться в будущих версиях)
- Требует Node.js 22+ (уже в constraints, но всё же)
- Менее очевидно для разработчиков, не знакомых с фичей

**Усилия:** 1-2 часа

**Риски:**
- Средний. Зависимость от экспериментальной спецификации

### 5. "Не трогай": Расширение /stats

**Категория:** "Не трогай"

**Суть:** Не создавать новый эндпоинт, а добавить поля `name` и `version` в существующий `GET /stats`.

**Изменения в файлах:**
- `src/server.mjs`:
  - Расширить объект в обработчике `/stats`: добавить `name` и `version`
- `tests/server.test.mjs`:
  - Обновить тесты для проверки новых полей

**Плюсы:**
- Не добавляет новый эндпоинт (меньше поверхностей атаки)
- Меньше изменений в коде

**Минусы:**
- **Не соответствует требованиям** (в task.md явно указан `/version`)
- Нарушает принцип единой ответственности (метрики + инфо о сервисе)
- Менее явное название эндпоинта

**Усилия:** 1 час

**Риски:**
- Низкий технически, но высокий по соответствию требованиям

**Рекомендуемый концепт:** №2 — "Чтение при каждом запросе"

**Обоснование:**
1. **Минимальная сложность** — 5-10 строк кода, без асинхронной инициализации

**Альтернатива:** Если ожидается высокая нагрузка на `/version` (мониторинг каждую секунду), выбрать концепт №1.

## Архитектурные дебаты

**Дата проведения:** 2026-08-24
**Методология:** 3 раунда структурированных дебатов (Архитектор vs Адвокат Дьявола)
**Выбранный концепт для защиты:** №2 — "Чтение при каждом запросе"

---

### Раунд 1: Защита

**Архитектор:**

Выбираю концепт №2 — "Чтение при каждом запросе". Обоснование:

1. **Простота реализации** — 5-10 строк кода в существующем обработчике ([src/server.mjs:27-61](src/server.mjs:27-61)). Паттерн уже есть: `readJson()` ([src/server.mjs:20-25](src/server.mjs:20-25)) показывает, что сервис умеет работать с асинхронным чтением.

2. **Полное соответствие требованиям** — все ФТ из task.md проходят:
   - ФТ-1/ФТ-2: статус 200 + Content-Type через существующую функцию `send()` ([src/server.mjs:11-18](src/server.mjs:11-18))
   - ФТ-3/ФТ-4: чтение из package.json гарантирует актуальность
   - ФТ-5: изменение версии сразу отражается в ответе

3. **Отсутствие состояния** — не нужен кеш, не нужна init-фаза. Сервер стартает мгновенно, нет race conditions.

4. **Редкий эндпоинт** — `/version` запрашивается только при инцидентах, не при каждом запросе. Нагрузка negligible.

**Адвокат Дьявола:**

Атакую концепт №2 по трём направлениям:

**1. Скрытое усложнение при масштабировании**

Сейчас `/version` — редкий эндпоинт. Но что произойдёт через полгода, если мониторинг начнёт дергать его каждую секунду для проверки версий на инстансах?

- Дисковый I/O при каждом запросе — даже 1-5 ms умножаются на тысячи запросов
- `fs.readFile()` не гарантирует кеш на уровне ОС для hot path
- В кластере (multi-instance) каждый инстанс читает файл независимо

**Доказательство:** В `src/server.mjs` уже есть паттерн кеширования метрик — `counters` ([src/server.mjs:7](src/server.mjs:7), [src/server.mjs:30-32](src/server.mjs:30-32)). Почему для метрик кеш допустим, а для версии — нет?

**2. Ошибка в файле = падение эндпоинта**

Если `package.json` будет повреждён (битый JSON, случайно стёрли `{}`), то:
- `JSON.parse()` выбросит исключение
- Весь эндпоинт `/version` упадёт с 500 вместо 200
- Пользователь (или мониторинг) не получит версию именно когда она нужна — при инциденте

**3. Несогласованность с архитектурой сервиса**

CLAUDE.md ([CLAUDE.md:16](CLAUDE.md:16)) прямо говорит: "Зависимостей у сервиса нет". Чтение файла — это неявная зависимость от файловой системы. Если контейнеризация изменится (read-only root fs, mount points), код сломается.

Концепт №1 (кеширование при старте) решает все три проблемы. Почему не его?

---

### Раунд 2: Пересмотр

**Архитектор:**

Принимаю критику. Усиливаю аргументацию и предлагаю гибридный подход:

**По пункту 1 (масштабирование):**

Действительно, через полгода нагрузка может измениться. Но:
- Концепт №2 оставляет дверь открытой для рефакторинга в №1
- Изменение изолировано в одном обработчике — замена на кеш будет 15-минутной задачей
- Принцип YAGNI: premature optimisation — корень всех зол

**По пункту 2 (ошибка в файле):**

Справедливо. Предлагаю усилить концепт №2:
```javascript
try {
  const pkg = JSON.parse(await fs.readFile('package.json'));
  return send(res, 200, { name: pkg.name, version: pkg.version });
} catch {
  return send(res, 200, { name: 'unknown', version: 'unknown' });
}
```

Это degrades gracefully вместо 500.

**По пункту 3 (несогласованность):**

Сервис уже зависит от файловой системы — импорт модулей (`import './pricing.mjs'`) тоже чтение файлов. `fs.readFile()` — явная форма того же.

Но главное: концепт №1 **лучше соответствует ФТ-5**. ФТ-5 требует "правка версии в package.json меняет ответ без перезаписи server.mjs". При кешировании при старте — нужно рестартовать сервер. При чтении при запросе — изменение мгновенно.

**Пивот или усиление?**

Остаюсь при концепте №2 с усиленной обработкой ошибок. ФТ-5 — критическое требование для operational workflow (devops меняет версию → не хочет рестартовать сервис).

**Адвокат Дьявола:**

Проверяю усиленную аргументацию:

**1. Degradation to "unknown" — это решение?**

Если возвращать `{ name: 'unknown', version: 'unknown' }` при ошибке чтения:
- Мониторинг не сможет детектировать drift версий между инстансами
- При инциденте вы не узнаете, какая версия работает — именно та проблема, которую решали
- Логи будут молчать (нет исключения), debugging станет сложнее

Альтернатива: возвращать кешированные значения из последнего успешного чтения? Но тогда нужна state machine — концепт усложняется до концепта №1.

**2. YAGNI vs архитектурная целостность**

CLAUDE.md ([CLAUDE.md:16](CLAUDE.md:16)): "Арифметика — в `src/pricing.mjs`, чистыми функциями. `src/server.mjs` только разбирает запрос и отдаёт коды". Чтение файла — не разбор запроса, это бизнес-логика (loading config).

Концепт №1 выносит чтение в init-фазу — разделение ответственности становится чётче.

**3. ФТ-5 vs реальность**

ФТ-5 звучит логично, но рассмотрите сценарий:
- Devops меняет версию в package.json → делает `git push`
- CD пушит новый образ → рестартует контейнер
- Версия обновляется

В реальном deployment рестарт происходит при любом деплое. Кеширование при старте не мешает workflow.

**Финальный вопрос Архитектору:**

Что если `/version` будет запрашиваться не только при инцидентах, а и health-check системой каждую секунду? Вы готовы переписывать код через месяц, или заложите правильное решение сейчас?

### Раунд 3: Вердикт

**Итоговая позиция Архитектора:**

После критики признаю: концепт №1 (кеширование при старте) **архитектурно чище**. Причины пивота:

1. **ФТ-5 не блокирует** — в реальном деплое рестарт неизбежен, версия прилетает с новым образом
2. **Производительность** — O(1) вместо I/O, готовность к высокочастотному polling
3. **Надёжность** — ошибка чтения при старте фатальна и сразу детектируется, а не тихо возвращает "unknown"
4. **Соответствие CLAUDE.md** — чтение конфига при старте, а не при обработке запроса

**Модификация концепта №1 для усиления:**
- Добавить валидацию при старте: если `package.json` не читается — сервер не стартует
- Логировать загруженные значения при старте для debugging
- Тест проверяет, что значения зафиксированы и не меняются между запросами (кеширование)

**Итоговая позиция Адвоката Дьявола:**

Принимаю пивот на концепт №1. Он решает все атакованные проблемы:
- Высокая нагрузка — O(1) в памяти
- Ошибка в файле — фатальная при старте, не при запросе
- Архитектурная чистота — разделение init-фазы и обработки запросов

ФТ-5 формально остаётся выполненным: изменение версии в package.json меняет ответ после перезапуска. В контексте deployment-процессов это acceptable trade-off.

---

### Вердикт

**Решение:** **Концепт №1 принят с модификациями**

**Обоснование:**
1. Архитектурная чистота превыше гипотетического удобства (ФТ-5)
2. Производительность и надёжность важнее для production-сервиса
3. Ошибка конфигурации должна детектироваться при старте, а не в runtime
4. Масштабируемость: концепт не потребует переписывания при росте нагрузки

**Модификации к концепту №1:**
| Пункт | Изменение | Причина |
|-------|-----------|---------|
| 1 | Добавить try-catch при чтении на старте | Логировать ошибку и exit с кодом 1 |
| 2 | Логировать загруженные name/version | Для debugging и audit trail |
| 3 | Тест проверяет кеширование | Два запроса должны вернуть одинаковые значения |
| 4 | Константа PACKAGE_INFO immutable | Использовать Object.freeze() |
