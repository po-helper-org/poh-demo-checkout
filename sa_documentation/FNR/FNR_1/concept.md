## Категория 1: Правильное решение (Minimal Viable Architecture)

**Суть:** Добавить минимально необходимую архитектуру для промо-кодов без излишней абстракции, но с возможностью расширения.

**Изменения:**

### `src/pricing.mjs`

```javascript
// Константа для промо-кодов (можно вынести в env в будущем)
export const PROMO_CODES = {
  WELCOME10: 0.10,  // 10%
  // можно добавить другие коды
};

/**
 * Применяет скидку по промо-коду.
 * @param {number} goodsAmount — сумма товаров
 * @param {string} promoCode — код промо
 * @returns {number} — сумма скидки
 * @throws {Error} — если код неизвестен
 */
export function applyPromo(goodsAmount, promoCode) {
  if (!(promoCode in PROMO_CODES)) {
    throw new Error(`неизвестный промо-код: ${promoCode}`);
  }
  const discount = goodsAmount * PROMO_CODES[promoCode];
  return Math.floor(discount); // рубли — целые
}

/**
 * Итог заказа с учётом промо-кода.
 * @param {Item[]} items
 * @param {string} [promoCode] — опциональный промо-код
 */
export function quote(items, promoCode) {
  const goods = subtotal(items);
  const delivery = deliveryFee(goods); // порог от goods ДО скидки

  if (promoCode === undefined) {
    return { goods, delivery, total: goods + delivery };
  }

  const discount = applyPromo(goods, promoCode);
  return { goods, delivery, discount, total: goods + delivery - discount };
}
```

### `src/server.mjs`

```javascript
if (req.url === '/quote' && req.method === 'POST') {
  // ... разбор JSON
  try {
    return send(res, 200, quote(body?.items, body?.promo));
  } catch (err) {
    return send(res, 400, { error: err.message });
  }
}
```

### `tests/pricing.test.mjs`

Добавить тесты:
- `applyPromo()` с известным кодом → скидка
- `applyPromo()` с неизвестным кодом → ошибка
- `quote()` с promo → включает `discount`
- Порог доставки от `goods` до скидки (заказ 3000₽ с 10% скидкой → доставка 0)

**Плюсы:**
- ✅ Архитектура допускает добавление кодов без правки кода (если вынести `PROMO_CODES` в env/config)
- ✅ Тесты покрывают все ветки
- ✅ Следует принципам репозитория (чистые функции, тесты)
- ✅ Понятное расширение: можно добавить типы скидок (фиксированная сумма, "купон на X₽")

**Минусы:**
- ❌ Жёстко задаёт тип скидки (процент от goods) — для других типов нужен рефакторинг
- ❌ Нет истории/аналитики использования промо-кодов (но это не MVP)

**Усилия:** 2-3 часа

**Риски:** Низкие — изменения локализованы и следуют существующей структуре

## Категория 2: Прагматичное решение (Inline-подход)

**Суть:** Минимум изменений — промо-коды только как процент скидки, без отдельной функции `applyPromo()`.

**Изменения:**

### `src/pricing.mjs`

```javascript
export const PROMO_CODES = {
  WELCOME10: 0.10,
};

export function quote(items, promoCode) {
  const goods = subtotal(items);
  const delivery = deliveryFee(goods);
  let discount = 0;

  if (promoCode !== undefined) {
    if (!(promoCode in PROMO_CODES)) {
      throw new Error(`неизвестный промо-код: ${promoCode}`);
    }
    discount = Math.floor(goods * PROMO_CODES[promoCode]);
  }

  return { 
    goods, 
    delivery, 
    ...(promoCode && { discount }), // включаем только если был promo
    total: goods + delivery - discount 
  };
}
```

### `src/server.mjs`

Так же, как в Правильном решении.

### `tests/pricing.test.mjs`

Только интеграционные тесты для `quote()` — без отдельной проверки `applyPromo()`.

**Плюсы:**
- ✅ Меньше кода — меньше мест для ошибки
- ✅ Быстрее реализации
- ✅ Логика в одном месте — легче читать

**Минусы:**
- ❌ Нет отдельной функции для тестирования механики скидки
- ❌ Если типов скидок станет >1 — нужен рефакторинг
- ❌ Условный spread `...(promoCode && { discount })` может быть менее читаемым

**Усилия:** 1-2 часа

**Риски:** Низкие — но менее модульная структура

## Категория 3: Быстрый костыль (Env-only)

**Суть:** Промо-коды только через переменную окружения — без валидации в коде. HTTP-уровень валидирует код, передаёт скидку как число.

**Изменения:**

### `src/pricing.mjs`

```javascript
export function quote(items, discountPercentage = 0) {
  const goods = subtotal(items);
  const delivery = deliveryFee(goods);
  const discount = Math.floor(goods * discountPercentage);
  return { goods, delivery, discount, total: goods + delivery - discount };
}
```

### `src/server.mjs`

```javascript
// Проверка промо-кода на HTTP-уровне
const PROMO_CODES = {
  WELCOME10: 0.10,
};

if (req.url === '/quote' && req.method === 'POST') {
  // ... разбор JSON
  let discount = 0;
  if (body?.promo) {
    if (!(body.promo in PROMO_CODES)) {
      return send(res, 400, { error: `неизвестный промо-код: ${body.promo}` });
    }
    discount = PROMO_CODES[body.promo];
  }
  return send(res, 200, quote(body?.items, discount));
}
```

**Плюсы:**
- ✅ `pricing.mjs` не зависит от конкретных кодов — легко тестировать
- ✅ HTTP-уровень уже валидирует — логично там же хранить коды

**Минусы:**
- ❌ Бизнес-логика (промо-коды) размазана по слоям
- ❌ Тесты `pricing.mjs` не покрывают валидацию промо-кодов
- ❌ `PROMO_CODES` в `server.mjs` — не тестируется без поднятия HTTP

**Усилия:** 1 час

**Риски:** Средние — нарушение принципа "арифметика в чистых функциях"

## Категория 4: «Не трогать» (Отказ от изменения)

**Суть:** Не реализовывать промо-коды в коде сервиса. Скидка считается на стороне клиента (фронтенд) или в переписке, а сервис отправляет только базовый расчёт.

**Обоснование:**

Текущий контракт `POST /quote` возвращает `{goods, delivery, total}`. Клиент может:
- Показать пользователю базовую сумму
- Применить скидку на фронтенде
- Отправить итог на оплату с учётом скидки

**Изменения:** Никаких.

**Плюсы:**
- ✅ Ноль рисков поломки существующего кода
- ✅ Не усложняет сервис
- ✅ Гибкость для разных типов скидок на клиенте

**Минусы:**
- ❌ Нет единого источника правды для скидок
- ❌ Разные клиенты могут считать скидку по-разному
- ❌ Невозможно гарантировать, что скидка применена корректно
- ❌ Противоречит требованию задачи (промо-коды "обещаны продавцам")

**Усилия:** 0 часов

**Риски:** Отсутствуют — но решение не соответствует бизнес-требованию

## Рекомендация

**Для MVP:** Прагматичное решение (Категория 2)

**Обоснование:**
1. Следует принципам репозитория — чистые функции, тесты
2. Минимальные изменения — меньше рисков
3. Покрывает требования HowToDemo полностью
4. Допускает расширение до Категории 1 (Правильное решение) в будущем

## Дебаты (Архитектор vs Адвокат Дьявола)

### Раунд 1: Защита концепта

**Архитектор defends: Прагматичное решение (Категория 2)**

**Архитектор:**
- **Минимальные изменения** — логика остаётся в `quote()`, одна точка входа для расчёта — доказательство: `src/pricing.mjs:25` (текущая `quote()` уже центрирует логику)
- **Следует существующей структуре** — чистые функции в `pricing.mjs`, HTTP-обёртка в `server.mjs` — доказательство: `src/server.mjs:2` комментарий подтверждает разделение ответственности
- **Покрывает MVP полностью** — HowToDemo из `task.md:97-109` проходит без дополнительных абстракций
- **Допускает расширение** — при необходимости можно выделить `applyPromo()` без переделки всей архитектуры

**Адвокат Дьявола:**
- **Отсутствует отдельная функция для тестирования** — логика скидки смешана с `quote()`, нельзя протестировать механику скидки независимо от структуры заказа — обоснование: при добавлении второго типа скидки (фиксированная сумма) `quote()` разрастётся и станет трудночитаемой
- **Условный spread `...(promoCode && { discount })`** — менее читаем, чем явное условие — обоснование: при отладке неочевидно, когда `discount` появляется в ответе
- **Нет расширяемости для правил скидок** — при добавлении "минимальная сумма заказа для скидки" или "только для определённых SKU" понадобится рефакторинг всей `quote()` — обоснование: текущий концепт не предполагает конфигурацию правил

**Архитектор (ответ на критику):**
- **Насчёт тестирования** — интеграционные тесты `quote()` покрывают весь путь, включая механику скидки — доказательство: `tests/pricing.test.mjs:52` уже тестирует `quote()` полностью
- **Насчёт условного spread** — можно заменить на явное условие для читаемости
- **Насчёт расширяемости** — это MVP, когда появятся новые типы скидок, выделится `applyPromo()` по необходимости

### Раунд 2: Пересмотр

**Архитектор:**
- **Усиление концепта:** заменить условный spread на явное условие для читаемости:
  ```javascript
  const result = { goods, delivery };
  if (promoCode !== undefined) result.discount = discount;
  result.total = goods + delivery - discount;
  return result;
  ```
- **Дополнение:** добавить JSDoc-комментарий с указанием, что при расширении типов скидок следует выделить `applyPromo()`

**Адвокат Дьявола:**
- **Проверка усиленного варианта:** явное условие решает читаемость, но основной риск остаётся — при росте типов скидок (>2 типов) `quote()` станет "god function"
- **А что если через полгода появится:** "скидка 10% только для товаров категории X" — это потребует передавать в `quote()` контекст категорий, и функция разрастётся ещё больше
- **А что если промо-кодов станет >10:** хардкод в `PROMO_CODES` станет неудобен, потребуется конфигурация из env или базы — тогда логика валидации всё равно выйдет за пределы `quote()`

**Архитектор (пивот):**
- Признание риска: при >2 типов скидок или >10 кодов прагматичный подход не масштабируется
- **Предложение:** для MVP оставить прагматичный подход, но сразу заложить структуру для миграции к Правильному решению (Категория 1):
  - Добавить константу `PROMO_CODES` как "точка расширения" — можно будет вынести в env без переделки `quote()`
  - Добавить комментарий в код: "TODO: вынести в config при >5 кодов"
  - Добавить тест-фикстуру для проверки неизвестного кода — это основа для будущего `applyPromo()`

**Адвокат Дьявола:**
- Проверка пивота: TODO-комментарий не гарантирует, что рефакторинг будет сделан при росте кода — это может быть забыто
- Лучше сразу заложить структуру для Правильного решения, добавив `applyPromo()` как отдельную функцию — усилия минимальны (+30 минут), но архитектура готова к расширению

### Раунд 3: Финальная позиция

**Архитектор:**
Прагматичный подход с усилениями (явное условие + TODO + структура для миграции) достаточен для MVP и следует принципам репозитория. При росте >2 типов скидок или >10 кодов будет сделан пивот на Правильное решение.

**Адвокат Дьявола:**
Прагматичный подход несёт риск техдолга при росте типов скидок. Рекомендуется либо сразу Правильное решение (усилия на 30-60 минут больше), либо чёткий критерий пивота с автоматическим напоминанием (Issue/SubIssue при достижении порога).
