# FNR-1: Концепты решений

## Дата создания
2026-08-20

## Исходная задача
**FNR-1: Минимальная сумма заказа для оформления**

Система расчёта стоимости заказа не блокирует оформление заказов с суммой товаров ниже установленного порога, что приводит к приёму убыточных мелких заказов.

---

## Анализ пространства решений

### Текущее состояние
- **Точка внедрения**: `src/pricing.mjs:48-52` — функция `quote()`
- **Паттерн валидации**: выброс `Error` с сообщением на русском
- **HTTP-обработка**: уже существует в `server.mjs:42-45` → автоматически превращает Error в HTTP 400
- **Существующие константы**: `DELIVERY_FEE = 300`, `FREE_DELIVERY_FROM = 3000`

### Ограничения
- **Зависимости**: новые не заводятся (свойство проекта)
- **Архитектура**: арифметика — в `pricing.mjs`, HTTP — в `server.mjs`
- **Тесты**: новая логика — новый тест

---

## Варианты решений

### Концепт 1: Правильное — Базовая константа

**Суть:** Добавить константу `MIN_ORDER_AMOUNT` и проверку в `quote()` после вычисления `goods`.

**Изменения:**

| Файл | Что меняется |
|------|--------------|
| `src/pricing.mjs` | Добавить `export const MIN_ORDER_AMOUNT = <N>;` после строки 9 |
| `src/pricing.mjs` | Добавить проверку в `quote()`: `if (goods < MIN_ORDER_AMOUNT) throw new Error(...)` |
| `tests/pricing.test.mjs` | Добавить тест на валидацию минимальной суммы |

**Плюсы:**
- Следует существующему паттерну констант (`DELIVERY_FEE`, `FREE_DELIVERY_FROM`)
- Минимальные изменения — только одна функция
- Легко тестировать
- Сообщение об ошибке может указывать точную недостающую сумму

**Минусы:**
- Порог захардкожен — требует деплоя для изменения
- Не решает вопрос выбора значения порога

**Усилия:** ~30 минут

**Риски:**
- Неверное значение порога при первом коммите
- Возможная регрессия в расчётах

**Код:**
```javascript
// src/pricing.mjs
export const MIN_ORDER_AMOUNT = 1000; // после FREE_DELIVERY_FROM

export function quote(items) {
  const goods = subtotal(items);
  if (goods < MIN_ORDER_AMOUNT) {
    throw new Error(`минимальная сумма заказа ${MIN_ORDER_AMOUNT}, не хватает ${MIN_ORDER_AMOUNT - goods}`);
  }
  const delivery = deliveryFee(goods);
  return { goods, delivery, total: goods + delivery };
}
```

### Концепт 2: Прагматичное — Конфигурируемая через env

**Суть:** Порог задаётся переменной окружения, с дефолтным значением.

**Изменения:**

| Файл | Что меняется |
|------|--------------|
| `src/pricing.mjs` | Добавить `const MIN_ORDER_AMOUNT = Number(process.env.MIN_ORDER_AMOUNT || 1000);` |
| `src/pricing.mjs` | Проверка аналогично Концепту 1 |
| `tests/pricing.test.mjs` | Тесты на валидацию с разными значениями |
| `.github/workflows/ci.yml` | Опционально: добавить тест с другим значением |

**Плюсы:**
- Гибкость — можно изменить без деплоя (в Kubernetes/Docker)
- Дефолтное значение — безопасное на случай отсутствия env
- Следует паттерну `PORT` в `server.mjs`

**Минусы:**
- Легче сломать конфигом, чем кодом
- Env видна во всём процессе, а не только в модуле (но это приёмлемо для константы)
- Тесты должны учитывать variadic behaviour

**Усилия:** ~45 минут

**Риски:**
- Некорректное значение в env (не число, отрицательное)
- Разное поведение в разных окружениях при неявной конфигурации

**Код:**
```javascript
// src/pricing.mjs
const MIN_ORDER_AMOUNT = Number(process.env.MIN_ORDER_AMOUNT || 1000);
if (!Number.isFinite(MIN_ORDER_AMOUNT) || MIN_ORDER_AMOUNT <= 0) {
  throw new Error('некорректная конфигурация MIN_ORDER_AMOUNT');
}

export function quote(items) {
  const goods = subtotal(items);
  if (goods < MIN_ORDER_AMOUNT) {
    throw new Error(`минимальная сумма заказа ${MIN_ORDER_AMOUNT}, не хватает ${MIN_ORDER_AMOUNT - goods}`);
  }
  // ...
}
```

### Концепт 3: Быстрый костыль — Встроить в `subtotal()`

**Суть:** Добавить параметр `minAmount` в `subtotal()` и проверять там же.

**Изменения:**

| Файл | Что меняется |
|------|--------------|
| `src/pricing.mjs` | Добавить параметр `minAmount` в `subtotal()` |
| `src/pricing.mjs` | Вызов `subtotal(items, MIN_ORDER_AMOUNT)` в `quote()` |
| `tests/pricing.test.mjs` | Обновить все вызовы `subtotal()` в тестах |

**Плюсы:**
- Логика валидации рядом с вычислением суммы
- Теоретически — переиспользуемость для других расчётов

**Минусы:**
- **Не соответствует архитектуре**: `subtotal` — чистая функция подсчёта, валидация там не её ответственность
- Требует переписывания всех тестов (их уже 8 штук)
- Смешивает две обязанности: подсчёт и валидация

**Усилия:** ~1 час (в основном из-за тестов)

**Риски:**
- Высокая вероятность нарушения существующих тестов
- Нарушение принципа единой ответственности

**Вердикт:** НЕ РЕКОМЕНДУЕТСЯ из-за архитектурных нарушений.

### Концепт 4: Креативный хак — Отдельный модуль валидации

**Суть:** Вынести все валидации в отдельный модуль `src/validators.mjs`.

**Изменения:**

| Файл | Что меняется |
|------|--------------|
| `src/validators.mjs` | **НОВЫЙ ФАЙЛ**: функции `validateItems()`, `validateMinOrderAmount()` |
| `src/pricing.mjs` | Вызвать `validateItems(items)` в `quote()` |
| `src/pricing.mjs` | Вызвать `validateMinOrderAmount(goods)` после `subtotal()` |
| `tests/pricing.test.mjs` | Импортировать из `validators.mjs` |
| `tests/validators.test.mjs` | **НОВЫЙ ФАЙЛ**: тесты валидаций |

**Плюсы:**
- Чистое разделение: расчёт отдельно, валидация отдельно
- Переиспользуемость валидаций
- Тестирование валидаций независимо от расчётов

**Минусы:**
- **Новый файл** — увеличение числа компонентов
- Дольше делать (~1.5 часа)
- Для проекта такого размера может быть overengineering

**Усилия:** ~1.5 часа

**Риски:**
- Увеличение сложности без явной необходимости
- Возможно нарушение принципа "без новых зависимостей"

**Вердикт:** ХОРОШ для будущего, но ИЗБЫТОЧНЫЙ для текущей задачи.

### Концепт 5: «Не трогай» — Отложить до уточнения требований

**Суть:** Не внедрять, пока не утверждён точный порог и частота его изменения.

**Обоснование:**
- Текущее поведение системы не блокирует бизнес-процессы (иначе задача была бы горящей)
- Неправильное значение порога может нанести больше вреда, чем его отсутствие
- Demoproject может демонстрировать и текущее поведение

**Плюсы:**
- Не вводится изменение с неуверенными параметрами
- Время на сбор метрик и согласование с бизнесом

**Минусы:**
- Проблема не решается
- Убыточные заказы продолжают приниматься

**Когда выбрать:** если есть сомнения в значении порога или частоте его изменения.

# Архитектурные дебаты

**Дата:** 2026-08-20
**Метод:** 3 раунда структурированных дебатов (Архитектор vs Адвокат Дьявола)
**Участники:**
- **Архитектор**: защищает выбранный концепт, доказывает его пригодность
- **Адвокат Дьявола**: атакует, ищет слабые места, риски, скрытые проблемы

---

## Раунд 1: Защита

### Архитектор: Выбор и защита Концепта 1

**Выбранное решение:** Концепт 1 (Базовая константа)

**Аргументы за:**

1. **Следует существующему паттерну проекта**
   - Доказательство: `src/pricing.mjs:5-10` — константы `DELIVERY_FEE` и `FREE_DELIVERY_FROM` уже определены как `export const`
   - Добавление `MIN_ORDER_AMOUNT` продолжит этот паттерн, а не введёт новый
   - Код будет однородным и предсказуемым для будущих разработчиков

2. **Минимальные изменения = минимальные риски**
   - Изменяется только один файл (`src/pricing.mjs`)
   - Изменяется только одна функция (`quote()`)
   - Точка внедрения чётко определена: после `const goods = subtotal(items)`, до `const delivery = deliveryFee(goods)`
   - Зона изменения изолирована и не затрагивает существующие тесты

3. **Автоматическая HTTP-интеграция**
   - Доказательство: `src/server.mjs:38-42` — существующий catch уже превращает любой `Error` в HTTP 400
   - Новая проверка не потребует изменений в HTTP-слое
   - Интеграция бесплатная в обоих смыслах: не нужно писать код и не нужно тестировать

4. **Легкость тестирования**
   - Паттерн уже существует: `tests/pricing.test.mjs:16-19` — тест валидации через `assert.throws()`
   - Новый тест будет аналогичен существующим
   - Значение константы можно менять в тестах через импорт

**Вывод Архитектора:** Для MVP этого демо-стенда Концепт 1 оптимален — он решает задачу минимальными усилиями, следует архитектуре проекта и не вводит новой сложности.

---

### Адвокат Дьявола: Атака на Концепт 1

**Критика:**

1. **Жёстко захардкоженное значение**
   - `MIN_ORDER_AMOUNT = 1000` — откуда это значение?
   - Если через неделю бизнес решит, что порог должен быть 1500 или 500 — потребуется полный цикл: код → ревью → тесты → деплой
   - Для конфигурационного параметра это неоправданно дорого

2. **Риск неверного первого значения**
   - Аналогия: `FREE_DELIVERY_FROM = 3000` — это значение тщательно продумано и согласовано с бизнесом
   - Если `MIN_ORDER_AMOUNT` выбрать наугад (например, 1000), можно:
     - Слишком низко — продолжить приём убыточных заказов
     - Слишком высоко — отпугнуть legitimate мелкие заказы
   - Первое впечатление от фичи важнее, чем "мы потом поправим"

3. **Концепт не решает вопрос выбора значения**
   - Концепт 1 описывает КАК добавить проверку, но не ГДЕ взять значение
   - Если бы Таск содержал "утверждённый бизнесом порог = 1000 руб", Концепт 1 был бы идеален
   - Но в `task.md:6-7` чёрным по белому: "Какое значение порога минимальной суммы? — Открыт — Требуется согласование с бизнесом"
   - Внедрять неутверждённый параметр — это не решение, это создание технического долга

4. **Сравнение с Концептом 2**
   - Концепт 2 (env) тоже не решает проблему значения, но хотя бы даёт flexibility изменить его без деплоя
   - Стоимость перехода от Концепта 1 к Концепту 2: переписать константу на `process.env`, добавить валидацию — примерно те же 30 минут, что и внедрение Концепта 1 с нуля
   - Почему не выбрать Концепт 2 сразу?

**Контраргумент на "следует паттерну":**
- Да, `DELIVERY_FEE` и `FREE_DELIVERY_FROM` захардкожены
- Но это значение ОДИН РАЗ выбрано и редко меняется
- Минимальная сумма заказа — это именно тот параметр, который бизнес МОЖЕТ захотеть менять часто (A/B тестирование, сезонность, промо-акции)

**Вывод Адвоката:** Концепт 1 технически корректен, но бизнес-риски велики. Неверное значение первого коммита создаст больше проблем, чем отсутствие проверки.

## Раунд 2: Пересмотр

### Архитектор: Ответ на критику

**Усиление позиции:**

1. **По вопросу значения порога:**
   - Согласен: внедрение неутверждённого значения — риск
   - Однако: это риск не Концепта 1, а процесса внедрения
   - Рекомендация: перед кодом получить утверждение от бизнеса (быстрый email/чат: "какой порог ставить?")
   - Если утверждение невозможно — Концепт 5 (отложить) становится валидным выбором

2. **По вопросу гибкости vs простоты:**
   - Концепт 2 даёт гибкость, но вводит новый паттерн: `process.env` в pricing-модуле
   - Текущий код (`src/pricing.mjs:1-53`) не использует `process.env` вообще — это чистый модуль арифметики
   - Введение `process.env` в `pricing.mjs` нарушает его чистоту (чистые функции не должны зависеть от окружения)

3. **По вопросу стоимости перехода 1→2:**
   - Да, переход недорог (~15 минут)
   - Но: YAGNI — не будем вводить сложность до того, как она понадобится
   - Если бизнес скажет "нам нужно часто менять порог" — тогда пивот на Концепт 2
   - Если бизнес скажет "нам нужен один раз и навсегда" — Концепт 2 был бы перебором

4. **Новый аргумент: Деплой-простота**
   - Концепт 1 требует только изменения кода — ни конфигов, ни документации по env
   - Для демо-стенда это важно — обучение и демонстрация фичи не должны включать настройку окружения

**Пересмотрённая позиция:**
- Концепт 1 остаётся выбором для MVP при условии: значение порога утверждено бизнесом перед кодом
- Если значение не утверждено → Концепт 5 (отложить до утверждения)
- Концепт 2 становится опцией только после явного требования "нужна частая изменяемость"

### Адвокат Дьялола: Проверка на сценарии "что если"

**Сценарий 1: Бизнес утверждает порог, но через месяц просит изменить**

- Концепт 1: код → ревью → тест → деплой (~2 часа)
- Концепт 2: изменить env в Kubernetes/Docker (~2 минуты)
- Вопрос: почему мы так уверены, что порог не будет меняться?

**Сценарий 2: Разные пороги для разных окружений**

- Dev/Stage: порог 500 (для тестирования)
- Prod: порог 1000 (боевой)
- Концепт 1: не поддерживается — один порог на все окружения
- Концепт 2: поддерживается нативно через разные env-значения
- Для демо-стенда это может быть важно: на dev/test удобно иметь низкий порог для тестирования

**Сценарий 3: Некорректное значение в env**

- Адвокат признаёт: Концепт 2 имеет этот риск
- Но: риск можно митигировать валидацией при старте (как в коде Концепта 2: `if (!Number.isFinite(MIN_ORDER_AMOUNT) || MIN_ORDER_AMOUNT <= 0)`)
- Плюс: CI может тестировать с разным env

**Сценарий 4: Концепт 5 (отложить) — это не решение**

- Отложить не решает проблему убыточных заказов
- Проблема либо достаточно остра (тогда надо решать), либо нет (тогда почему задача вообще заведена?)
- Откладка без четкого критерия "когда вернуться" — это прокрастинация, а не стратегия

**Вывод Адвоката:**
- Если бизнес НЕ уверен в значении → Концепт 5
- Если бизнес УТВЕРДИЛ значение, но НЕ уверен в частоте изменений → Концепт 2 (страховка)
- Концепт 1 оправдан только если бизнес сказал "это значение — навсегда и не будет меняться"

## Раунд 3: Вердикт

### Финальная позиция Архитектора

Концепт 1 — это "правильное" решение для демо-стенда:
- Следует архитектуре проекта (чистые функции в `pricing.mjs`, HTTP в `server.mjs`)
- Минимальные изменения = минимальная вероятность багов
- Если понадобится гибкость — переход на Концепт 2 дёшев и прост

Но: это решение требует утверждения значения порога перед внедрением. Без утверждения — это создание техдолга.

### Финальная позиция Адвоката Дьявола

Признаю Концепт 1 техническиsound, но настаиваю на условии: значение порога должно быть утверждено бизнесом до первой строчки кода.

Если бы спросили меня:
- Есть утверждённое значение + уверенность "не будет меняться" → **Концепт 1**
- Есть утверждённое значение + неуверенность в частоте изменений → **Концепт 2**
- Нет утверждённого значения → **Концепт 5** (до утверждения) → затем выбор между 1 и 2

## ИТОГОВЫЙ ВЕРДИКТ

**Концепт 1 (Базовая константа) ПРИНЯТ с модификацией процесса**

### Условия принятия:

1. **Значение порога должно быть утверждено бизнесом до начала разработки**
   - Минимальное действие: email/чат с бизнесом: "какой минимальный порог ставим?"
   - Если ответ не получен → перейти к Концепту 5 (отложить)

2. **Если бизнес скажет "это значение будет часто меняться"** → перейти на Концепт 2

3. **Если будет нужна разная конфигурация для окружений** → перейти на Концепт 2

### План действий:

1. Получить утверждение значения порога (предлагается 1000 руб как разумное среднее)
2. Если утверждено → внедрять Концепт 1
3. После внедрения — мониторить запросы на изменение порога
4. Если запросы участились → рефакторинг на Концепт 2

### Обоснование:

- Для демо-стенда простота важнее преждевременной гибкости
- Концепт 1 следует существующей архитектуре (чистые функции без env)
- Переход на Концепт 2 недорог, если гибкость понадобится
- Концепты 3, 4, 5 отпадают:
