# FNR-1: Концепты решений

**Задача:** Гостевой заказ без регистрации  
**Источник:** Issue #43, БФТ (быстрый проход)  
**Анализ:** task.md, FNR_1  
**Дата:** 2025-08-19

---

## Диагноз ситуации

**Факт:** Текущий сервис `poh-demo-checkout` реализует только расчёт стоимости заказа (`POST /quote`) и не содержит инфраструктуры для:
- Сохранения заказов
- Управления пользователями/профилями
- Отправки email-уведомлений
- Аутентификации/авторизации

**Ограничение:** Репозиторий — демо-стенд контура производства, код намеренно простой. Зависимостей нет (только Node.js stdlib).

**Следствие:** Реализация полноценного гостевого чекаута выходит за границы текущего scope демо-репозитория.

---

## Концепты решений

### 1. Правильное: Полноценный Order Service (Reference Architecture)

**Суть:** Отказаться от идеи вписать чекаут в текущий демо-сервис и построить полноценный Order Service с необходимой инфраструктурой.

**Что делать:**

| Компонент | Файл/Технология | Описание |
|-----------|-----------------|----------|
| Модель заказа | `src/order.mjs` (новый) | Entity: Order, GuestCheckout, UserProfile |
| Модель пользователя | `src/user.mjs` (новый) | Entity: User, Profile, MergeLogic |
| Хранилище | SQLite через stdlib | Файл БД для persisted state |
| Email-сервис | `src/email.mjs` (новый) | Интеграция с внешним SMTP (sendmail/stdlib) |
| Сессии/токены | `src/session.mjs` (новый) | JWT-like токены для гостевой сессии |
| Endpoints | `src/server.mjs` (расширить) | `POST /guest/checkout`, `POST /guest/claim`, `GET /orders/:id` |
| Миграции | `migrations/` (новый каталог) | Schema evolution |
| Тесты | `tests/order.test.mjs`, `tests/guest-flow.test.mjs` | Integration тесты полного flow |

**Затрагиваемые файлы из repomix:**
- `src/server.mjs` — расширить новыми endpoints
- `tests/` — новые тесты
- Новые файлы: вся бизнес-логика чекаута

**Плюсы:**
- Правильная архитектура для реального e-commerce
- Масштабируется: можно добавить авторизованный flow
- Тестируемость: чёткое разделение ответственности
- Персистентность: заказы сохраняются, не теряются

**Минусы:**
- Уходит за границы демо-репо (слишком сложно для стенда)
- Требует БД (новая зависимость/инфраструктура)
- Требует SMTP-сервер (внешняя зависимость)
- Значительный объём кода (3-5 дней работы)

**Усилия:** 3-5 дней  
**Риски:** Высокие — проект превращается в полноценный e-commerce, теряет фокус "простого демо"

### 2. Прагматичное: Stateful Guest Flow без БД

**Суть:** Минимальный MVP гостевого оформления в памяти текущего сервиса, без персистентности и реальной email-отправки.

**Что делать:**

| Компонент | Файл | Описание |
|-----------|-------|----------|
| Валидация гостевой формы | `src/server.mjs` (новый endpoint) | `POST /guest/quote` — валидирует email/адрес/телефон |
| Мок отправки email | `src/email.mjs` (новый, заглушка) | Логирует письмо вместо отправки |
| Мок сессии | В памяти процесса | Map сессия → данные (теряется при рестарте) |
| Тесты | `tests/guest.test.mjs` (новый) | Проверка валидации и моков |

**Затрагиваемые файлы из repomix:**
- `src/server.mjs` — добавить `/guest/quote`
- Новые файлы: `src/email.mjs` (заглушка)

**Плюсы:**
- Остаются в рамках текущего демо-репо
- Нет БД и внешних зависимостей
- Быстрый MVP (1-2 дня)
- Flow можно продемонстрировать

**Минусы:**
- Данные теряются при рестарте (нет персистентности)
- Нет реальной email-отправки (только мок)
- Нет привязки к профилю (нет профиля)
- Сложно тестировать полный flow

**Усилия:** 1-2 дня  
**Риски:** Средние — flow работает, но бизнес-ценность ограничена (данные не сохраняются)

### 4. Креативный хак: Email-based токен вместо сессии

**Суть:** Использовать email как primary key и выдавать одноразовый токен для доступа к статусу заказа — без профиля, без сессии.

**Что делать:**

| Компонент | Файл | Описание |
|-----------|-------|----------|
| Checkout endpoint | `src/server.mjs` | `POST /guest/checkout` → возвращает `{orderId, token}` |
| Токен | В памяти Map | `token → {orderData, email, timestamp}` |
| Status endpoint | `src/server.mjs` | `GET /guest/status/:token` → возвращает статус |
| Тесты | `tests/guest-token.test.mjs` | Flow: checkout → status → expire |

**Затрагиваемые файлы из repomix:**
- `src/server.mjs` — два новых endpoint
- Новые файлы: нет

**Плюсы:**
- Изящно: email = идентификатор
- Без сессий и БД (в памяти)
- Можно проверить статус заказа без аккаунта
- Подходит для демо

**Минусы:**
- Данные теряются при рестарте
- Нет реальной email-отправки
- Нет привязки к профилю (профилей нет)
- Токен expires = заказ потерян

**Усилия:** 1 день  
**Риски:** Средние — работает для демо, но не продакшн

3. Реализовать гостевой чекаут в новом репо

**Затрагиваемые файлы из repomix:**

**Плюсы:**
- Честные границы: демо остаётся демо

**Минусы:**

- Два репа вместо одного
- Не решает исходный запрос "здесь и сейчас"

## Раунд 1: Защита

### 🔵 Архитектор: Выбор концепта #4 (Email-based токен)

**Защищаемый концепт:** #4 — Креативный хак: Email-based токен вместо сессии

**Выбор:**
Для демо-стенда `poh-demo-checkout` концепт #4 оптимален. Он даёт рабочий flow гостевого заказа без выхода за границы репозитория.

**Аргументы:**

1. **Вписывается в ограничения демо-репо:**
   - Нет БД — все данные в памяти (`Map` токен → orderData)
   - Нет внешних зависимостей — только Node.js stdlib (согласно CLAUDE.md:66-67)
   - Минимальное расширение `server.mjs` — два новых endpoint

2. **Реализует требуемый HowToDemo flow:**
   - Пользователь вводит email + данные → получает `{orderId, token}`
   - Может проверить статус по токену (`GET /guest/status/:token`)
   - Email используется как идентификатор (для поиска в поддержке)

3. **Баланс сложность/ценность:**
   - 1 день усилий vs 3-5 дней у концепта #1
   - Реальная функциональность vs заглушка у концепта #3
   - Подходит для демонстрации паттерна "гостевой доступ"

**Доказательства кода:**
- `src/server.mjs:26-46` — текущий `/quote` эндпоинт, можно расширить тем же паттерном
- `src/server.mjs:10-17` — функция `send()` уже реализована, переиспользуем
- Нет auth-логики — значит, не ломаем существующий flow

**Вывод:** Концепт #4 даёт минимум необходимой функциональности для демо без нарушения ограничений репозитория.

---

### 🔴 Адвокат Дьявола: Атака на концепт #4

**Критика:**

1. **Персистентность критична для HowToDemo:**
   - При рестарте сервера все заказы теряются — токены в памяти
   - HowToDemo требует: "После входа → новый заказ привязался к профилю"
   - Но профилей в репо нет — как привязывать несуществующий заказ к несуществующему профилю?

2. **Email-отправка необходима по требованиям:**
   - БФТ требует: "Письмо со статусом заказа на указанный email"
   - Концепт #4: "Нет реальной email-отправки (только мок)"
   - Значит, требования БФТ не выполняются

3. **Обработка повторных заказов невозможна:**
   - Требование: "Повторный заказ на ту же почту не должен создавать дубль профиля"
   - Но нет профилей — нет дубликатов — нет проблемы
   - Это "решение" игнорирует требование, а не решает его

4. **Разрыв между демо и реальностью:**
   - Если stakeholder увидит демо, он ожидает, что в проде это будет работать так же
   - Но в проде нужен персистентный storage, real email, profile merge logic
   - Демо создаёт ложные ожидания

**Доказательства:**
- `task.md:48-60` — HowToDemo явно требует письмо и привязку к профилю
- `task.md:51` — "Повторный заказ на ту же почту не должен создавать дубля профиля"
- Текущий код не содержит ни User Service, ни email-сервиса

**Вердикт раунда 1:** Концепт #4 не проходит по критериям HowToDemo — нет персистентности, нет email, нет профилей для привязки.

## Раунд 2: Пересмотр

### 🔵 Архитектор: Пивот на концепт #2 (Stateful Guest Flow без БД)

**Признание проблем:**
Адвокат прав — концепт #4 не выполняет требования БФТ по email и профилям. Но концепт #1 тоже не подходит — превращает демо в полноценный e-commerce.

**Пивот на концепт #2:** Stateful Guest Flow без БД

**Аргументы:**

1. **Реализация email через mock:**
   - Создаём `src/email.mjs` с функцией `sendOrderStatus(email, orderData)`
   - Вместо real SMTP — логируем в console (это допустимо для демо)
   - Тест проверяет вызов функции, а не реальную доставку

2. **Профили — out of scope MVP:**
   - Требование "привязка к профилю" можно интерпретировать как будущий enhancement
   - Для MVP достаточно: заказ сохранён, email отправлен (мок), статус доступен
   - Профили и слияние — SubIssue с `root-issue: #43`

3. **Персистентность через файл (не БД):**
   - Можно использовать JSON-файл для хранения заказов (в пределах stdlib)
   - `fs.writeFileSync` и `fs.readFileSync` — из Node.js stdlib, новая зависимость не нужна

**Доказательства кода:**
- Node.js stdlib включает `fs` — не противоречит CLAUDE.md:66-67

**Вывод:** Концепт #2 с файловой персистентностью и mock-email проходит HowToDemo для MVP.

### 🔴 Адвокат Дьявола: What-if анализ

**Критика пивота:**

1. **Файловое хранилище — race conditions:**
   - Два одновременных запроса на один файл → один перезапишет другого
   - Для демо может быть ок, но это антипаттерн
   - В реальном проде это приведёт к потере данных

2. **Mock-email не обнаружит проблемы интеграции:**
   - Если потом подключить real SMTP, могут вылезти баги
   - Mock скрывает реальное поведение системы
   - Демо становится ненадёжным предсказателем продакшена

3. **Профили — "будущий enhancement" = никогда:**
   - История показывает: "потом" часто = "никогда"
   - Требование было явным в БФТ — игнорирование это технический долг
   - Stakeholder увидит демо без профилей и спросит: "где привязка?"

4. **Scope creep по определению:**
   - Добавляем файловое хранилище — это уже не stateless
   - Добавляем email-мок — это ещё один компонент
   - Добавляем endpoints — растет сложность `server.mjs`
   - Скоро это станет концептом #1, только хуже (нет БД, но есть state)

**Вопрос к Архитектору:**
> Что если через полгода спросят: "Где feature X из демо?" — а в проде это не работает, потому что демо было на файлах и моках?

**Доказательства:**
- `CLAUDE.md:3-6` — репо "демо-стенд контура производства", а не реальный e-commerce
- `task.md:122-132` — диагноз: проблема = отсутствие функциональности, а не баг

**Вердикт раунда 2:** Концепт #2 с файлами и моками создаёт ложное впечатление готовности. Проблема не в реализации, а в scope задачи относительно репозитория.

**Обоснование:**

1. **Честный подход:** Концепт явно декларирует своё ограниченное назначение — proof-of-concept для API-контракта, а не реальная функциональность.

2. **Соответствие scope демо-репо:**
   - Не требует БД, email-сервиса, профилей
   - Минимальное изменение `src/server.mjs` и `tests/pricing.test.mjs`
   - Сохраняет текущую архитектуру (stateless service)

3. **Быстрая обратная связь:**
   - 2-4 часа работы vs 1-2 недели на новый репо
   - API-контракт можно обсудить со stakeholders до реальной реализации
   - Если контракт утверждён — переход к концепту #1 или #5

4. **Минимальные риски:**
   - Изменение обратно совместимо
   - Никаких новых зависимостей
   - Легко откатить или расширить
