# Концепты решений для FNR-1: Округление итогов в ответе /quote

**Родительская задача:** [Issue #10](https://github.com/po-helper-org/poh-demo-checkout/issues/10)
**Дата генерации:** 2026-08-18
**Зона воздействия:** `src/pricing.mjs`, `src/server.mjs`, `tests/pricing.test.mjs`

---

## Диагноз проблемы

Эндпоинт `POST /quote` возвращает дробные значения в полях `goods`, `delivery`, `total`. Платёжная форма на фронтенде отображает только целые рубли → визуальное расхождение между данными API и UI.

**Корень проблемы:** отсутствует этап округления в цепочке расчёт→сериализация ответа.

**Точки внедрения:**
1. В `quote()` (domain-слой, `src/pricing.mjs:48-52`)
2. В HTTP-обработчике (boundary, `src/server.mjs:39`)
3. В сериализации (`src/server.mjs:10-16`)

---

## Архитектурные ограничения

Из `CLAUDE.md`:

> Арифметика — в `src/pricing.mjs`, чистыми функциями. `src/server.mjs` только разбирает запрос и отдаёт коды: логика в обёртке — логика, которую тест не увидит.

> Зависимостей у сервиса нет. Новая заводится, только если задачу нечем закрыть из стандартной библиотеки.

## Концепты решений

### Концепт 1: Округление в domain-слое (Правильное)

**Суть:** Округлять значения в функции `quote()` перед возвратом результата.

**Место изменений:** `src/pricing.mjs:48-52`

**Реализация:**
```javascript
export function quote(items) {
  const goods = subtotal(items);
  const delivery = deliveryFee(goods);
  const total = goods + delivery;
  return {
    goods: Math.round(goods),
    delivery: Math.round(delivery),
    total: Math.round(total)
  };
}
```

**Плюсы:**
- Логика округления централизована в одном месте
- Автоматически покрывается существующими тестами `pricing.test.mjs`
- Все callers получают округлённые значения (если `quote()` будет использоваться где-то ещё)
- Явное и предсказуемое поведение

**Минусы:**
- Теряется внутренняя точность для потенциальных будущих расчётов
- Функция перестаёт быть "чистой" в строгом смысле (добавляет нормализацию выхода)
- Незначительное усложнение кода domain-слоя

**Усилия:** 30 минут
**Риски:** Низкие

---

### Концепт 2: Округление на API-границе (Прагматичное)

**Суть:** Округлять значения в HTTP-обработчике после вызова `quote()`, но до сериализации.

**Место изменений:** `src/server.mjs:39`

**Реализация:**
```javascript
// В обработчике /quote
const result = quote(body?.items);
return send(res, 200, {
  goods: Math.round(result.goods),
  delivery: Math.round(result.delivery),
  total: Math.round(result.total)
});
```

**Плюсы:**
- Domain-слой остаётся точным (принцип разделения ответственности)
- Округление применяется только на границе API
- Изменения максимально локализованы
- Тесты domain-слоя не требуют правок

**Минусы:**
- Существующие тесты `pricing.test.mjs` не покрывают округление
- Требуются отдельные HTTP-тесты для проверки округления
- Дублирование структуры объекта ответа

**Усилия:** 1 час (включая HTTP-тесты)
**Риски:** Низкие

### Концепт 3: Округление при сериализации (Быстрый костыль)

**Суть:** Модифицировать функцию `send()` для форматирования числовых полей при `JSON.stringify`.

**Место изменений:** `src/server.mjs:10-16`

**Реализация:**
```javascript
function send(res, code, body) {
  // Заменить значения всех числовых полей на округлённые
  const rounded = deepRoundNumbers(body);
  const payload = JSON.stringify(rounded);
  // ... остальной код
}

function deepRoundNumbers(obj) {
  if (typeof obj === 'number') return Math.round(obj);
  if (obj === null || typeof obj !== 'object') return obj;
  if (Array.isArray(obj)) return obj.map(deepRoundNumbers);
  return Object.fromEntries(
    Object.entries(obj).map(([k, v]) => [k, deepRoundNumbers(v)])
  );
}
```

**Плюсы:**
- Максимальная локализация изменений
- Оригинальные объекты не модифицируются
- Работает для всех эндпоинтов сразу

**Минусы:**
- Сложно применить избирательно (только для `/quote`)
- Неявное поведение (клиент не видит, что произошло округление)
- Сериализатор должен "знать" о структуре данных
- Может случайно округлить то, что не должно округляться
- Наименее читаемое решение

**Усилия:** 2 часа
**Риски:** Средние (нечаянное округление других полей)

### Концепт 4: Не трогать (Консервативный)

**Суть:** Не менять поведение API. Отображение — ответственность фронтенда.

**Обоснование:**
- API возвращает точные значения (это правильно)
- Фронтенд должен сам форматировать данные для отображения
- Дробные рубли — валидное значение (есть копейки)

**Плюсы:**
- Никаких изменений в бэкенде
- API остаётся «источником правды» с максимальной точностью
- Отсутствие риска поломки существующих клиентов

**Минусы:**
- Не решает исходную проблему (расхождение UI и API)
- Фронтенду всё равно нужно округлять
- Проблема не исчезает, только переносится

**Усилия:** 0
**Риски:** Отсутствуют

### Концепт 5: Двухуровневое округление (Креативный хак)

**Суть:** Создать отдельную функцию `quoteRounded()` в domain-слое, которая вызывает `quote()` и округляет результат. Использовать её для API, оставив `quote()` нетронутой для внутренних нужд.

**Место изменений:** `src/pricing.mjs` (новая функция)

**Реализация:**
```javascript
export function quoteRounded(items) {
  const result = quote(items);
  return {
    goods: Math.round(result.goods),
    delivery: Math.round(result.delivery),
    total: Math.round(result.total)
  };
}
```

**Плюсы:**
- Сохраняется точность базовой функции
- Явное разделение точных и округлённых значений
- Легко тестировать обе функции
- Гибкость для будущего использования

**Минусы:**
- Дублирование API (две функции для похожих целей)
- Возможная путаница: когда какую использовать
- Незначительное усложнение кодовой базы

**Усилия:** 45 минут
**Риски:** Низкие

## Пограничный случай: согласованность округления

**Проблема:** При суммировании округлённых значений может возникнуть расхождение:

```
goods: 1000.50 → 1001
delivery: 299.50 → 300
total: 1300.00 → 1300
```

Но `1001 + 300 = 1301 ≠ 1300`

**Решение для всех концептов:**
- Округлять `total` независимо: `Math.round(goods + delivery)`
- Это гарантирует `total ≈ goods + delivery` с погрешностью округления
- Документировать это поведение в API

## Раунд 1: Защита

### Архитектор: Выбор концепта #1

Я выбираю **Концепт #1 (округление в domain-слое)** как оптимальное решение.

**Основные аргументы:**

1. **Соответствие архитектурным принципам** (`CLAUDE.md:58-60`):
   > Арифметика — в `src/pricing.mjs`, чистыми функциями. `src/server.mjs` только разбирает запрос и отдаёт коды.

   Округление — это арифметическая операция. Место ей — в `pricing.mjs`, рядом с другими вычислениями.

2. **Автоматическое покрытие тестами** (`tests/pricing.test.mjs:38-44`):
   Существующие тесты вызывают `quote()` напрямую и проверяют точные значения. При округлении внутри `quote()` эти же тесты автоматически покроют новую логику.

3. **Централизация**: Все callers `quote()` получают округлённые значения. Если в будущем появится второй эндпоинт или внутренний модуль, использующий `quote()`, округление будет работать везде автоматически.

4. **Простота**: 30 минут работы, минимум кода, максимум прозрачности.

### Адвокат Дьявола: Атака на концепт #1

**Возражения:**

1. **Утеря точности для будущих вычислений**:
   После округления в `quote()` внутренняя точность теряется. Если через полгода появится необходимость в точных вычислениях (например, для налогового учёта или аналитики), нам придётся создавать новую функцию `quoteExact()`. Это технический долг, которого можно избежать сейчас.

2. **Нарушение чистоты функции**:
   `quote()` сейчас — чистая функция: `f(x) = y`. Добавление округления делает её функцией нормализации: `f(x) = format(y)`. Это смешивает вычисление с представлением.

3. **API-контракт меняется неявно**:
   Текущие клиенты (если они есть) могут полагаться на точные значения. Округление в domain-слое меняет контракт для всех callers, не только для HTTP-API.

4. **Проблема согласованности** (из concept.md:216-230):
   ```
   goods: 1000.50 → 1001
   delivery: 299.50 → 300
   total: 1300.00 → 1300
   ```
   Но `1001 + 300 = 1301 ≠ 1300`. Это математическое несоответствие будет встроено в domain-слой.

## Раунд 2: Пересмотр

### Архитектор: Ответ на критику

**По поводу утери точности:**

Задача (`task.md:13-18`) чётко определяет: проблема в расхождении между API и UI. Округление до целых рублей — требование к API-контракту, а не к внутренним вычислениям.

Если в будущем понадобятся точные значения:
- Вариант A: Создать `quoteExact()` и рефакторить callers (час работы)
- Вариант B: Сохранять точное значение в объекте: `{ goods, goodsRounded, ... }`

Но это speculation about future requirements. Current requirement: округление для UI.

**По поводу чистоты функции:**

Округление — это не форматирование, это нормализация результата. `Math.round()` — арифметическая операция, как и `+` или `*`. Разница только в том, что она применяется к результату, а не к промежуточным значениям.

**По поводу несогласованности total:**

Это верное замечание. Решение: вычислять `total` из округлённых компонентов:
```javascript
const goodsRounded = Math.round(goods);
const deliveryRounded = Math.round(delivery);
return {
  goods: goodsRounded,
  delivery: deliveryRounded,
  total: goodsRounded + deliveryRounded
};
```

Это гарантирует `total === goods + delivery`.

### Адвокат Дьявола: Критика исправления

**Но что если через полгода изменится правило округления?**

Сейчас — `Math.round()`. Tomorrow — `Math.floor()` для `goods`, но `Math.round()` для `delivery`. Или округление до десятков, а не единиц.

При концепте #1 это изменение в domain-слое. При концепте #2 (API-граница) — изменение только в HTTP-обработчике.

**А что если появится другой формат вывода?**

Например, CSV-экспорт, где нужны точные значения. При концепте #1 CSV тоже получит округлённые значения (если использует `quote()`). При концепте #2 CSV может вызывать `quote()` напрямую и получать точные значения.

**Сложность тестов:**

При концепте #1 нужно добавить тесты для дробных значений в `pricing.test.mjs`. Это хорошо. Но что если эти тесты замаскируют проблему: тесты проходят, но HTTP-вывод всё равно содержит дробные значения из-за бага в сериализации?

При концепте #2 нужны HTTP-тесты, которые проверяют полный путь → округление → сериализация. Это более надёжно.

## Раунд 3: Вердикт

### Архитектор: Итоговая позиция

**Концепт #1 остаётся оптимальным по следующим причинам:**

1. **YAGNI** (You Aren't Gonna Need It): Предположения о будущих требованиях (CSV-экспорт, налоговый учёт) — это speculation. Текущее требование: округление для HTTP-API.

2. **Принцип единой ответственности**: Округление — это бизнес-логика ("мы показываем клиентам целые рубли"), а не представление. Место бизнес-логики — в domain-слое.

3. **Покрытие тестами**: Исправление для согласованности `total` (вычислять из округлённых компонентов) решает основную математическую проблему.

4. **Усилия vs ценность**: 30 минут работы для решения проблемы немедленно.

**Ограничение применения:**
Если在未来 появляются требования для точных значений, они будут решены тогда (SubIssue, не сейчас).

### Адвокат Дьявола: Итоговая позиция

**Признаю сильные стороны концепта #1, но настаиваю на ограничениях:**

1. Концепт #1 оптимален **только если**:
   - Все callers `quote()` требуют округлённых значений
   - Нет требований к точным значениям в других контекстах
   - Правило округления стабильно

2. **Рекомендуется**:
   - Добавить JSDoc к `quote()`, документирующий округление
   - Добавить тесты для пограничных случаев (`.5`, отрицательные округления)
   - Рассмотреть концепт #5 (две функции) если есть сомнения в будущем использовании

3. **Минимальное изменение**:
   Исправление для `total` (вычислять из округлённых) обязательно, иначе математическое несоответствие будет багом.

### Вердикт

**Концепт #1 (округление в domain-слое) ПРИНЯТ с модификациями:**

**Модификации:**
1. `total` вычисляется из округлённых компонентов для согласованности
2. Добавляется JSDoc документация округления
3. Добавляются тесты для пограничных случаев (`.5`, нули, крупние суммы)

**Обоснование:**
- Соответствует архитектурным принципам (`CLAUDE.md:58-60`)
- Минимальные усилия (30 минут)
- Автоматическое покрытие существующими тестами
- Math.round() — арифметическая операция, место в domain-слое

**Риски:**
- Низкие (нет текущих требований для точных значений)
- Будущие требования решены будут в будущем (YAGNI)
