## Анализ проблемы

### Корень проблемы

По живому сервису невозможно определить версию работающего кода без доступа внутрь контейнера. Метка образа и лог старта недостоверны: образ пересобирается молча, строка «сервис запущен» идентична для всех версий.

### Зона воздействия

| Компонент | Тип воздействия |
|-----------|----------------|
| `src/server.mjs` | Новый маршрут `/version` |
| `package.json` | Чтение версии (источник данных) |
| `tests/server.test.mjs` | Новые тесты |

### Ограничения

| Ограничение | Деталь |
|-------------|--------|
| Без новых зависимостей | Сервис не имеет зависимостей — не добавлять |
| `/healthz` не меняется | Версия отдаётся отдельным маршрутом |
| `pricing.mjs` не трогается | Зона изменений — только `server.mjs` и тесты |
| Метод только GET | Другие методы отвечают 405 |
| Версия из `package.json` | Не дублировать константой в коде |

## Концепты решений

### Концепт 1: ES-импорт JSON (Правильное)

**Суть:**

Использовать нативный ES-импорт JSON для чтения `package.json` при инициализации модуля. Версия загружается один раз при старте сервиса и хранится в константе. Эндпоинт `/version` следует паттерну `/healthz` — проверка метода, ответ 405 с заголовком `Allow: GET` для не-GET запросов.

**Изменяемые файлы:**

- `src/server.mjs` — добавить импорт и маршрут
- `tests/server.test.mjs` — добавить тесты

**Плюсы:**

- Нативный механизм Node.js 22+ (соответствует `engines.node >=22`)
- Версия загружается один раз при старте — нет I/O на каждый запрос
- Следует существующему паттерну `/healthz` — консистентность кода
- Читается из единого источника правды — `package.json`

**Минусы:**

- Импорт верхнего уровня привязывает версию к моменту старта — при горячей замене кода без перезапуска версия устареет (неактуально для демо-стенда)

**Усилия:** 1-2 часа

**Риски:** Минимальные — нативная возможность, не ломает существующий код

---

### Концепт 2: fs.readFile при старте с кешированием (Прагматичное)

**Суть:**

Читать `package.json` через `fs.readFile` при первом обращении к `/version` или при старте сервиса, кешировать результат в замыкании. При повторных вызовах возвращать кешированное значение. Эндпоинт следует паттерну `/healthz`.

**Изменяемые файлы:**

- `src/server.mjs` — добавить логику чтения и кеширования
- `tests/server.test.mjs` — добавить тесты

**Плюсы:**

- Гибкость — можно перечитывать версию при необходимости (например, по сигналу)
- Работает на любой версии Node.js (если вдруг опустим требование)
- Легко добавить логирование ошибок чтения

**Минусы:**

- Больше кода, чем Concept 1
- Ленивая загрузка — первый запрос отработает медленнее (I/O)
- Требует обработки ошибок I/O (хотя для демо-стенда файл всегда есть)

**Усилия:** 2-3 часа

**Риски:** Низкие — ошибка чтения файла вернёт 500 вместо версии (можно обработать гранично)

---

### Концепт 3: Хардкод версии с комментарием (Быстрый костыль)

**Суть:**

Прописать версию константой в `server.mjs` с комментарием, что значение должно совпадать с `package.json`. Эндпоинт возвращает эту константу. Минимальная правка для быстрого MVP.

**Изменяемые файлы:**

- `src/server.mjs` — добавить константу и маршрут
- `tests/server.test.mjs` — добавить тесты

**Плюсы:**

- Максимально быстро — 10-15 минут работы
- Нет I/O вообще — версия в памяти
- Не зависит от структуры `package.json`

**Минусы:**

- Дублирование — версия в двух местах (нарушает DRY)
- Легко рассинхронизировать при обновлении `package.json`
- Требуется ручное обновление при каждом релизе
- Противоречит требованию «Версия из `package.json`»

**Усилия:** 0.5 часа

**Риски:** Средние — человеческий фактор при обновлении версии, но не критично для демо

---

### Концепт 4: Build-time инъекция (Креативный хак)

**Суть:**

Добавить в `package.json` скрипт, который при сборке/запуске инъектирует версию в переменную окружения или генерирует файл `version.mjs` с константой. Сервис читает оттуда. Версия актуальна на момент билда, а не запуска.

**Изменяемые файлы:**

- `src/server.mjs` — чтение из env или сгенерированного файла
- `package.json` — добавить build-скрипт
- `tests/server.test.mjs` — добавить тесты
- (опционально) `.github/workflows` — инъекция версии в CI

**Плюсы:**

- Версия зафиксирована на момент сборки — точно соответствует коду
- Легко расширяется до добавления git-sha, build-time и др.
- Нет I/O на рантайме

**Минусы:**

- Требует изменения процесса сборки/деплоя
- Для демо-стенда избыточно — нет separate build step
- Если билд не пересобирается, версия устареет

**Усилия:** 4-6 часов (включая настройку CI)

**Риски:** Средние — изменения в инфраструктуре, но даёт больше метаданных

---

### Концепт 5: Расширение `/healthz` («Не трогай»)

**Суть:**

Добавить поле `version` в ответ `/healthz`. Не создавать новый эндпоинт, а расширить существующий.

**Изменяемые файлы:**

- `src/server.mjs` — модифицировать ответ `/healthz`
- `tests/healthz.test.mjs` — обновить тесты

**Плюсы:**

- Меньше кода — один маршрут вместо двух
- Вся метаинформация в одном месте
- Меньше маршрутов — проще поддержка

**Минусы:**

- **Противоречит требованию задачи** — `/healthz` не должен меняться
- Нарушает принцип единой ответственности — `/healthz` про здоровье, не про идентификацию
- Если нужно проверить только версию — придётся парсить лишнее
- Раздувает тело ответа `/healthz`

**Усилия:** 1 час

**Риски:** Низкие по реализации, но **высокие по требованиям** — нарушает ограничение «`/healthz` не меняется»

---

## Рекомендация

**Для реализации: Концепт 1 (ES-импорт JSON)**

**Обоснование:**

1. **Соответствует ограничениям:** версия из `package.json`, `/healthz` не трогается, новых зависимостей нет
2. **Правильный подход:** использует нативную возможность Node.js 22+ (`engines.node >=22` в `package.json`)
3. **Консистентность:** следует паттерну `/healthz` для 405
4. **Эффективность:** версия загружается один раз при старте
5. **Простота:** минимум кода, легко понять и поддерживать

**Альтернатива:** Концепт 3 (хардкод) — если нужно абсолютное минимальное время, но с риском рассинхронизации версии.

**Не рекомендуется:** Концепт 5 — прямо противоречит ограничению «`/healthz` не меняется».

## Архитектурные дебаты

**Дата:** 2026-08-25
**Участники:** Архитектор vs Адвокат Дьявола
**Предмет:** Выбор концепта реализации эндпоинта GET /version

---

### Раунд 1 — Защита

#### Архитектор:

Я защищаю **Концепт 1 (ES-импорт JSON)** как оптимальное решение.

**Аргумент 1: Нативность соответствует стеку**

В [`package.json:11-12`](package.json:11-12) указано `"engines": { "node": ">=22" }`. ES-импорт JSON — это стандартная возможность Node.js 22+, не требующая дополнительных зависимостей. Код будет читаться как:

```javascript
import packageJson from '../package.json' with { type: 'json' };
const version = packageJson.version;
```

Это следование принципу "использовать нативные возможности платформы" — код чище, понятнее, не изобретает велосипед.

**Аргумент 2: Консистентность с существующей кодовой базой**

В [`server.mjs:43-50`](server.mjs:43-50) уже реализован паттерн для `/healthz`: проверка метода → 405 с заголовком `Allow: GET`. Новый эндпоинт `/version` следует этому же паттерну. Это консистентность кода, которую тесты уже подтверждают в [`tests/server.test.mjs:163-182`](tests/server.test.mjs:163-182).

**Аргумент 3: Эффективность — версия грузится один раз**

При импорте верхнего уровня версия загружается при старте сервиса и хранится в константе. Нет I/O на каждый запрос — это O(1) по памяти и O(1) по времени ответа.

**Аргумент 4: Соответствие всем ограничениям**

- Версия из `package.json` ✓ — источник правды один
- `/healthz` не меняется ✓ — новый маршрут
- Новых зависимостей нет ✓ — нативный `import`
- Метод только GET ✓ — паттерн 405
- `pricing.mjs` не трогается ✓ — зона изменений только `server.mjs`

#### Адвокат Дьявола:

Атакую Концепт 1 по трём направлениям.

**Контраргумент 1: Скрытое связывание со структурой package.json**

ES-импорт JSON привязывает код к конкретному пути `../package.json`. Если файл переедет или структура репозитория изменится — импорт сломается. При `fs.readFile` мы можем контролировать путь и обработать ошибку gracefully. Ссылка на жёсткий путь — это скрытое хрупкое связывание.

**Контраргумент 2: Что если версия изменилась, но сервис не перезапустили?**

В импорте верхнего уровня версия фиксируется на момент старта сервиса. Если:
- Образ пересобрался с новой версией
- Но контейнер/процесс не перезапустили

Тогда `/version` будет возвращать устаревшее значение. Это особенно актуально для long-running процессов.

**Контраргумент 3: А что если требование Node.js >=22 изменится?**

Концепт 1 жёстко привязан к Node.js 22+. Если завтра проекту понадобится поддержка Node.js 20 или 18, всё решение придётся переписывать. Концепт 2 (`fs.readFile`) работает на любой версии Node.js.

**Контраргумент 4: Отсутствие обработки ошибок**

При ES-импорте, если `package.json` битый или отсутствует, сервис не стартует вовсе — будет syntax error на этапе загрузки модуля. При `fs.readFile` мы можем вернуть 500 с внятным сообщением или degrade gracefully.

### Раунд 2 — Пересмотр

#### Архитектор:

Учитываю критику.

**Ответ на "Скрытое связывание":**

Структура `package.json` в корне проекта — это стандарт Node.js. Это не "скрытое связывание", а следование конвенции экосистемы. Переезд `package.json` из корня сломает не только наш импорт, но и `npm install`, `node -v`, и всю работу с пакетами. Это риск, который есть у любой Node.js-системы, а не нашего решения.

**Ответ на "Версия устарела без перезапуска":**

Для демо-стенда это не проблема: версия кода = версия запущенного процесса. Если процесс не перезапустили, он и работает со старым кодом — версия должна отражать это.

Но если бы это было production-решение с hot reload — да, согласен, Концепт 1 не подходит. Тогда нужен Концепт 2 с периодическим перечитыванием или сигналом SIGHUP.

**Ответ на "Требование Node.js изменится":**

Согласен, Концепт 2 более переносим. Но вопрос: есть ли реальный риск понижения требования с Node.js 22 на старые версии? В [`package.json:11-12`](package.json:11-12) указано `>=22` — это сознательное решение. Если бы проекту нужна была совместимость с 18/20, там было бы `>=18`.

**Ответ на "Отсутствие обработки ошибок":**

Если `package.json` битый или отсутствует — **сервис не должен работать**. Это правильное поведение: без версии деплой мы не можем понять, что выкачано. Фейл-фаст — это баггарят, а не дефект.

Однако признаю: Концепт 2 даёт больше контроля в scenarios, где версия опциональна.

**Усиление позиции:**

Добавляю аргумент **тестопригодность**. С Концептом 1 тесты проще: мы можем мокать `package.json` через changing import или используя тестовый package.json. С Концептом 2 нам нужно либо мокать `fs`, либо тестировать реальный I/O — что медленнее и хрупче.

#### Адвокат Дьявола:

Проверяю усиленную позицию.

**Проверка "Ошибка запуска = правильно":**

Согласен, для демо-стенда фейл-фаст при отсутствии `package.json` — это правильно. Но что если сервис запускается в environments, где `package.json` монтируется отдельно (например, в Kubernetes configMap)? Тогда Концепт 1 не стартует вообще, а Концепт 2 мог бы вернуть degrade-режим.

**Проверка "Структура package.json стандарт":**

Да, но что если проект переедёт на monorepo с `package.json` в подкаталогах? Концепт 1 сломается, Концепт 2 можно адаптировать изменением пути.

**Проверка "Концепт 2 избыточен":**

Смотрю на код Концепта 2 — это ~10-15 строк кода вместо 2 строк в Концепте 1. Больше кода = больше багов. Для демо-стенда, где все ограничения фиксированы, простота важнее гибкости.

**Новый what-if: Что если потребуется версия не только из package.json?**

Например, добавить git-sha, build-time, environment. Концепт 1 придётся расширять до комбинации импортов. Концепт 4 (build-time инъекция) был бы лучше. Но это уже другая задача.

### Раунд 3 — Вердикт

#### Архитектор — итоговая позиция:

**Концепт 1 остаётся моим выбором** для текущей задачи.

**Финальные аргументы:**

1. **Задача демо-стенда** — ограничения фиксированы, environment стабильный, требования к гибкости минимальны
2. **Простота кода** — 2 строки вместо 10-15, меньше мест для ошибок
3. **Нативность** — использует возможности платформы, не изобретает велосипед
4. **Консистентность** — следует паттерну `/healthz` из [`server.mjs:43-50`](server.mjs:43-50)
5. **Соответствие ограничениям** — все требования выполнены

**Признание рисков:**

- Если проект переедёт в monorepo или изменится структура — потребуется адаптация. Но это refactoring, а не баг текущего решения.
- Если потребуется hot reload версий — придётся перейти на Концепт 2 или 4.

#### Адвокат Дьявола — итоговая позиция:

Признаю **Концепт 1 приемлемым** для текущих ограничений задачи.

**Согласие с выбором:**

- Для демо-стенда с фиксированным environment риски Концепта 1 минимальны
- Простота кода перевешивает гибкость Концепта 2
- Фейл-фаст при отсутствии `package.json` — правильное поведение

**Остающиеся опасения:**

- Если контекст задачи изменится (monorepo, hot reload, degrade-режим) — решение нужно пересматривать
- Тестирование edge-кейсов (битый package.json, отсутствующий файл) должно быть явно прописано

### Вердикт

**Концепт 1 (ES-импорт JSON) ПРИНЯТ с модификациями.**

**Модификации (по критике Адвоката):**

1. Добавить в требования явное specification: версия грузится при старте сервиса, обновляется только при перезапуске
2. Добавить тестовый сценарий: поведение при отсутствии/битом `package.json` — сервис не стартует (это ожидаемое поведение)
3. Документировать в комментариях к коду: версия привязана к старту процесса, для hot reload требуется перезапуск

**Альтернатива на случай изменения контекста:**

Если в будущем возникнет потребность в hot reload версий или degrade-режиме — перейти на Концепт 2 (fs.readFile с кешированием и сигналом перечитывания).

**Почему не другие концепты:**

- **Концепт 2:** Избыточен для текущих ограничений, больше кода = больше рисков
- **Концепт 3:** Нарушает требование "версия из package.json", риск рассинхронизации
- **Концепт 4:** Избыточен для демо-стенда, нет separate build step
- **Концепт 5:** Прямо противоречит ограничению "/healthz не меняется"

**Следующий шаг:** Генерация системных требований на основе утверждённого Концепта 1 с модификациями.
